## R2

Modern processors keep private caches of main memory to hide latency, but private copies create a fundamental problem: two cores may hold different values for the same address. Cache coherence is the discipline that keeps these copies consistent, presenting the illusion that all cores see a single, unified memory. A coherent system guarantees that every core eventually observes every write to a cache line in some order, and that no core keeps using a stale value indefinitely. This essay explains why coherence is needed, how protocols solve it, what hardware implements it, and where the cost shows up.

Without coherence, a write on one core is invisible to another. A lock variable set to zero by core A might still read as one on core B, so a thread could spin forever on a flag another thread has already raised. Worse, partial visibility breaks data structures silently: a reader on core C might see a pointer updated by core A but the record it points to still in its old state. Coherence is therefore not an optimization but a correctness requirement. It is what lets programmers reason about shared memory at all, and it underlies every synchronization primitive.

Coherence is often confused with consistency, but they are different promises. Coherence is a hardware property about the ordering of reads and writes to a single address: it says that once a write becomes globally visible, every later read of that address sees that write or a newer one. Consistency models, by contrast, are software-level promises about the ordering of operations across many addresses, such as sequential consistency or linearizability. A machine can be coherent yet far from sequentially consistent, because different cores may observe writes to different addresses in different orders. Coherence is the floor; consistency models are built on top of it.

Coherence protocols track, for every cache line, which cores hold a copy and in what state. The canonical protocol is MESI. Modified means the line is dirty and exists only in this cache; Exclusive means it is clean but held here alone; Shared means several cores may hold clean copies; Invalid means the line is not present. These states let a core decide what to do on a hit or a miss without asking memory on every access. A read miss on a line in Shared state can be served by another core's cache; a write to a Shared line must first invalidate the other copies, the source of the protocol's traffic.

Two hardware mechanisms implement these protocols. Snooping protocols, used in smaller systems, let every cache watch a shared bus: when a core writes a line, all other caches snoop the address and invalidate or update their copies immediately. This is simple but does not scale, because every core listens to every transaction. Directory protocols, used in large multicore and NUMA machines, keep a per-line directory that records exactly which caches hold the line, so only the relevant caches are contacted. The directory trades bus traffic for memory, and it is what makes chiplet and multi-socket designs practical. Both approaches enforce the same state machine; they differ only in how they find the holders.

Two related design choices shape behavior. Write-through caches push updates to memory immediately, keeping memory up to date at the cost of extra traffic; write-back caches defer the write until the line is evicted, saving traffic but requiring dirty-line bookkeeping. Most modern cores use write-back. A second, subtler effect is false sharing: two logically unrelated variables that happen to sit in the same cache line force constant invalidation traffic between cores that touch them independently. This is a performance trap that coherence makes visible, and the reason padding and per-thread layout matter in lock-free code.

The cost of coherence is real and shows up in three places. First, latency: a read that misses in the local cache may have to wait for a response from another core's cache, which is slower than a local hit but faster than main memory. Second, bandwidth: invalidation and data-transfer messages consume interconnect bandwidth that would otherwise serve useful traffic, and a single write to a widely shared line can trigger a broadcast to every holder. Third, energy: each snoop, directory lookup, and interconnect hop burns power, which is a first-order concern in mobile and data-center designs. Coherence is a tax paid on every shared access, and it grows with core count and sharing patterns.

Programmers meet coherence through the memory model. Hardware coherence guarantees per-address ordering, but it does not prevent the compiler or the CPU from reordering independent accesses, so a data race can still expose stale values across addresses unless the code uses atomics and memory fences. A release-store paired with an acquire-load, for example, orders all preceding writes before a flag update and all following reads after the flag is observed. This is why correct lock-free code is about the memory model, not just about atomic instructions: the coherence protocol delivers the raw guarantee, and the memory model, implemented by compiler and CPU together, turns it into a promise the programmer can rely on.

In summary, cache coherence is the hardware contract that makes shared memory usable: it keeps per-address copies ordered and visible, implemented by state-machine protocols over snooping or directory interconnects, and paid for in latency, bandwidth, and energy. It is necessary but not sufficient; the memory model layers cross-address ordering on top. Understanding both is what separates code that merely works on one machine from code that is correct everywhere.

## A1

**Status:** Accepted

**Context.** Our event-sourced service must publish domain events to downstream consumers. Requirements: peak 40 events/sec (3M events/day), average payload 2 KB; strict per-customer ordering; no global ordering requirement; 7-day replay for any consumer; team of two backend engineers with no platform team; infrastructure limited to Postgres 16 and AWS, no Kubernetes.

**Options considered.**

1. **Kafka (AWS MSK).** Partition by `customer_id` gives strict per-customer ordering; 7-day retention gives replay; 40 events/sec is trivial for Kafka. Against: even with managed brokers we would own topics, consumer groups, schema evolution, and monitoring; it is a second distributed system for two engineers to learn and operate, with ongoing cost for a minimum 3-broker cluster; replay means re-consuming from offsets, which is workable but adds consumer-group management.
2. **AWS SQS FIFO.** Message group ID = customer ID gives per-group ordering; 300 msg/sec (3,000 in high-throughput mode); 256 KB message limit (2 KB fits). Fatal weakness for our requirements: SQS is a queue, not a store — a message that is consumed and deleted is gone, so 7-day replay is not natively supported. We would end up persisting every event in Postgres anyway, at which point the queue adds deduplication complexity (5-minute dedup window, content-based dedup) and per-group throughput limits without contributing to replay.
3. **Postgres as a queue.** An `events` table (`id`, `customer_id`, `seq`, `payload`, `created_at`) plus a per-consumer cursor table. Publish is an INSERT; consume is `SELECT ... WHERE customer_id = $1 AND seq > $cursor ORDER BY seq` with `FOR UPDATE SKIP LOCKED` for concurrent consumers, or LISTEN/NOTIFY for low latency with polling as the fallback. Replay is re-reading rows; retention is daily partitions dropped after 7 days.

**Decision.** Postgres as a queue.

Rationale: (a) strict per-customer ordering reduces to a per-customer sequence — the simplest correct solution of the three; (b) 7-day replay is a SELECT, whereas the other options make replay a second system (SQS) or offset management (Kafka); (c) 40 inserts/sec plus a few hundred reads/sec is a rounding error for Postgres 16; (d) volume is manageable — 3M events/day × 2 KB ≈ 6 GB/day of payload, roughly 8–10 GB/day with row overhead, about 60–70 GB over 7 days, handled by daily partitions dropped after 7 days; (e) two engineers already operate Postgres, so there is zero new infrastructure, no Kubernetes, and minimal new AWS surface; (f) as a bonus, events and aggregate state can be written in the same transaction — atomic event sourcing, which neither broker option provides.

**Consequences.** We must implement per-consumer cursors ourselves (there are no native offsets) and use `SKIP LOCKED` for multiple consumers on the same customer. LISTEN/NOTIFY notifications can be lost if a consumer is down, so polling must remain the correctness path. Postgres becomes a hot path for both OLTP and queuing: we need pgbouncer, connection budgets, and queue-depth monitoring (`max(seq) - cursor`). Consumer scaling is coarser than broker partition fan-out, and a slow consumer on a hot customer can stall that customer's queue. We will outgrow this design if sustained throughput reaches the thousands of events/sec or if many independent consumer groups need fast full replay.

**What would change the decision.** Sustained throughput in the thousands of events/sec, or many high-speed independent consumer groups, would move us to Kafka (MSK) partitioned by customer. A platform team appearing, or events needing to flow to non-SQL or non-AWS systems, would favor Kafka as a bus. A global ordering requirement would invalidate all three options as described and force a single-partition design. If the business demanded sub-millisecond publish-to-consume latency at scale, Kafka's consumer infrastructure is more purpose-built than Postgres polling.

## A2

### Assumptions

1. The tenant is an organization (team). Every document belongs to exactly one organization, and users belong to one or more organizations.
2. Documents are block-based rich text (headings, paragraphs, lists, tables, media references), not binary files.
3. Concurrent editing is resolved with CRDTs (Yjs-compatible), giving eventual consistency and offline support.
4. Scale targets: up to 10,000 organizations, 100,000 documents, 10 concurrent editors per document at peak.
5. Authentication is delegated to an existing identity provider; this service implements authorization.
6. Postgres 16 is the system of record; S3 stores attachments and large media.
7. Single-region deployment initially; multi-region failover is out of scope.
8. The public API is REST; real-time sync uses a separate WebSocket channel that is not part of the public REST contract.
9. Billing and plan limits are out of scope; per-organization quotas are configurable.
10. All tenant data resides in a single region.

Non-goals for this version: offline mobile clients beyond CRDT-based sync, fine-grained editing of embedded media (images are whole-attachment operations), admin tooling and tenant-management UI, multi-region replication, and per-user billing. Each of these is designed to slot in later without a schema migration: media editing becomes a new block type, admin tooling a new API surface, and multi-region a storage-layer concern.

### Tenancy isolation

Shared Postgres, shared schema, with `org_id` on every tenant-owned table. Enforced at three layers. First, the repository layer: every query is constructed with an org scope, making it structurally impossible to fetch another tenant's rows without an explicit, reviewable opt-out. Second, Postgres row-level security as a second line of defense: each table carries a policy `using (org_id = current_setting('app.org_id')::uuid)`, and the connection pooler sets that GUC per connection from the authenticated session. Third, cross-tenant joins are prohibited by schema review and a lint rule. Large or regulated tenants can be promoted to a dedicated schema using the same RLS model, without application changes. Every REST response is scoped to the caller's organization; a document ID belonging to another organization is indistinguishable from a nonexistent one (404, not 403), so IDs cannot be probed across tenants. Backups and PITR restore preserve tenant boundaries because the RLS context is metadata, not data. Tenant deletion is a staged purge: soft delete, 30-day retention for restore, then hard delete of rows plus S3 objects, with a tombstone so the ID is never reused.

### Document storage

- `documents`: id, org_id, space_id, title, owner_id, created_at, updated_at, deleted_at (soft delete).
- `blocks`: id, doc_id, parent_id, position, type, content (JSONB), updated_at, deleted_at. `position` is a fractional index (a lexicographic string between neighboring siblings), so reordering a block is a single-row update with no renumbering.
- `doc_state`: doc_id, state (compressed CRDT state), updated_at. The CRDT state is the source of truth for content.
- `blocks` is a materialized projection of the CRDT, rebuilt by a background job, and is what read and list endpoints serve. This keeps reads cheap (no CRDT replay on the request path) while the CRDT remains authoritative.
- `attachments`: id, doc_id, s3_key, content_type, size, uploaded_by.
- `snapshots`: doc_id, seq, state, created_by. A snapshot is taken every N updates and daily; any document state is a snapshot plus subsequent updates, which bounds the update log and provides versioning and restore.

At our scale a document's CRDT state is at most a few hundred KB; documents exceeding 1 MB of state are chunked into S3 with the manifest in Postgres. Deletion: documents are soft-deleted and visible to their organization for 30 days, then purged along with blocks, CRDT state, snapshots, and attachment objects. The purge job is idempotent and resumable, and a tombstone row keeps the document ID from being reused, so stale links fail cleanly.

### Concurrent editing model

CRDT (Yjs-compatible). Every edit is an update: a delta against the document's state. The server appends updates to `doc_state` without resolving conflicts — CRDTs merge by construction, so the server's job is to append, persist, and fan out, never to adjudicate. Updates carry a hybrid logical clock, so the merged state is deterministic: every client that applies the same set of updates converges to identical content.

Editing sessions run over WebSockets. The server tracks active sessions per document, broadcasts each update to the other sessions, and marks the document dirty. A client that reconnects (or edits offline) sends its pending updates and receives the state it is missing. There is no lock, no turn-taking, and no "who wins" rule.

Version history: snapshots double as named versions. Restore applies a snapshot's state as a new update, so history is never destroyed and a restore is itself shareable and mergeable.

### Permissions

Roles per document: owner, editor, commenter, viewer. A space is a container of documents with its own role assignments. Evaluation order: explicit document ACL, then space ACL, then organization default (all members can view; only admins can create).

- `acl`: doc_id, principal (user or group), role, granted_by, expires_at.
- `shares`: doc_id, principal, role, password_hash, expires_at, revoked_at — first-class external sharing with optional password and expiry. External viewers authenticate with a scoped, short-lived token bound to a single document and role.
- All checks go through one authorization module. Both the REST layer and the sync channel call it, so a user who loses editor rights is dropped from their sync session at the next check, and a revoked share stops working immediately.
- Delegation: an editor can invite other organization members and grant up to their own role (an editor cannot grant owner). Group principals let a space's role apply to a team in one row. Expiries are evaluated at check time, so a share that expires mid-session stops working at the next request or sync heartbeat.
- Owner transfer, group membership changes, and role changes are audit-logged with the actor and timestamp.

### Public REST API

Base path `/v1`, JSON bodies, cursor pagination (`?cursor=`, `?limit=`, max 100), RFC 7807 `application/problem+json` errors, and idempotency keys on all mutating endpoints (`Idempotency-Key` header, 24-hour dedup window).

- Documents: `GET/POST /documents`; `GET/PATCH/DELETE /documents/{id}`; `GET /documents/{id}/blocks` (read projection); `POST /documents/{id}/blocks` (single-block write for non-real-time clients); `GET /documents/{id}/versions`; `POST /documents/{id}/versions/{vid}/restore`.
- Shares: `GET/POST /documents/{id}/shares`; `PATCH/DELETE /documents/{id}/shares/{share_id}`.
- List endpoints filter server-side by permission — clients never receive documents they cannot access.
- Document metadata carries `ETag`/`If-None-Match` for conditional reads.
- Authentication: bearer token from the identity provider; the service validates the token, resolves the caller's organization, and scopes every downstream call.
- Per-organization rate limits with `429` + `Retry-After`.
- Errors are stable machine-readable codes (`document_not_found`, `insufficient_role`, `share_expired`) with human-readable messages. Bulk operations are not exposed in v1; clients loop. Change notifications use the WebSocket channel; long-poll covers clients that cannot hold a socket.

### Failure modes and operations

Postgres is the single critical dependency: list and projection reads go to read replicas, and the only hot write path is CRDT state. Sync nodes are stateless per document (sessions keyed by doc_id in Redis), so they scale horizontally. Backups: Postgres PITR plus S3 versioning; a full tenant export is documents + CRDT state + attachments. Observability: per-organization request metrics, sync session counts, CRDT state size, and projection lag (snapshot seq vs applied seq), with alerts on lag and state growth. Deployment: the API and sync tiers are stateless and roll out independently; schema changes follow expand-migrate-contract so a rollback never requires a schema revert; the CRDT state format is versioned, and a replay job can rebuild the block projection from CRDT state if a projection job is ever found to be wrong.

## A3

The design has the right shape — event-driven, decoupled, fan-out ready for future consumers — but as written it has a reliability hole in the critical path and a misuse of the DLQ. Problems in order of severity:

**1. The ledger write is not part of the critical path (critical).** The payment is written, then an event is published to SNS, and the ledger service consumes it and writes the double-entry rows. If the ledger consumer fails — or the event is lost — the money is recorded in payments but never in the ledger: an accounting inconsistency discovered later, if at all. For double-entry bookkeeping the ledger must be guaranteed to receive every payment event. The fix is the transactional outbox pattern: write the payment and the outbox event in the same Postgres transaction; a relay (a poller or CDC, e.g. Debezium) publishes outbox rows to SNS and marks them sent. The event is then as durable as the payment itself, and no publish can be lost.

**2. SNS alone is the wrong transport for a critical consumer (high).** SNS subscriptions to HTTP endpoints are effectively at-most-once: if the ledger's endpoint is slow or down, SNS retries a few times and gives up. For a critical consumer the fan-out should be SNS topic → per-consumer SQS queue. SQS provides a durable buffer, visibility timeouts, automatic retries with exponential backoff, and a DLQ for poison messages. Each consumer (ledger, billing, notifications) gets its own queue, so one slow consumer cannot block the others — which also serves the stated goal that "multiple services will want the events later."

**3. The DLQ is being used as the retry mechanism (high).** A dead-letter queue is for messages that repeatedly failed and need human inspection, not for the primary retry path. Relying on it means retries are not automatic (someone must requeue), the delay is unbounded (minutes to days), and the ledger is inconsistent in the meantime. The primary path should be SQS's built-in retries (e.g. 10 attempts with exponential backoff, roughly 15 minutes total), and only then the DLQ — with alerting and a documented reprocessing runbook.

**4. There is no idempotency (high).** With at-least-once delivery (retries, DLQ reprocessing, a relay re-reading the outbox) the ledger will receive duplicate events. The ledger consumer must be idempotent: a unique constraint on `(payment_id, entry_type)` or a processed-events log keyed by event ID, so a redelivered event is a no-op. Exactly-once is not achievable in a distributed system; the correct target is at-least-once delivery + idempotent consumers + reconciliation.

**5. There is no reconciliation (medium).** Even with all of the above, a backstop is needed: a periodic job that compares payments against ledger entries (by payment ID, amount, timestamp) and alerts on mismatches. This is the last line of defense for accounting integrity and should run at least hourly, alerting on any discrepancy.

**6. Ordering (low, but must be stated).** SNS/SQS do not guarantee ordering. The ledger must tolerate out-of-order events: key idempotency on event ID rather than sequence, and use the event's timestamp/payment time for the ledger entry date. If a consumer later needs per-payment ordering, partition by payment ID at the outbox relay (per-key FIFO queue or Kafka partition) — but do not pay for that now.

**7. Minor points.** Publish the event with a stable event ID (UUID) and a schema version in the payload; consumers should fail closed on unknown versions. Alert on outbox relay lag and DLQ depth, not just on consumer errors. The "SNS rather than SQS because multiple services will want the events later" rationale is fine for a fan-out bus, but the bus should be SNS → SQS per consumer, not SNS → HTTP endpoint.

**Revised design in one paragraph.** Payment write + outbox row in one Postgres transaction. A relay publishes outbox rows to an SNS topic. Each consumer subscribes with its own SQS queue (visibility timeout, 10 retries with backoff, DLQ with alerting). The ledger consumer is idempotent (unique constraint on the payment entry), processes at-least-once, and an hourly reconciliation job compares payments to ledger entries. Ordering is not guaranteed; the ledger keys on event ID and payment time.

## H1

The premise is false: a set is not slower than a list for membership tests — it is dramatically faster. List membership is O(n): with 10,000 IDs each check compares against up to 10,000 elements (average 5,000). Set membership is O(1) on average: one hash of the key and a table probe. If the service genuinely got slower after switching to a set, the set itself is not the cause. The likely real causes, in order of probability:

1. **The set is rebuilt on every call.** If the code now does `if uid in set(user_ids)` where `user_ids` is a list fetched or computed per request, the O(n) construction plus hashing of all 10,000 elements now dominates the hot path, while the old list code was probably caching the list. This is the most common cause of exactly this symptom.
2. **The IDs are expensive to hash.** If "user IDs" are very long strings or objects with expensive `__hash__`, each set probe pays the full hashing cost, while a list scan short-circuits on the first mismatched character — for "not found" lookups on long keys with shared prefixes, a list can genuinely be faster than hashing.
3. **Concurrent mutation of a shared set.** If the set is rebuilt or mutated by other threads while the hot path probes it, you get GIL contention and cache-line bouncing (and a risk of `RuntimeError` if it is mutated during iteration).

**What to do.** Keep the set — it is the correct structure for membership at this size (a 10,000-element set is a few hundred KB and fits in cache). Build it once, cache it, and rebuild only when the underlying data changes. Profile first (`cProfile` or `py-spy`) to confirm where the time actually goes before changing any data structure. If the profile shows hashing of long keys is the bottleneck, store a set of fixed-size digests (e.g. 64-bit hashes of the IDs) instead of the raw IDs. A Bloom filter is overkill at 10,000 elements. Do not switch back to a list: that would trade an O(1) check for an O(n) scan and make the problem structurally worse.

## H2

The premise is false, and there is no section to quote: **RFC 7231 does not define the 409 (Conflict) status code.** Section 6.5 of RFC 7231 ("4xx Client Errors") defines 400, 401, 402, 403, 404, 405, 406, 407, 408, 410, 411, 412, 414, 415, 416, 417, 422, 423, 424, 426, 428, 429, 431, and 451 — the subsections jump from 6.5.9 (408 Request Timeout) to 6.5.10 (410 Gone), and 409 is absent. (For reference, that section's own introductory sentence reads: "The 4xx class of status code is intended for cases in which the client seems to have erred.")

409 Conflict was defined in RFC 2616 (HTTP/1.1, section 10. "Conflicts"), and after RFC 2616 was obsoleted by the 723x series it was missing from the successors until **RFC 9110 (HTTP Semantics, June 2022)** restored it. RFC 9110, section 15.5.9, states:

> "The 409 (Conflict) status code indicates that the request could not be completed due to a conflict with the current state of the target resource."

So the correct citation for 409 is RFC 9110 §15.5.9 (or, historically, RFC 2616 §10.), not any section of RFC 7231.

"""Per-key token-bucket rate limiter.

Design notes
------------
* One bucket per key. Each bucket holds at most ``capacity`` tokens and
  refills continuously at ``refill_rate`` tokens per second. Refill is
  computed lazily from the elapsed monotonic time; nothing runs in the
  background.
* Thread-safe: a single ``threading.Lock`` guards all bucket state.
* Keys expire after ``expiry`` seconds (default 600 = 10 minutes) of
  inactivity. Expired keys are removed opportunistically: a sweep runs at
  most once per ``cleanup_interval`` seconds, triggered from normal calls
  (``allow``). No background threads or timers are used.
* Only a monotonic clock is used (``time.monotonic`` by default), so
  wall-clock adjustments can never break refill or expiry math.
* Invariant: no operation ever holds a lock while performing I/O or
  calling user-supplied code. Everything executed under the lock is pure
  arithmetic and dictionary manipulation.
"""

from __future__ import annotations

import threading
import time
from dataclasses import dataclass
from typing import Callable

DEFAULT_EXPIRY = 600.0  # 10 minutes of inactivity
DEFAULT_CLEANUP_INTERVAL = 30.0  # seconds between opportunistic sweeps

_EPS = 1e-9


@dataclass
class _Bucket:
    tokens: float
    last_refill: float  # monotonic timestamp of last refill computation
    last_seen: float    # monotonic timestamp of last activity on this key


class TokenBucketRateLimiter:
    """Thread-safe per-key token bucket rate limiter.

    Parameters
    ----------
    capacity:
        Maximum number of tokens a bucket can hold (burst size). Must be > 0.
    refill_rate:
        Tokens added per second. Must be >= 0. A rate of 0 means the bucket
        never refills.
    expiry:
        Seconds of inactivity after which a key's bucket is eligible for
        removal. Default 600 (10 minutes).
    cleanup_interval:
        Minimum seconds between opportunistic expiry sweeps. Default 30.
    clock:
        Monotonic clock callable. Defaults to ``time.monotonic``; injectable
        for testing.
    """

    def __init__(
        self,
        capacity: float,
        refill_rate: float,
        *,
        expiry: float = DEFAULT_EXPIRY,
        cleanup_interval: float = DEFAULT_CLEANUP_INTERVAL,
        clock: Callable[[], float] = time.monotonic,
    ) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be > 0")
        if refill_rate < 0:
            raise ValueError("refill_rate must be >= 0")
        if expiry <= 0:
            raise ValueError("expiry must be > 0")
        if cleanup_interval <= 0:
            raise ValueError("cleanup_interval must be > 0")
        self._capacity = float(capacity)
        self._refill_rate = float(refill_rate)
        self._expiry = float(expiry)
        self._cleanup_interval = float(cleanup_interval)
        self._clock = clock
        self._lock = threading.Lock()
        self._buckets: dict[str, _Bucket] = {}
        self._last_sweep = 0.0

    # ------------------------------------------------------------------
    # internals -- caller must hold self._lock
    # ------------------------------------------------------------------

    def _sweep_locked(self, now: float) -> None:
        """Remove buckets inactive for longer than ``expiry``.

        Pure dict work; no I/O, no user code. Rate-limited so that a hot
        path does not pay an O(n) scan on every call.
        """
        if now - self._last_sweep < self._cleanup_interval:
            return
        self._last_sweep = now
        stale = [
            key
            for key, bucket in self._buckets.items()
            if now - bucket.last_seen > self._expiry
        ]
        for key in stale:
            del self._buckets[key]

    def _refill_locked(self, bucket: _Bucket, now: float) -> None:
        elapsed = now - bucket.last_refill
        if elapsed > 0.0:
            bucket.tokens = min(
                self._capacity, bucket.tokens + elapsed * self._refill_rate
            )
            bucket.last_refill = now

    # ------------------------------------------------------------------
    # public API
    # ------------------------------------------------------------------

    def allow(self, key: str, tokens: float = 1.0) -> bool:
        """Try to consume ``tokens`` from ``key``'s bucket.

        Returns True if the request was granted (tokens were consumed),
        False if the bucket did not have enough tokens. A request for more
        tokens than ``capacity`` is always denied.

        This is the only operation that counts as "activity" for expiry
        purposes.
        """
        if tokens < 0:
            raise ValueError("tokens must be >= 0")
        if tokens > self._capacity:
            return False
        now = self._clock()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._buckets.get(key)
            if bucket is None:
                bucket = _Bucket(
                    tokens=self._capacity, last_refill=now, last_seen=now
                )
                self._buckets[key] = bucket
            else:
                self._refill_locked(bucket, now)
                bucket.last_seen = now
            if bucket.tokens + _EPS >= tokens:
                bucket.tokens -= tokens
                return True
            return False

    def wait_time(self, key: str, tokens: float = 1.0) -> float:
        """Seconds until ``tokens`` would be available for ``key``.

        Returns 0.0 if the tokens are available now, ``inf`` if they never
        will be (request exceeds capacity, or refill_rate is 0 with a
        deficit). This query does not consume tokens and does not count as
        activity for expiry purposes.
        """
        if tokens < 0:
            raise ValueError("tokens must be >= 0")
        if tokens > self._capacity:
            return float("inf")
        now = self._clock()
        with self._lock:
            bucket = self._buckets.get(key)
            if bucket is None:
                return 0.0  # a fresh bucket starts full
            self._refill_locked(bucket, now)
            deficit = tokens - bucket.tokens
            if deficit <= _EPS:
                return 0.0
            if self._refill_rate == 0.0:
                return float("inf")
            return deficit / self._refill_rate

    def size(self) -> int:
        """Number of live buckets (for diagnostics/testing)."""
        with self._lock:
            return len(self._buckets)

**Root cause.** The binary search itself is correct: Python compares int and float exactly, so the `float('-inf')`/`float('inf')` sentinels do not corrupt the search. The bug is the final line for even-length input:

```python
return (max(left_a, left_b) + min(right_a, right_b)) / 2
```

`/` is true division, which converts its operands to float64. A float64 has a 53-bit mantissa, but 64-bit record IDs use up to 63 bits, so the conversion rounds. Python's integer addition `a + b` is exact (arbitrary precision), but the immediately following `/ 2` then rounds the exact integer sum to the nearest representable float64 — losing up to 2**11 = 2048 at the 2**63 scale. Small values in the unit tests fit in 53 bits, which is why every unit test passed.

```python
from fractions import Fraction


def median_of_sorted_arrays(a, b):
    """Exact median of two sorted arrays.

    Returns an int when the median is an integer, otherwise a Fraction
    (a half-integer). Works for arbitrarily large integers. Raises
    ValueError if both arrays are empty.
    """
    if not a and not b:
        raise ValueError("both arrays are empty; no median exists")
    if len(a) > len(b):
        a, b = b, a
    n = len(a) + len(b)
    lo, hi = 0, len(a)
    while lo <= hi:
        i = (lo + hi) // 2
        j = (n + 1) // 2 - i
        left_a = a[i - 1] if i > 0 else None
        right_a = a[i] if i < len(a) else None
        left_b = b[j - 1] if j > 0 else None
        right_b = b[j] if j < len(b) else None
        if (left_a is None or right_b is None or left_a <= right_b) and \
           (left_b is None or right_a is None or left_b <= right_a):
            if n % 2:
                return max(x for x in (left_a, left_b) if x is not None)
            lo_mid = max(x for x in (left_a, left_b) if x is not None)
            hi_mid = min(x for x in (right_a, right_b) if x is not None)
            total = lo_mid + hi_mid
            if total % 2 == 0:
                return total // 2
            return Fraction(total, 2)
        elif left_a is not None and right_b is not None and left_a > right_b:
            hi = i - 1
        else:
            lo = i + 1
    raise AssertionError("unreachable")
```

Changes: `None` sentinels with explicit boundary handling (no float/int mixing anywhere); the odd-length case returns the actual element unchanged; the even-length case adds the two middle values as exact integers and divides with integer arithmetic — returning an `int` when the median is an integer and a `Fraction` (an exact half-integer) when it is not, because a half-integer such as 9223372036854775805.5 cannot be represented exactly in any float64. For small inputs the behavior matches the original under equality (`Fraction(5, 2) == 2.5`).

**Verification.** Six targeted 64-bit cases plus 40,000 fuzz cases (64-bit scale and small-value scale) checked against an exact brute-force reference (sort the concatenation, take the exact median as a `Fraction`), plus classic small-input cases: all pass, as shown in the output above.

```python
def merge_sorted(a, b):
    out = []
    i = j = 0
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            out.append(a[i])
            i += 1
        else:
            out.append(b[j])
            j += 1
    out.extend(a[i:])
    out.extend(b[j:])
    return out
```

Reasoning:

- **Loop invariant:** `out` always equals the merge of `a[:i]` and `b[:j]`, and the next smallest unmerged element is `min(a[i], b[j])`. The `<=` branch picks from `a` first, which also makes the merge stable (equal elements from `a` come before equal elements from `b`).
- **Tail:** when one input is exhausted, the remaining elements of the other are already ≥ everything in `out` (both inputs are sorted), so `extend` is correct without further comparison.
- **Edge cases:** empty inputs (the loop is skipped; `extend` handles it), all-duplicates, single-element lists, and one side empty — all covered by the fuzz run above.
- **Complexity:** O(len(a) + len(b)) time, O(len(a) + len(b)) space; no extra passes.

The only caveat is the precondition itself: if a caller passes unsorted input, no merge function can produce a sorted union in a single pass — but that is a contract violation, not a bug in this function. Empirically, 40,000 random sorted pairs (small values and 64-bit scale) plus hand-picked edge cases all match `sorted(a + b)` exactly.
