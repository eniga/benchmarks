## R2
Cache coherence is the discipline of keeping the multiple copies of a memory location that exist in a modern system consistent with each other. In a multicore machine, every core (and often every device) keeps its own private cache, and each cache holds a subset of the address space. If one core writes a word, other cores that later read that word must observe the new value, not a stale one from their own cache. The coherence protocol is the mechanism that makes this happen without forcing every core to talk to main memory for every access.

The basic unit of coherence is the cache line, typically sixty-four bytes, because programs access memory in spatially local patterns. Each line in each cache carries a state that describes how fresh it is and who else knows about it. The classic protocol family is MESI: Modified, Exclusive, Shared, and Invalid. A line in the Shared state is clean and may be held by several caches at once. Exclusive means a single cache holds a clean copy. Modified means the cache holds a dirty copy that differs from main memory, and the memory controller must be told before the line can be shared. Invalid means the copy is stale and must be refetched.

When a core reads an address, its cache checks its own state first. On a hit in a valid state, the read is served locally in a few nanoseconds. On a miss, the core issues a request on the coherence interconnect. In a snooping design, every cache watches the interconnect and reacts to requests addressed to lines it holds. If core A requests a line that core B holds in the Modified state, B is obliged to supply the current value, and the requester marks the line as shared or exclusive depending on whether the access is a read or a write. In a directory-based design, used in large NUMA machines, a directory per line records which caches hold copies, and the home agent of a line coordinates transactions directly with those caches, avoiding a broadcast storm.

Most modern systems implement coherence with an invalidate protocol rather than an update protocol. When a core wants to write a line, it first issues a read-for-ownership request, which invalidates the copies in every other cache and grants the writer exclusive, dirty ownership. The alternative, an update protocol, would broadcast the new value to all sharers on every write, which is wasteful when a line is written many times before it is shared again. Invalidation also pairs naturally with write-back caching, because the dirty copy can be transferred to the new owner or written back to memory at eviction time, rather than on every store.

Write policies add a second dimension. A write-back cache keeps dirty data locally and writes it to memory only when the line is evicted, which reduces memory traffic but requires the transfer of dirty lines during coherence. A write-through cache updates memory on every write, keeping memory fresher at the cost of bandwidth. Write allocation determines whether a partial write fetches the whole line into the cache.

The ordering of these transactions is where coherence meets memory consistency. Coherence guarantees that a single location is seen in a single order by all observers, but it says nothing about the order in which different locations are observed. A weak memory model, such as the one implemented by x86-TSO or ARMv8, allows some reordering of reads and writes to different addresses, and programmers must insert fences or acquire-release operations to build the ordering their algorithms require.

Scalability is the central engineering challenge. A snoopy bus is simple but does not scale beyond a handful of cores, because every transaction is broadcast and every cache must decode it. Directory protocols scale better, but the directory itself becomes a bottleneck and a large memory consumer. Modern chip multipprocessors therefore use hybrid designs: a ring or mesh interconnect, per-core snoop filters that remember which lines are cached where, and home agents that own a slice of the address space.

Coherence also crosses the chip boundary. NUMA systems keep coherence between sockets over the inter-socket link, and the cost of a remote access is several times that of a local one, which is why NUMA-aware allocation matters in practice. Coherent attachment of devices, such as CXL.cache and PCIe atomic operations, extends the same idea to accelerators, letting a GPU or a smart NIC hold coherent lines without bouncing data through main memory.

Finally, coherence interacts with virtual memory. Tags are usually physical, so the translation lookaside buffer and the cache work together, and page-table updates must flush or invalidate the affected lines. Multicast and atomic instructions, such as compare-and-swap, are implemented on top of the same coherence transactions, which is why lock-free algorithms depend on the protocol behaving exactly as specified.

In summary, cache coherence is an invisible layer of distributed-systems engineering that runs on every modern multicore machine. Verifying coherence is itself a research-grade problem: the protocol is a distributed state machine with millions of states, so it is checked with model checkers, formal proofs, and stress tests that hammer the interconnect with adversarial address patterns. It trades bandwidth and protocol complexity for the illusion of a single, consistent memory, and its design choices ripple all the way up to the performance and correctness of the software that runs on top of it.

## A1
**ADR-001: Event transport for the order-processing service**

Status: Accepted. Deciders: the two backend engineers owning the service.

### Context

We are building a new order-processing service. Its event transport must carry domain events (order placed, payment captured, fulfillment updated, and similar) from the order service to downstream consumers (billing, fulfillment, analytics, notifications). The requirements are:

- Peak 40 events/sec; about 3M events/day; average payload 2 KB (roughly 6 GB/day, about 42 GB/week of event data).
- Strict per-customer ordering: events for one customer must be processed in the order they were emitted. Global ordering is not required.
- The last 7 days of events must be replayable for reprocessing.
- The team is two backend engineers, with no dedicated platform team.
- We already run Postgres 16 and AWS; we do not run Kubernetes.

### Options considered

**Kafka (Amazon MSK).** Partitioning by `customer_id` gives strict per-customer ordering, 7-day retention with consumer-group offsets gives replay, and 40 events/sec is a trivial load for a single partition. The problem is operational. Even managed, a Kafka cluster is a new distributed system: brokers and client versions to keep current, monitoring and alerting to build, ACLs and networking to manage, and possibly a schema registry. Two engineers with no platform team and no in-house Kafka experience would spend a real share of their capacity just keeping it healthy. At this volume, that cost buys nothing we actually need.

**AWS SQS FIFO.** Setting `MessageGroupId` to the customer ID gives per-customer ordering, and 300 messages/sec per queue (3,000 with batching) is ample headroom. The fatal gap is replay. SQS deletes a message once it has been processed; the retention period (up to 14 days) only protects messages that have not yet been consumed. To replay the last 7 days of already-processed events we would have to archive every event to S3 or Postgres anyway. At that point the archive, not the queue, is the source of truth, and we have built the Postgres design plus an extra queue on top of it.

**Postgres as a queue.** An append-only `events` table (`id`, `customer_id`, `kind`, `payload jsonb`, `created_at`, `processed_at`), partitioned daily. Consumers claim work with a bounded `SELECT ... WHERE customer_id = ? AND id > ? FOR UPDATE SKIP LOCKED ORDER BY id`, mark rows processed, and a nightly job drops partitions older than 7 days. Per-customer ordering is guaranteed by claiming within a customer in `id` order. Replay is a plain `SELECT` over the retained rows. 40 inserts/sec plus 40 claims/sec is a small fraction of what Postgres 16 handles comfortably, and the team already operates this system every day.

### Decision

Use Postgres 16 as the event queue: an append-only `events` table with `FOR UPDATE SKIP LOCKED` consumer polling.

### Consequences

Positive:

- No new system to operate; the team's existing Postgres skills cover the whole design.
- Transactional outbox for free: the order write and the event append happen in the same Postgres transaction, eliminating the dual-write problem that plagues SNS/SQS designs.
- Replay is a `SELECT`; retention is a partition drop; there is no offset management.
- Per-customer ordering is enforced by the claim query, not by partitioning luck.

Negative and risks:

- Postgres now carries both OLTP and queue load. An aggressive poller adds pressure; mitigate with a short sleep between polls and bounded claim batch sizes.
- Fan-out is limited: each independent consumer group needs its own cursor table. Fine for a handful of consumers, painful for many.
- Retention cleanup must be partition-based or batched to avoid long-running transactions and bloat.
- The design stops being comfortable well before 10x the current volume; that is a known, accepted limit.

### What would change the decision

- Sustained throughput above roughly 1-2k events/sec, or large and bursty payloads: move to MSK Kafka.
- Ten or more independent consumer groups with very different processing speeds: Kafka consumer groups (or SNS fan-out with per-consumer queues).
- A platform team or in-house Kafka expertise appears: Kafka becomes the default choice.
- Replay retention must exceed about 30 days, or the event store must scale independently of the order database: Kafka with longer retention, or S3 as the durable log.

## A2
**Design: multi-tenant document collaboration service**

### Assumptions

1. A tenant is an organization with member users and one or more admin users.
2. A user belongs to exactly one organization; there is no cross-tenant membership in v1.
3. Document content is rich text (a ProseMirror-style document) under about 1 MB; binary attachments are up to 100 MB each.
4. Real-time collaboration supports up to about 10 concurrent editors per document, with a round-trip target under 200 ms within a region.
5. Clients are a web app plus a public REST API; there is no offline-first mobile client in v1.
6. Available infrastructure is Postgres 15+ (single primary, logical replication available) and S3; nothing else is assumed.
7. Authentication (sessions/JWT) already exists; this design covers authorization only.
8. Compliance requires logical separation of tenant data; dedicated hardware per tenant is not required in v1.
9. Scale: up to 10k tenants, 100k documents per tenant, 10k users per tenant.
10. Documents are soft-deleted; tenant offboarding purges all of the tenant's data.

### Tenancy isolation

Strategy: shared database, shared schema, a `tenant_id` column on every tenant-owned row, plus Postgres row-level security (RLS) as a backstop.

- Every tenant-owned table (`documents`, `revisions`, `shares`, `attachments`, `audit_log`) carries `tenant_id uuid NOT NULL`, and its primary indexes lead with `tenant_id`.
- The application sets `SET LOCAL app.tenant_id = '<uuid>'` at the start of each request's transaction, from the verified session, never from user input.
- RLS policies deny by default: `ENABLE ROW LEVEL SECURITY` on every tenant table, with a policy `USING (tenant_id = current_setting('app.tenant_id')::uuid)`. A query that forgets the tenant context sees nothing rather than everything.
- Cross-tenant access tests run in CI: for two fixture tenants, every repository read made as tenant A must return zero rows belonging to tenant B.
- S3: one bucket, key prefix `tenants/{tenant_id}/documents/{doc_id}/...`, no bucket ACLs; access only through short-lived presigned URLs (15 minutes) or a streaming proxy.
- Why not a schema or database per tenant: at 10k tenants, per-tenant schemas multiply migration, backup, and connection-pooling cost with no meaningful isolation gain for a SaaS with logical separation. If a regulated tier appears later, it can be carved out as a separate deployment of the same code.
- Backups and restore: logical backups (pg_dump per table, filtered by `tenant_id`) plus S3 object versioning; a tenant-level restore is a filtered re-import, which the shared schema makes straightforward.

### Document storage

- `documents`: `id`, `tenant_id`, `title`, `owner_id`, `content_format`, `version` (a logical revision counter), `created_at`, `updated_at`, `deleted_at`, `content_ref` (enum `pg|s3`), `content jsonb` (used when `content_ref = pg`).
- v1 stores current content in Postgres as jsonb. Documents are under 1 MB (assumption 3) and TOAST keeps hot tables slim; this makes reads, permission checks, and revisions local to one transaction.
- The `content_ref` enum is the escape hatch: when a document grows past 1 MB, or a tenant enters a heavy-attachment tier, content moves to S3 and Postgres keeps only the pointer. The API does not change.
- `revisions`: `id`, `doc_id`, `tenant_id`, `version`, `content`, `size`, `created_by`, `created_at`, `label`. Full snapshots, taken automatically (debounced, roughly every 30 seconds of collaborative editing or every N CRDT updates) and on explicit "save version". Retention: last 50 plus daily snapshots for 90 days.
- `attachments`: `id`, `doc_id`, `tenant_id`, `s3_key`, `size`, `mime`, `uploaded_by`, `created_at`. Uploads are presigned PUTs straight to S3; the row is committed after a HEAD check confirms the object.

### Concurrent editing model

Two cooperating layers:

1. **Real-time collaboration via CRDT.** Each document has a Yjs CRDT. The server keeps the CRDT state in memory while a session is open, appends incoming updates, and broadcasts them to other connected clients over a WebSocket. CRDT updates are commutative and convergent, so concurrent edits merge without a central transform step and without user-visible conflicts. Presence (cursors, selections) is ephemeral in-memory state and is never persisted.
2. **Document-level optimistic concurrency for non-real-time writes.** REST saves carry a `base_version`; if it does not match the current version the API returns 409 with the current document so the client can rebase. This covers single-user edits, API integrations, and any fallback client.

Persistence: the in-memory CRDT is snapshotted to `revisions` on a timer and on disconnect; on cold start the server loads the latest snapshot and replays any updates logged since. The `version` counter is a logical value for the UI and the 409 check, not a lock.

Why CRDT rather than OT: no transform server is required for correctness, merging is commutative (which keeps the REST fallback and rebasing simple), and the library is mature. The costs — larger state and more complex debugging — are acceptable at the assumed scale of 10 concurrent editors.

Failure behavior: if the server loses the in-memory CRDT state, it reloads the latest snapshot, and any client whose updates were not yet persisted resends them from its own state vector; because updates are idempotent and commutative, a resend is harmless. A client that disconnects mid-edit reconnects and reconciles against the server's state vector without user intervention.

### Permissions

- Roles: owner > editor > viewer. The creator is the initial owner; ownership is transferable (owner only, audited).
- `shares`: `id`, `doc_id`, `tenant_id`, `principal_type` (`user|group|tenant`), `principal_id`, `role`, `created_by`, `created_at`, `expires_at`.
- Effective permission is the maximum of the applicable shares; `principal_type = tenant` means "everyone in the organization".
- Rules: sharing is within the tenant only (assumption 2); only the owner (or an admin, with an audit entry) can delete or transfer ownership; tenant admins can view any document in the tenant (compliance mode), and every such read is written to `audit_log`; `expires_at` is enforced at check time, not by a background job.
- Enforcement: a single `can(tenant_id, principal, doc_id, action)` in the API layer, backed by one indexed query against `shares` (owner check first, then the share lookup). RLS is the backstop, not the hot path, because per-row policy evaluation on the read path is slower than one explicit query.
- `audit_log`: `tenant_id`, `actor_id`, `action` (`share.created`, `share.deleted`, `owner.transferred`, `doc.deleted`, `admin.view`, ...), `doc_id`, `at`; retained for one year.

### Public REST API

Base path `/api/v1`, Bearer-token auth, JSON bodies, errors as `{"error": {"code", "message"}}`. Pagination is cursor-based (keyset on `(updated_at, id)`) with `?cursor=&limit=` (default 50, max 200). `ETag` on document GETs; `Idempotency-Key` honored on `POST /documents`.

Documents:

- `POST /documents` — body `{title, content?}` → `201` with the document.
- `GET /documents` — list the caller's documents (owned or shared), cursor-paginated.
- `GET /documents/{id}` → `{document, content, version}` (403 without permission, 404 if missing or deleted).
- `PATCH /documents/{id}` — body `{title?, content?, base_version}` → `200` with the new version, or `409` with the current document.
- `POST /documents/{id}/revisions` — body `{content, label?}` → `201` (explicit version).
- `GET /documents/{id}/revisions` — cursor-paginated list.
- `GET /documents/{id}/revisions/{version}` — content at that version.
- `DELETE /documents/{id}` → `204` (soft delete; owner or admin only).
- `POST /documents/{id}/restore` → `200`.
- `POST /documents/{id}/attachments` — multipart upload → `201` with the attachment.
- `GET /documents/{id}/attachments/{attachment_id}/download` → `302` to a 15-minute presigned URL.

Shares:

Real-time (not REST, listed for completeness): `POST /rt/{doc_id}/join` upgrades to a WebSocket; the client sends `{type: "update", base: <state_vector>, data: <base64>}` and receives update and presence frames.

## A3
The instinct to use SNS for fan-out is right, but the design as stated has four real problems.

1. **The publish is not atomic with the payment (dual write).** "Write the payments row, then publish to SNS" is two operations with no transaction spanning them. A crash in between produces either an event with no payment or a payment with no event, and there is no reliable way to detect either. Fix: the transactional outbox pattern. Write the payment row and an outbox row in one Postgres transaction; a relay process polls the outbox and publishes to SNS (at-least-once), marking rows sent. The event now exists if and only if the payment committed, and a relay crash just delays delivery.

2. **The ledger path is not idempotent.** SNS/SQS delivery is at-least-once, and "retry from the DLQ" means deliberate redelivery. The ledger must deduplicate: give every event a unique `event_id` in the payload, and have the ledger insert into a `processed_events` table keyed on it (or `INSERT ... ON CONFLICT (event_id) DO NOTHING` around the double-entry rows). Without this, every retry double-posts the ledger.

3. **Ordering is not guaranteed and is not addressed.** SNS does not order messages, so `PaymentRefunded` can arrive before `PaymentCreated` for the same payment. Either the events carry a per-payment sequence number and the ledger buffers out-of-order events, or each event is designed to be independently applicable (self-contained deltas, idempotent application) so order does not matter. The current design assumes neither.

4. **"SNS DLQ" is a category error.** A raw SNS subscription has no retry queue and no DLQ; it retries a few times and drops (or invokes a Lambda with its own retry). The topology that actually gives retries and a DLQ is SNS topic → one SQS queue per subscriber → that queue's redrive policy to a DLQ. The ledger should consume from its own SQS queue, which also buys visibility timeouts and independent backpressure.

Smaller points: make the event payload self-contained (amount, currency, accounts, timestamps, schema version) so the ledger never has to re-read the payments table — that coupling breaks replay if payment rows are later updated or deleted; validate the double-entry invariant (debits equal credits) per event and alert on violation; and add a periodic reconciliation job comparing payment totals to ledger totals, which is cheap once the outbox and idempotent consumer are in place. Keep SNS itself: fan-out to multiple future consumers is exactly what it is for.

## H1
The premise is backwards, so I can't explain it as stated: for membership tests, a set is faster than a list, not slower. In CPython, `x in list` is a linear scan, O(n) — up to 10,000 element comparisons per check — while `x in set` is a hash-table lookup, O(1) on average, typically one or two probes. For 10,000 user IDs the set should be dramatically faster, and any well-written unit test would show it.

If the service really got slower after the change, the likely causes are:

1. **The set is being rebuilt on every check.** If the code is `if uid in set(user_ids)` with `user_ids` a list, a fresh 10,000-element set is constructed on every call — O(n) hashing per lookup, which is much slower than scanning a list (hashing 10k strings each time versus comparing at most 10k of them). This is the classic version of this bug. Fix: build the set once (at module load, or memoized) and reuse it.
2. **Expensive hashing.** If the IDs are not plain `str`/`int` but objects with a slow or pathological `__hash__` (or very long strings), the set's per-lookup cost rises. Check `type(user_ids[0])` and the cost of hashing one element.
3. **Measurement artifact.** The "slower" observation may be capturing the one-time O(n) construction cost (e.g., first request after a deploy), GC pressure from the larger structure, or an unrelated change shipped alongside. Profile before concluding.
4. **Cache effects** — a 10k-entry set is a few hundred KB of scattered buckets versus a compact pointer array, but this is a small effect and does not overturn the asymptotic advantage.

**Recommendation:** keep the set — it is the correct structure for membership testing — and make sure it is constructed once, not per call. If the IDs are a dense range of small integers, a `bytearray`/bit array indexed by ID is O(1) with better cache behavior, but that is an optimization, not a fix. Profile first to confirm where the time actually goes before changing the data structure.

**Module (`work/rate_limiter.py`):**

```python
"""Per-key token-bucket rate limiter.

Properties
----------
* Token bucket per key, with configurable capacity and refill rate.
* Thread-safe: all shared state is guarded by a single lock.
* Keys not touched for ``expiry`` seconds (default 600 = 10 minutes) are
  evicted, so memory stays bounded.
* No background threads or timers: eviction happens inside normal calls,
  amortized (a full scan runs at most once per ``cleanup_interval``).
* Monotonic clock only (``time.monotonic`` by default), so system clock
  changes cannot affect the limiter. A backward jump of the injected clock
  is tolerated: it simply refills nothing.

Invariant
---------
No operation ever holds the lock while performing I/O or calling
user-supplied code. The only user-supplied callable is the clock, and it is
always invoked *before* the lock is acquired.
"""

from __future__ import annotations

import threading
import time
from dataclasses import dataclass


@dataclass
class _Bucket:
    tokens: float
    last_refill: float
    last_used: float


class TokenBucketRateLimiter:
    """Per-key token bucket.

    Parameters
    ----------
    capacity:
        Maximum number of tokens a bucket can hold (burst size).
    refill_rate:
        Tokens added per second.
    expiry:
        Seconds of inactivity after which a key's bucket is evicted.
        "Touched" means an :meth:`allow` call (allowed or denied).
    cleanup_interval:
        Minimum seconds between full expiry scans. A stale key therefore
        lives at most ``expiry + cleanup_interval`` seconds.
    clock:
        Zero-argument callable returning the current time. Must be
        monotonic; defaults to :func:`time.monotonic`.
    """

    def __init__(
        self,
        capacity: float,
        refill_rate: float,
        expiry: float = 600.0,
        cleanup_interval: float = 30.0,
        clock=time.monotonic,
    ) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be > 0")
        if refill_rate < 0:
            raise ValueError("refill_rate must be >= 0")
        if expiry <= 0:
            raise ValueError("expiry must be > 0")
        if cleanup_interval <= 0:
            raise ValueError("cleanup_interval must be > 0")
        self._capacity = float(capacity)
        self._refill_rate = float(refill_rate)
        self._expiry = float(expiry)
        self._cleanup_interval = float(cleanup_interval)
        self._clock = clock
        self._lock = threading.Lock()
        self._buckets: dict[str, _Bucket] = {}
        self._last_cleanup = clock()

    # ------------------------------------------------------------------
    # Public API
    # ------------------------------------------------------------------

    def allow(self, key: str, tokens: float = 1.0) -> bool:
        """Try to consume ``tokens`` from ``key``'s bucket.

        Returns True and debits the bucket if enough tokens are available,
        False otherwise. Every call counts as activity for the key (it
        refreshes the key's expiry).
        """
        if tokens <= 0:
            raise ValueError("tokens must be > 0")
        now = self._clock()  # user-supplied callable: outside the lock
        with self._lock:
            self._cleanup_locked(now)
            bucket = self._buckets.get(key)
            if bucket is None:
                bucket = _Bucket(self._capacity, now, now)
                self._buckets[key] = bucket
            self._refill_locked(bucket, now)
            bucket.last_used = now
            if bucket.tokens >= tokens - 1e-12:
                bucket.tokens -= tokens
                return True
            return False

    def remaining(self, key: str) -> float:
        """Tokens currently available for ``key`` (refilled up to now).

        A probe: does not count as activity for the key.
        """
        now = self._clock()  # user-supplied callable: outside the lock
        with self._lock:
            bucket = self._buckets.get(key)
            if bucket is None:
                return self._capacity
            self._refill_locked(bucket, now)
            return bucket.tokens

    def __len__(self) -> int:
        """Number of live keys (buckets not yet evicted)."""
        with self._lock:
            return len(self._buckets)

    # ------------------------------------------------------------------
    # Internals -- caller must hold self._lock
    # ------------------------------------------------------------------

    def _refill_locked(self, bucket: _Bucket, now: float) -> None:
        elapsed = now - bucket.last_refill
        if elapsed > 0:
            bucket.tokens = min(
                self._capacity, bucket.tokens + elapsed * self._refill_rate
            )
            bucket.last_refill = now

    def _cleanup_locked(self, now: float) -> None:
        if now - self._last_cleanup < self._cleanup_interval:
            return
        self._last_cleanup = now
        stale = [
            key
            for key, bucket in self._buckets.items()
            if now - bucket.last_used >= self._expiry
        ]
        for key in stale:
            del self._buckets[key]
```

"""Tests for rate_limiter.TokenBucketRateLimiter (unittest, no deps)."""

import threading
import unittest

from rate_limiter import TokenBucketRateLimiter


class FakeClock:
    """Deterministic, manually advanced clock."""

    def __init__(self, start: float = 0.0) -> None:
        self.now = start

    def __call__(self) -> float:
        return self.now

    def advance(self, seconds: float) -> None:
        self.now += seconds


class RateLimiterTests(unittest.TestCase):
    def test_capacity_enforced(self):
        rl = TokenBucketRateLimiter(capacity=5, refill_rate=0, clock=FakeClock())
        for _ in range(5):
            self.assertTrue(rl.allow("k"))
        self.assertFalse(rl.allow("k"))

    def test_refill_over_time(self):
        clock = FakeClock()
        rl = TokenBucketRateLimiter(capacity=5, refill_rate=1.0, clock=clock)
        for _ in range(5):
            rl.allow("k")
        clock.advance(0.5)
        self.assertFalse(rl.allow("k"))  # only 0.5 tokens refilled
        clock.advance(5.0)  # 5.5s total -> refilled back to capacity
        for _ in range(5):
            self.assertTrue(rl.allow("k"))
        self.assertFalse(rl.allow("k"))

    def test_partial_refill(self):
        clock = FakeClock()
        rl = TokenBucketRateLimiter(capacity=10, refill_rate=2.0, clock=clock)
        self.assertTrue(rl.allow("k", 10))
        clock.advance(2.0)  # +4 tokens
        self.assertTrue(rl.allow("k", 4))
        self.assertFalse(rl.allow("k", 1))
        self.assertAlmostEqual(rl.remaining("k"), 0.0, places=9)

    def test_per_key_independence(self):
        clock = FakeClock()
        rl = TokenBucketRateLimiter(capacity=2, refill_rate=0, clock=clock)
        self.assertTrue(rl.allow("a"))
        self.assertTrue(rl.allow("a"))
        self.assertFalse(rl.allow("a"))
        self.assertTrue(rl.allow("b"))
        self.assertTrue(rl.allow("b"))
        self.assertFalse(rl.allow("b"))

    def test_key_expires_after_10_minutes(self):
        clock = FakeClock()
        rl = TokenBucketRateLimiter(
            capacity=1, refill_rate=0, clock=clock,
            expiry=600.0, cleanup_interval=30.0,
        )
        rl.allow("idle")
        clock.advance(601.0)
        rl.allow("other")  # this call triggers the expiry scan
        self.assertEqual(len(rl), 1)  # "idle" evicted, "other" live
        # the evicted key starts fresh at full capacity
        self.assertTrue(rl.allow("idle"))
        self.assertFalse(rl.allow("idle"))

    def test_recently_used_key_not_evicted(self):
        clock = FakeClock()
        rl = TokenBucketRateLimiter(
            capacity=1, refill_rate=0, clock=clock,
            expiry=600.0, cleanup_interval=30.0,
        )
        rl.allow("busy")
        clock.advance(599.0)
        self.assertFalse(rl.allow("busy"))  # denied, but still activity
        clock.advance(2.0)
        rl.allow("other")
        self.assertEqual(len(rl), 2)  # "busy" was touched 2s ago

    def test_thread_safety_exact_capacity(self):
        rl = TokenBucketRateLimiter(capacity=1000, refill_rate=0, clock=FakeClock())
        errors: list[BaseException] = []
        allowed = [0] * 8
        tally = threading.Lock()

        def worker(idx: int) -> None:
            local = 0
            try:
                for _ in range(2000):
                    if rl.allow("shared"):
                        local += 1
            except BaseException as exc:  # noqa: BLE001 - report any failure
                errors.append(exc)
            with tally:
                allowed[idx] = local

        threads = [threading.Thread(target=worker, args=(i,)) for i in range(8)]
        for t in threads:
            t.start()
        for t in threads:
            t.join()
        self.assertEqual(errors, [])
        self.assertEqual(sum(allowed), 1000)  # exactly capacity, no over-allow

## I2

**Why it fails in production but not in unit tests.** The binary search itself is correct; the bug is in the arithmetic. The sentinels are fine, but the even-length branch computes `(max(left_a, left_b) + min(right_a, right_b)) / 2`. In Python 3, `int / int` converts both operands to float64, which has a 53-bit mantissa. 64-bit record IDs above 2^53 are not exactly representable, so each operand is rounded before the addition — and the result is wrong. Unit tests pass because they use small integers (below 2^53), where float64 is exact.

**Reproduction inputs** (64-bit record IDs):

- `a = [2**63 - 1]`, `b = [2**63]` → true median `2**63 - 0.5 = 9223372036854775807.5`; original returns `9223372036854775808.0` (because `float(2**63 - 1)` rounds to `2**63`).

**Fixed function** — same O(log n) binary search, but no data value ever passes through float64: `None` sentinels instead of `±inf`, and exact integer arithmetic for the final average (returns an `int` when the median is integral, an exact `Fraction` otherwise — a `.5` value above 2^53 is not representable in float64 at all):

```python
def median_of_sorted_arrays_fixed(a, b):
    if len(a) > len(b):
        a, b = b, a
    n, m = len(a), len(b)
    if n == 0 and m == 0:
        raise ValueError("at least one array must be non-empty")
    lo, hi = 0, n
    while lo <= hi:
        i = (lo + hi) // 2
        j = (n + m + 1) // 2 - i
        left_a  = a[i-1] if i > 0 else None
        right_a = a[i]   if i < n else None
        left_b  = b[j-1] if j > 0 else None
        right_b = b[j]   if j < m else None
        ok_a = left_a is None or right_b is None or left_a <= right_b
        ok_b = left_b is None or right_a is None or left_b <= right_a
        if ok_a and ok_b:
            max_left = max(x for x in (left_a, left_b) if x is not None)
            if (n + m) % 2:
                return max_left
            min_right = min(x for x in (right_a, right_b) if x is not None)
            total = max_left + min_right
            if total % 2 == 0:
                return total // 2
            return Fraction(total, 2)
        elif left_a is not None and right_b is not None and left_a > right_b:
            hi = i - 1
        else:
            lo = i + 1
    raise AssertionError("unreachable")
```
