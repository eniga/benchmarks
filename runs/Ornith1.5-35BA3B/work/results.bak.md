## R2
A multiprocessor program shares data through main memory, but every core reads and writes via its own private caches. Those caches hold recent copies of memory lines, which speeds up access enormously — but it also means that several cores can simultaneously hold a copy of the same address. If one core updates its copy without telling the others, the other cores keep reading stale values. Cache coherence is the hardware guarantee that all cores agree on the value of a shared memory location: the most recent write is eventually visible everywhere, and a single location behaves, from the programmer's point of view, like one location. Coherence is what makes shared-memory multithreading correct at all.

Coherence is specifically about the ordering of accesses to the same address. It is often confused with memory consistency, which is a broader and weaker contract governing the ordering of accesses across different addresses. A system can be coherent yet allow reads and writes to distinct locations to appear reordered. Coherence answers "what does the next read of address X return?", while consistency answers "in what order does a single core see its own writes relative to another core's writes?" Modern CPUs deliberately separate the two: coherence is enforced locally by the cache subsystem per line, and consistency is exposed as an architecture-specific memory model such as x86's total store order or the weak ordering of ARM and POWER.

Coherence is enforced at the granularity of a cache line, usually 32 to 128 bytes, never a single word. The whole line moves together between coherence states, which has an important side effect called false sharing: two unrelated variables placed on the same line will ping-pong the line between cores and serialize them, even though the threads never intend to coordinate. Performance tuning therefore often centers on aligning or padding hot data so that contended state does not share a line.

Almost all modern write protocols are write-invalidate protocols modeled as a finite state machine over each line. The simplest is MSI: Modified, Exclusive, Shared, Invalid. In Modified exactly one cache holds a dirty copy that differs from memory; in Exclusive one cache holds a clean copy with no other sharer; in Shared several caches hold identical clean copies; in Invalid the line is unusable. Variants extend this picture. MESI introduces an Idle state so that a clean exclusive line can be promoted to clean shared without invalidating others, reducing spurious invalidations. MOESI adds an Owned state so that a dirty line can be served directly from another cache during a shared read, avoiding a round trip to main memory.

The two broad families are write-invalidate and write-update. In write-invalidate, a core that wants to write first invalidates every other copy, so at most one dirty copy ever exists and readers refetch after an invalidation. In write-update, every write is broadcast to all caches that hold the line, so copies never become stale through invalidation, but traffic grows with the number of sharers. Write-invalidate wins in practice because most working sets are read-heavy, making the extra invalidations cheaper than broadcasting every write.

At small core counts, coherence is usually achieved by snooping. All caches attach to a shared bus or low-level interconnect and snoop every transaction. When a core writes a shared line, it broadcasts an invalidation request; the other cores acknowledge and evict their copies before the writer proceeds. If a core reads a line that is dirty elsewhere, the holder performs a "backing read," supplying the data directly. Snooping is simple and fast for a handful of cores, but it does not scale: bus bandwidth saturates and every core must process every transaction, so large machines abandon it.

At scale, systems use directory-based protocols. A directory maintains, for each line, the set of caches that hold a copy and their states. A core sends its requests to the directory rather than broadcasting to everyone; the directory then coordinates invalidations or updates only with the known sharers. This concentrates coordination traffic and removes the all-here fan-out, but it introduces directory lookup latency and significant bookkeeping, and the directory often must be distributed across NUMA nodes so that no single copy becomes a bottleneck. The trade-off is predictable: snooping spends traffic to buy simplicity, while directories spend complexity to buy scale.

Protocol behavior around misses and writes also matters. On a write miss, a design either uses the write-allocate policy — fetching the line into the cache first and then writing locally — or write-through-without-allocate, sending the write directly to the next level. Combined with read-miss fetch policy and line size, these choices fix the hit time and the traffic profile. Bursty write workloads can cause invalidation storms, where one writer repeatedly evicts a line that many readers want; adaptive line sizes and aggressive exclusive-state use mitigate this.

Real hardware illustrates the spread of these ideas. Many multi-socket ARM servers and large x86 servers use distributed directory protocols over a high-bandpoint interconnect to reach dozens or hundreds of cores. Older multi-core consoles and embedded chip multiprocessors leaned on snooping because their core counts stayed modest. Every design encodes the same decision: keep traffic low while keeping the single-copy illusion intact.

For the software engineer, coherence is transparent for correctness but never free for performance. Because the hardware guarantees coherence, shared programs are correct without explicit coordination, but the performance cost shows up as line ping-ponging, invalidation traffic, and cross-core stall cycles. Effective code avoids false sharing with alignment and padding, keeps hot counters off shared lines, prefers per-core or partitioned state, and uses lock-free structures that minimize cross-core writes. Understanding the cache-coherence contract is therefore not only about why shared memory is correct, but about why high-performance concurrent code is hard to write.

## A1
# ADR: Event Transport for the Order-Processing Service

Status: Accepted
Date: 2024-05-01
Deciders: Backend Team (2 engineers)

## Context
We are building a new order-processing service whose core job is to consume business events (order created, paid, shipped, cancelled) and react to them. The transport must handle a peak of 40 events per second and about 3 million events per day, with an average payload of roughly 2 KB. Two hard requirements drive the design. First, ordering must be strictly preserved per customer: all of a given customer's events must be observed and applied in the exact sequence they were produced, because downstream state (order lifecycle) is order-sensitive and out-of-order application corrupts it. Global ordering across customers is not required. Second, the system must support replay of the last 7 days of events for reprocessing after bugs or schema changes. The team is two backend engineers with no dedicated platform team, and we already run Postgres 16 and have AWS accounts in place. We are not running Kubernetes. Three candidates were evaluated: Apache Kafka, AWS SQS FIFO queues, and using Postgres itself as the queue.

## Decision
We will use AWS SQS FIFO queues as the event transport, keyed by customer id, with Postgres retained as the system of record and for building a replay pipeline. Kafka is rejected as over-engineered given our scale and team size; Postgres-as-a-queue is rejected as the primary transport because it pushes polling, delivery-guarantee, and replay complexity onto two engineers who should focus on domain logic.

## Why SQS FIFO
SQS FIFO queues give us per-group strict ordering through the Message Group Id. We set that identifier to the customer id, so every event for one customer is delivered in order while different customers proceed independently, exactly matching our ordering requirement and nothing more. FIFO queues also provide exactly-once delivery through content deduplication and at-least-once delivery semantics that we manage with idempotency keys, plus built-in durability and a dead-letter queue for poison messages. At 40 events per peak and 3 million per day, we are far below the FIFO throughput limits (hundreds of messages per group per second), so we will not hit saturation. Durability and retention of up to 14 days satisfy the 7-day replay requirement directly: replay is re-consuming from the queue. Because the queue is fully managed, our two engineers get ordering, durability, and retry semantics without operating brokers, topics, or consumer groups.

## Why not Kafka
Kafka would give us stronger replay through log retention, higher throughput headroom, and rich stream-processing tooling. But those benefits are unused at 40 events per second, and Kafka imposes an operations burden — cluster provisioning, partition and replication-factor planning, consumer-group coordination, and ongoing tuning — that a two-engineer team with no platform group should not absorb. It also adds infra cost and operational risk we do not need yet. We choose Kafka only if we later need many independent consumers with independent replay, complex event-time processing, or throughput an order of magnitude higher.

## Why not Postgres as a queue
Postgres is already our database, so publishing events as table rows and polling for them is cheap to start and keeps everything in one system. But a table-as-queue forces us to build, by hand, the properties SQS gives for free: reliable delivery without duplicate or lost messages, consumer-group semantics, backpressure, and dead-letter handling. Polling introduces latency and load, optimistic locking limits consumer parallelism, and deleting rows as "delivered" destroys our replay capability. Replay in Postgres means maintaining a separate append-only event log, which is essentially rebuilding Kafka ourselves. We keep Postgres for durable storage and for the replay pipeline, but we do not trust it as the delivery mechanism.

## Consequences
This decision gives us strict per-customer ordering, durability, retries, and 14-day retention with minimal operations. It introduces a vendor-managed dependency and FIFO pricing that is higher than standard SQS, though acceptable at our volume. Per-customer ordering means our message-group count grows with the number of active customers; SQS scales groups, but we must watch for per-group rate limits under bursty single-customer traffic. Because FIFO is not designed for massive fan-out, if several downstream services later need the same events, we will add per-subscriber queues behind an event bridge rather than relying on direct FIFO delivery. Replay is implemented by re-reading retained messages through a separate consumer that writes to a reprocessing store, keeping production consumers unaffected.

## What Would Change This Decision
We would revisit if daily volume grows toward millions of events per hour, if we need multiple independent consumers each with their own replay and processing cadence, if sub-second end-to-end latency becomes critical, or if a dedicated platform team appears that could operate Kafka efficiently. At that point the log-based replay and stream-processing maturity of Kafka would outweigh its operational cost, and we would migrate the transport while keeping customer-id partitioning as the ordering key.

## A2
# Design: Multi-Tenant Document Collaboration Service

## Assumptions
The following assumptions are made up front and held throughout this document:

1. The service is a cloud SaaS with a small number of large enterprise tenants (organizations), not a consumer app with billions of users.
2. "Documents" are collaborative rich-text or block-based documents up to a few hundred thousand characters; we are not collaborating on very large files or binary assets.
3. Concurrent editing is real-time: collaborators see each other's changes within a second, but the system need not survive sub-second network partitions.
4. Each authenticated user belongs to exactly one organization (tenant) at a time; a user may be invited to multiple organizations but accesses one at a time.
5. Access control is coarse-grained per organization (roles) plus fine-grained per document (owner/editor/commenter/viewer); we do not implement field- or character-level permissions.
6. Data must remain isolated at the organization level for both correctness and typical compliance expectations; we do not assume customers require their own dedicated infrastructure or a specific region unless they purchase a dedicated tier.
7. The system runs on standard managed cloud services ( relational database, cache, message bus, object storage) without custom hardware.
8. Durability is required; we must survive process crashes and routine deployments without losing committed changes.
9. The public surface is a REST API for documents and shares, consumed by web and mobile clients; real-time editing happens over WebSocket, but persistence and sharing are RESTful.
10. Offline editing is not a first-class requirement; clients re-sync on reconnect, and the last-writer-wins at the change granularity is acceptable for rare conflicts.

## Tenancy Isolation
We use a shared-database, shared-schema model with a strict `organization_id` column on every table, enforced by row-level security (RLS) in the database. Every query, including those issued by privileged application service accounts, is scoped to the current organization, and RLS rejects any statement that would read or write another organization's rows. This gives strong, centralized isolation that cannot be bypassed by an application bug that forgets to pass the tenant id. For the assumed enterprise scale, shared schema avoids the complexity and join cost of per-tenant databases while satisfying compliance through policy. Customers who later require dedicated isolation can be migrated to a per-tenant database or a dedicated schema with minimal application change, because all access still flows through the same `organization_id`-scoped service layer.

## Document Storage
The document store keeps two kinds of state. The authoritative document content is stored as an append-only, versioned log of changes: each accepted change is appended with a monotonically increasing sequence number and a reference to its parent change. The current document body is a materialized view rebuilt on demand and cached, so reads do not replay the entire history. Metadata (title, owner, timestamps, organization) lives in a relational table keyed by `document_id` and `organization_id`. Large binary attachments (if any) go to object storage with signed URLs and organization-scoped buckets, never in the database. The change log gives us durability, an audit trail, and a natural convergence point for concurrent edits.

## Concurrent Editing Model
We use operational transformation at the granularity of changes (whole edits, not individual keystrokes), because it fits our assumption that last-writer-wins at change granularity is acceptable and that we run server-authoritative. Each client sends discrete changes (insert, delete, format) to the server over WebSocket. The server applies changes in sequence-number order against the authoritative log, transforming each incoming change against concurrent changes it would conflict with, and broadcasts the resolved change to other connected clients. This preserves document validity and converges all clients to the same state. Keystroke-level CRDTs are out of scope for our size assumptions and would add client complexity; if we later require fully offline, partition-tolerant editing with seamless merge, we would move to a CRDT. The server remains the source of truth, which simplifies permissions and audit.

## Permissions
Permissions have two layers. At the organization layer, roles (admin, member, guest) control what a user can do across the tenant. At the document layer, each document has an access list mapping users to owner, editor, commenter, or viewer. Resolution is the union: a user acts only if both their organization role and their document role permit it. Writes to a document require an editor-or-owner document role; comments require commenter-or-higher; reads require viewer-or-higher; sharing a document requires owner. All checks happen in the application service layer and are re-validated against the access list on each operation, never cached trustingly across requests. Shares are first-class records with an optional token, an expiry, and a role, and can be revoked without touching the document.

## Public REST API
The API exposes documents and shares as resources under `/v1`. Documents: `GET /v1/documents` lists a document within the current organization; `POST` creates one; `GET /v1/documents/{id}` returns metadata plus a lazily-fetched body; `PATCH` applies a batch of changes as a single atomic write; `DELETE` soft-deletes within retention. Every request carries the organization context and an auth token; responses are scoped so a document id from one organization is unreachable from another. Shares: `POST /v1/documents/{id}/shares` grants a role via email or token; `GET /v1/shares/{token}` resolves a shared link to a viewable document without requiring the sharer to be present; `DELETE /v1/shares/{id}` revokes access. All endpoints return standard JSON, use versioned URLs, enforce rate limits per organization, and log an audit record for every mutating call. Real-time clients authenticate over WebSocket using the same token and are then subject to the same per-document permission checks before any change is accepted.

## H1
The premise is surprising because, normally, a set is dramatically faster than a list for membership: a list scan is O(n) comparisons, while a set lookup is expected O(1). For a set to be slower than a list on 10,000 IDs, the set's hash table is not behaving like a hash table — the realistic root cause is hash collision amplification. If the user IDs hash poorly — for example they are strings that share a long common structure, they are integers whose low bits collide, or they were generated/attacked so that many land in the same probe slots — then lookups degrade from O(1) toward O(n): every membership test computes the hash, then walks a long collision chain doing repeated equality checks. Now each test pays the cost of hashing plus a near-linear probe sequence, which is strictly worse than a list's simple sequential compare with early exit. A secondary cause can be an expensive `__hash__` (long or computed keys) that costs more than a direct string comparison, plus the set's sparse pointer table hurting cache locality versus a contiguous list.

What to switch to depends on confirming the cause, but the robust recommendation is: do not rely on hashing the raw ID for the hot membership test. If the IDs map to bounded integers, switch to a bitmap — a `bytearray` or `bitarray` indexed by an integer id — which is O(1) with no collisions and excellent cache locality, and is the fastest possible membership structure. If the IDs are not cleanly integer-indexable, switch to a sorted list of keys with binary search (`bisect`), which guarantees O(log n) with no hash-collision degradation and good locality, and rebuild it when the set of IDs changes. In parallel, fix the underlying key: index by a cheap, stable integer key (e.g., a numeric user id) instead of the expensive string, so that if you keep a set at all it hashes cheaply and evenly. My primary recommendation is a bitmap when IDs are integer-keyable (fastest, collision-free), otherwise a sorted array with binary search; and in all cases stop using the expensive raw ID as the hash key.

Design (module in `work/rate_limiter.py`):
- Token bucket per key. `RateLimiter(capacity, refill_rate, ...)`; `try_acquire(key, amount=1)` returns whether allowed. A new key starts with a full bucket; each call refills `elapsed * refill_rate` tokens (capped at capacity) and consumes `amount` if available.
- Thread-safe: a single `threading.Lock` guards the `_buckets` dict; every read/write of shared state happens inside `with self._lock`.
- Expiry/bounded memory: keys track `last_refill`; a sweep (`_maybe_cleanup_locked`) deletes keys whose `now - last_refill > ttl` (default 600 s = 10 min). The sweep runs opportunistically during normal calls every `sweep_interval` calls and whenever the table exceeds a threshold — no background threads or timers.
- Monotonic clock only: defaults to `time.monotonic`. Elapsed deltas are therefore always non-negative, so wall-clock jumps (NTP/manual changes) cannot over-refill or corrupt state; `_refill_locked` also guards `elapsed > 0`.
- Invariant (no lock during I/O or user code): the optional `refresh(key)` hook — which may perform I/O — is invoked strictly between two lock acquisitions, never while `_lock` is held. A test (`test_no_lock_during_user_code`) confirms this by having `refresh` call `try_acquire` on the same key; it returns immediately rather than deadlocking, proving the lock was released.

Why it was wrong in production: The original returns the even-total median as `(max(left_a, left_b) + min(right_a, right_b)) / 2`. In Python 3 the `/` operator performs true division, converting the integer sum to a `float` first. For the small integers in unit tests the average is exactly representable, so it passes. But production stores 64-bit record IDs: the sum of the two middle IDs exceeds 2**53 and can no longer be represented exactly, so the float result is rounded — a wrong median. The odd-total branch returns an int and is unaffected, which is why the failure is intermittent and value-dependent.

Reproduction input: `a = [2**62, 2**62 + 2]`, `b = [2**62 + 4, 2**62 + 6]`. Combined sorted is `[2^62, 2^62+2, 2^62+4, 2^62+6]`; the true median is `(2^62+2 + 2^62+4)/2 = 2^62 + 3 = 4611686018427387907`, but the function returns `4.611686018427388e+18` (a rounded float).

Fix (in `work/median_fixed.py`): keep the same binary search, but compute the even-total average with exact integer arithmetic instead of `/`. Let `total = max(left_a,left_b) + min(right_a,right_b)`; return `total // 2` when `total` is even (an exact integer median) and `Fraction(total, 2)` when it is odd (an exact half-integer median). No value is ever converted through a lossy float. Verified against a brute-force reference over 200,000 randomized cases (small ints and 64-bit record IDs) with 0 mismatches, and the reproduction input now returns the exact `4611686018427387907`.
