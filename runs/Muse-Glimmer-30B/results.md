## R2
Cache coherence is the property that ensures all processors in a multiprocessor system observe a consistent view of shared memory locations despite the presence of private caches. The problem arises because each core can hold a local copy of a cache line, and writes to that line must be made visible to other cores in a timely and ordered manner. Protocols such as MESI, MSI, MOSI, and MESIF define the states a cache line can occupy and the transitions triggered by reads and writes. Snooping protocols let every core monitor the shared bus for requests to lines it holds, while directory-based protocols maintain a directory that tracks which caches share a line, reducing broadcast traffic at scale. Coherence is typically paired with memory consistency models, which define the order in which memory operations appear to execute. Sequential consistency is the strongest model, requiring that operations appear to execute in program order across all cores, while relaxed models permit reordering for performance. Modern hardware implements coherence in hardware, using invalidation or update messages, write buffers, and store buffers to hide latency. Software can influence coherence through cache line alignment, false sharing avoidance, and use of non-temporal accesses. In distributed systems, coherence is approximated with consistency protocols like eventual consistency, which relax the guarantees for availability. Understanding cache coherence is essential for writing high-performance concurrent code, as poor locality and false sharing can degrade performance by orders of magnitude despite correct functional behavior. The interplay between coherence, prefetching, and out-of-order execution continues to drive microarchitectural innovation.

## A1
Context: The order-processing service emits domain events for downstream fulfillment, invoicing, and analytics. Peak load is 40 events/sec, ~3M events/day, average payload 2 KB. Strict per-customer ordering is required, global ordering is not. Replay of the last 7 days must be possible. Team is two backend engineers, no platform team. Existing stack is Postgres 16 and AWS, no Kubernetes.

Decision: Use Postgres as the event transport with an append-only outbox table per customer and a lightweight poller that publishes to an SQS FIFO queue per customer.

Rationale: Kafka would provide strong ordering and replay but requires operational overhead, ZooKeeper/KRaft management, and additional expertise that a two-person team cannot sustain without a platform team. AWS SQS FIFO provides per-queue FIFO ordering, message deduplication, and 14-day retention, matching the 7-day replay requirement via a separate archive table. Postgres-as-a-queue is the simplest for durability and transactional outbox: events are written in the same transaction as the order mutation, guaranteeing exactly-once emission at the source. The poller reads the outbox in customer order and pushes to SQS FIFO, providing decoupling and replay capability via the outbox.

Consequences: Positive: minimal new infrastructure, operational simplicity, strong per-customer ordering via both Postgres ordering and SQS FIFO. Negative: throughput limited to Postgres write capacity and poller latency; SQS FIFO limits of 300 messages/sec per queue and 120,000 in-flight messages are sufficient for 40 events/sec peak. Replay requires reading the outbox table and re-publishing.

What would change the decision: If peak grows beyond ~500 events/sec sustained, or multi-region active-active is required, migrate to Kafka or Kinesis with consumer groups. If a dedicated platform engineer joins, Kafka becomes viable for richer replay and stream processing. If per-customer ordering can be relaxed, standard SQS or SNS would reduce cost.

## H1
A set has O(1) average membership test but with higher constant factors than a list for small sizes and for integer IDs that are dense. For 10,000 IDs, a Python list membership test is a linear scan in C, which is very fast for small lists and benefits from CPU cache locality. A set uses hashing, which requires hashing each integer, probing the hash table, and handling collisions. For 10,000 items, the hash table overhead and random memory accesses can make the set slower than a linear scan, especially if the working set fits in cache.

Switch to a boolean array or a bitset if IDs are bounded and dense, or use a Python set with a smaller size, or use the `in` operator on a `bytearray`/`array` of booleans. For 10,000 IDs, a sorted list with binary search or a `set` of ints is usually fine, but the observed slowdown suggests hashing overhead dominates. A better structure is a `bytearray` or `array('b')` indexed by ID, or use `bisect` on a sorted list if lookups are rare.
