## R2
Modern processors cannot let every core wait on main memory for every byte it touches. Instead, each core keeps a small, fast cache of recently used memory lines, and a multicore machine therefore holds many private copies of the same data. Cache coherence is the discipline that keeps those copies consistent: whenever one core writes a byte, the other cores must eventually observe that write, and no core may keep reading a stale value forever. Without a coherence mechanism, a shared-memory machine would behave like several machines that merely happen to share an address space, and the memory model that programmers rely on would collapse.

The problem arises because caches are private. When core A reads address X, its cache stores a copy of the line containing X. When core B later writes X, core A's copy is silently wrong unless something invalidates or updates it. The classic requirements are atomicity, progress, and uniformity: a write must appear to happen at a single instant, it must complete in finite time, and all cores must agree on the order in which writes to the same address become visible. Coherence is deliberately weaker than a full memory consistency model; it governs the visibility of individual cache lines, while consistency models such as total store order or release consistency govern the ordering of operations across addresses.

The first and simplest way to enforce coherence is snooping. Every cache watches, or snoops, the address bus: when a core issues a read or write, the address is broadcast, and each cache compares it against its tags. If another cache holds the line in a dirty, modified state, it must supply the new value or relinquish it. Snooping is elegant because the protocol is distributed: each cache reacts locally to a global signal, and no central controller is involved. Its weakness is scaling. Every transaction is broadcast to every cache, so coherence traffic grows with the number of participants, and a shared bus becomes a bottleneck long before modern core counts are reached. Snoop filters, which remember which caches might hold a line, cut the broadcast to a point-to-point query, and modern point-to-point interconnects such as ring and mesh topologies implement snooping in that filtered form.

At larger scales, directory-based protocols replace the broadcast with a table. A directory entry for each line records which caches hold it and in what state, so a write only has to send invalidations to the caches that actually share the line. The directory can live in the last-level cache, in the memory controller, or in a dedicated coherence agent. This is how chip multiprocessors with dozens or hundreds of cores, and NUMA systems with many sockets, keep coherence traffic proportional to the number of sharers rather than to the number of participants. The price is extra state and complexity: the directory itself must be kept coherent, and its capacity and lookup latency become first-order design concerns.

The state machine that most protocols use is MESI. Each cache line is in one of four states. In Modified, the line is present only in this cache and has been written; it must be written back to memory before anyone else can use it. In Exclusive, the line is present only here but is clean. In Shared, several caches hold clean copies. In Invalid, the line is not usable. A read of an invalid line fetches it from memory or from the owning cache; a write to a shared line forces invalidations to every sharer, which is why MESI is a write-invalidate protocol rather than write-update. Variants such as MOESI add an Owned state so that a cache can supply a dirty line to others without writing it back to memory first, and MESIF adds a forwarding state for point-to-point interconnects. The state encodes exactly the information the protocol needs: who may hold the line, and who is responsible for its final value.

Coherence is a tax paid in hardware and bandwidth. Every cache line carries state bits, every access may trigger snoop comparisons, and a single write to a heavily shared line can fan out invalidations to many cores. The tax is usually worth it, because the alternative, fetching from main memory on every access, is far worse. But it shapes software: false sharing, where two threads write to different variables that happen to sit in the same cache line, turns independent work into a coherence storm, and padding or aligning hot structures is a standard remedy. Likewise, the cache line, not the byte, is the unit of movement between levels, which is why 64-byte lines dominate and why access patterns matter as much as raw bandwidth.

The frontier of coherence is moving beyond the chip. NUMA machines already force designers to weigh the cost of a remote cache line against local bandwidth, and interconnects such as CXL extend coherent memory across packages, boards, and even into the data center, where the directory must track sharers that are milliseconds rather than nanoseconds away. Heterogeneous accelerators, GPUs included, are joining the coherent domain, and their many cores make the directory's bookkeeping a serious memory subsystem of its own. Each of these extensions keeps the same core idea, a small set of states and a disciplined protocol over them, but pushes the state machines, the interconnects, and the memory models further from the simple picture that a single chip could once hold in its entirety.

## A1
**Status:** Accepted
**Deciders:** Backend team (2 engineers)

### Context

A new order-processing service must publish order lifecycle events (created, paid, shipped, cancelled) to downstream consumers. The hard requirements are:

- Peak 40 events/sec; about 3M events/day; average payload 2 KB (roughly 6 GB/day, 42 GB/week).
- Strict per-customer ordering; global ordering not required.
- The last 7 days of events must be replayable for reprocessing.
- Two backend engineers, no platform team.
- Existing infrastructure: Postgres 16 on AWS; no Kubernetes.

### Options considered

**1. Kafka (self-managed or Amazon MSK).** Partition by customer ID to get per-customer ordering; 7-day retention is one configuration knob; replay is a first-class operation (reset consumer offsets). At 40 events/sec we would use a small fraction of a broker's capacity, so performance is not the argument — operations are. Even on MSK we own consumer groups, offset management, schema evolution, monitoring, and capacity planning. Kafka's real value (very high throughput, many independent replay positions, stream processing) is not needed at this scale, and two engineers would be running a distributed system they do not yet need.

**2. AWS SQS FIFO.** FIFO queues order messages within a Message Group; setting the group ID to the customer ID gives exactly the per-customer ordering we need, and 3,000 msg/sec with batching is far above our peak. The fatal issue is the replay requirement: SQS is a queue, not a log. A message is deleted once received, so "replay the last 7 days" is not expressible — consumed events are gone. Meeting the requirement would force us to persist every event to a second store before or after publishing, at which point that store is doing the log's job and SQS is a redundant hop. FIFO also adds a 5-minute deduplication window and per-queue throughput subtleties.

**3. Postgres as a queue.** Append events to a table in the same transaction that changes the business state (transactional outbox). Consumers claim rows with `SELECT ... FOR UPDATE SKIP LOCKED`, process per customer in sequence order, and mark rows processed. Replay is trivial: the rows are still there; a reprocessing job re-reads them. 7-day retention is a day-partitioned table plus a cleanup job. At 40 rows/sec of 2 KB rows, Postgres 16 has a large margin, and every part of the design — schema, transactions, monitoring, backup — is already in the team's skill set.

### Decision

Use **Postgres as the event queue**, implemented as a transactional outbox:

- `events(id bigserial, customer_id, type, payload jsonb, created_at, processed_at)`, partitioned by day.
- Producers insert the event row in the same transaction as the order state change: no dual-write, no lost events.
- Consumers claim batches with `FOR UPDATE SKIP LOCKED` and process one customer at a time in `id` order, setting `processed_at` in a transaction.
- Each consumer records progress in a `consumer_cursors` table, giving independent replay positions per consumer.
- A nightly job drops partitions older than 7 days after confirming no replay is in progress.

### Consequences

Positive: no new infrastructure; event publication is atomic with the business write; replay is a query, not a protocol; two engineers can operate it with existing tooling and skills.

Negative: Postgres is now on the hot path for event delivery, so we must monitor polling lag and connection-pool usage; consumer scale-out is bounded by the database (fine at this scale, a ceiling later); we give up a managed broker's ecosystem (schema registry, offset tooling). We accept coupling event delivery to Postgres availability in exchange for eliminating an entire class of distributed-systems failure.

### What would change the decision

- Sustained throughput above roughly 1,000 events/sec, many independent consumer types needing their own replay positions, or a need for stream processing (joins, windows) → Kafka (MSK).
- Postgres becoming a bottleneck for the primary workload, or the team growing with a platform function → revisit managed brokers.
- A hard requirement that producers never be blocked by queue availability (separate durability domains) → put SQS in front of the outbox, with Postgres remaining the system of record for replay.

## A2
### Assumptions

1. The service is a SaaS product. A tenant is an organization; each user belongs to exactly one organization.
2. Documents are text-centric (prose, tables, comments) and at most about 100,000 characters; binary attachments are out of scope for v1.
3. Concurrency target: up to 50 simultaneous editors per document, at human editing speed (a few operations per second per editor).
4. Collaborators expect near-real-time visibility of each other's edits (sub-second), not just eventual synchronization.
5. v1 is online-only; offline editing and offline merge are deferred.
6. Authentication (sign-in) already exists via OIDC; this design covers authorization only.
7. v1 deploys in a single region; the design must not prevent a later multi-region deployment.
8. The primary datastore is Postgres 16.

### Tenancy isolation

Shared schema, shared Postgres, with `tenant_id` on every tenant-scoped table, enforced at three layers:

1. **Application layer.** A tenant context is established at the edge from the authenticated principal and propagated to every repository call; no repository method accepts a document ID without a tenant ID.
2. **Database layer.** Postgres row-level security (RLS) policies on every tenant-scoped table (`WHERE tenant_id = current_setting('app.tenant_id')::uuid`), with the session variable set per connection from the pool middleware. RLS is a backstop, not the primary control: it guards against bugs, not against a compromised application, and it has a measurable (single-digit percent) query cost, so every tenant-scoped table is indexed with `tenant_id` first.
3. **Operational layer.** Backups, exports, and support tooling are tenant-scoped; cross-tenant queries require an explicit, audited support-mode role.

We reject per-tenant databases (operational cost at our tenant count) and per-tenant schemas (migration fan-out) for v1. The schema is designed so a tenant can be extracted to its own database later: no cross-tenant foreign keys, and every query is tenant-scoped.

Encryption at rest uses KMS envelope encryption with per-tenant data keys: document content and CRDT state are encrypted with tenant-specific keys before they reach Postgres, so a database-level leak does not expose plaintext across tenants. The application holds the keys only for the duration of a request, and key rotation is a per-tenant operation that re-encrypts lazily on write. We do not use per-tenant database credentials in v1.

### Document storage

- `documents`: `id (uuid)`, `tenant_id`, `title`, `owner_id`, `created_at`, `updated_at`, `etag`.
- `doc_states`: `doc_id`, `version (int)`, `yjs_state (bytea)` — the CRDT's complete state at a snapshot version — plus `plain_text (text)` materialized from it for search, preview, and export.
- `doc_updates`: `doc_id`, `seq (int)`, `origin (uuid)`, `delta (bytea)` — the append-only stream of incremental CRDT updates; this is the collaboration log.
- Periodic snapshots: every N updates or every hour, a full state is persisted and the update stream is garbage-collected before it, so catch-up cost is bounded.

The CRDT state is the source of truth for content; the plain-text rendering is a cache. Search indexes the rendered text (Postgres full-text search for v1).

Storage sizing: a 100,000-character document has a CRDT state of roughly 1–3 MB after the GC horizon, and the update stream grows a few kilobytes per editing session. The snapshot-plus-GC scheme keeps per-document storage bounded by the snapshot interval rather than by document age. Large documents are the exception we optimize for, not the rule: the default document is a few kilobytes, and the read path (a single `doc_states` row plus the rendered text) stays a one-row fetch regardless of history length.

### Concurrent editing model

We use a CRDT (Yjs-compatible) rather than operational transformation:

- **Why CRDT.** Convergence is guaranteed by construction, no central transformation server is needed, and the same library runs in the browser and on the server, so client and server share one correctness argument. OT would give lower bandwidth at large edit rates, but at human speed with at most 50 editors the CRDT overhead is negligible, and the operational burden of an OT server (ordering, transformation, version vectors) is not worth it.
- **Live sync.** A WebSocket per document room. The server is a stateless relay: it forwards updates to the other participants and appends them to `doc_updates`. It does not interpret content.
- **Catch-up.** On connect, the client sends its state vector; the server computes the missing updates (from `doc_updates`, or from the nearest snapshot plus subsequent updates) and sends the diff.
- **Persistence.** The server persists updates in batches (every roughly 200 ms or 50 updates) in one transaction per document, so a crash loses at most a few hundred milliseconds of edits; the `etag` on `documents` is bumped per batch.
- **Metadata** (title, etc.) is not in the CRDT: it updates via REST with `If-Match` optimistic concurrency (412 on conflict).
- **Presence and cursors** are ephemeral: they ride the same WebSocket as transient messages, are never persisted, and expire when a participant disconnects. This keeps the collaboration log clean of chatty, non-authoritative data.
- **Failure behavior.** If the server drops a batch, the client's next state-vector exchange re-sends the missing updates, so a transient outage degrades to a brief pause rather than data loss. Clients retry with exponential backoff and reconnect with their full state vector, which is why the state vector (not a cursor) is the unit of catch-up.

### Permissions

- Roles per document: `owner` (one), `editor`, `commenter`, `viewer`. The document owner and organization admins have owner rights on all organization documents.
- `shares`: `doc_id`, `grantee_type (user|org)`, `grantee_id`, `role`, `granted_by`, `expires_at`. A share with `grantee_type = org` grants the role to every member of the organization (the default for internal documents).
- Public links: a `share_token` row (256-bit random) with `role`, `expires_at`, and an optional password hash. Tokens are revocable and never derived from the document ID.
- Enforcement: a single `check_access(doc_id, principal, needed_role)` call at the API edge for every document operation; WebSocket room admission uses the same check (commenter or above to join the live room; viewer to receive read-only presence).
- Every grant, revoke, and public-link access is written to an append-only `audit_log`.

### Public REST API

Base path `/api/v1`. All requests are authenticated with a bearer token; the tenant is derived from the principal. Errors use RFC 7807 problem+json. Pagination is cursor-based everywhere, with `limit` capped at 100. Idempotency keys are stored for 24 hours.

Documents:

- `GET /documents?cursor=&limit=` — list documents the principal can access, ordered by `updated_at` descending; returns `items[]` plus `next_cursor`.
- `POST /documents {title}` — create; returns 201 with the document; honors an `Idempotency-Key` header.
- `GET /documents/{id}` — metadata plus rendered text (`?fields=meta` for metadata only).
- `PATCH /documents/{id} {title?}` — with `If-Match: <etag>`; 412 on mismatch.
- `DELETE /documents/{id}` — owner only; soft delete with 30-day retention.
- `GET /documents/{id}/versions` and `GET /documents/{id}/versions/{version}` — list and fetch snapshots (viewer or above).
- `GET /documents/{id}/export?format=md|html|txt` — rendered export.
- `POST /documents/{id}/sync` — batched CRDT updates over HTTP for clients that cannot hold a WebSocket; `WS /documents/{id}/live` for the live room.

Shares:

- `GET /documents/{id}/shares` — list shares (owner).
- `PUT /documents/{id}/shares/{grantee_type}/{grantee_id} {role, expires_at?}` — create or update a share; owner only.
- `DELETE /documents/{id}/shares/{grantee_type}/{grantee_id}` — revoke.
- `POST /documents/{id}/public-link {role, expires_at?, password?}` — create a public link; returns the token exactly once.
- `DELETE /documents/{id}/public-link/{token}` — revoke.
- `GET /share/{token}` — unauthenticated; validates token, expiry, and password; returns the rendered read-only document (no metadata beyond the title).

Rate limiting is per principal (100 req/s) and per document room (100 updates/s).

Cross-cutting conventions: every list response carries `next_cursor` (null at the end) and all timestamps are RFC 3339 UTC. Writes are idempotent where an `Idempotency-Key` is supplied; replays within the 24-hour window return the original response body and status. The live WebSocket authenticates with a short-lived room token minted by `POST /documents/{id}/live-ticket`, so the socket handshake never carries the principal's bearer token. All errors are problem+json with a stable `type` URI that clients can branch on; 409 is reserved for share conflicts (two admins setting different roles on the same grantee in the same second), 410 for expired public links, and 423 for documents under a compliance hold.

## A3
The proposal has the right instincts (event-driven, decoupled, fan-out ready), but three load-bearing problems.

**1. The dual write is not atomic.** "Each payment writes to the payments table, then publishes PaymentCreated to SNS" is a two-system commit. If the process crashes between the commit and the publish, the payment exists but the event never fires — the ledger silently misses it, and no retry mechanism can find it, because nothing records that the publish was attempted. Fix: a transactional outbox. Insert the payment row and an outbox row in one Postgres transaction; a relay (polling, or logical decoding) publishes the outbox rows and marks them sent. The event is then produced if and only if the payment committed.

**2. The ledger must not depend on a DLQ for correctness.** A DLQ is a failure sink, not a retry path: messages land there only after repeated failed receives, and recovery is manual and slow. For a double-entry ledger, "the ledger write failed, we'll retry from the DLQ later" means the books are wrong in the meantime with no defined bound on how long. The ledger consumer needs: (a) idempotent application keyed on the payment ID — redelivery is guaranteed to happen, because SNS and SQS are at-least-once; (b) bounded automatic retry with exponential backoff before anything touches the DLQ; and (c) a reconciliation job that periodically compares payments to ledger entries and alerts on any gap, so a missed event is detected even if every retry mechanism fails.

**3. Failure semantics are unspecified.** If one payment's ledger write persistently fails, does it block later payments? Payments are independent, so the answer should be no — but that must be explicit: the consumer must be able to skip a poison message to the DLQ without stalling the queue. If per-payment ordering ever matters (a payment and its reversal), that is an argument for SQS FIFO with the payment ID as the message group, not for SNS fan-out.

What I would keep:

- SNS for fan-out is defensible: multiple future subscribers is a real requirement. But each subscriber should be an SQS queue (SNS-to-SQS per subscriber is the standard pattern); never subscribe a service endpoint directly to SNS.
- Publishing the event after the commit, not before, is the right direction; the outbox just makes it atomic.

Additional details I would add:

- Version the event schema (`PaymentCreated.v1`) and include an `event_id` (UUID, for idempotency) and `occurred_at`.
- DLQs with a small `maxReceiveCount` (around 5), alarms on DLQ depth, and an automated reprocessing tool.
- Monitoring: outbox lag (commit-to-publish time), consumer lag, DLQ depth, reconciliation mismatches.
- If the ledger is truly on the critical path — the payment must not be considered complete until it is booked — the simplest design that preserves the invariant is to write the ledger rows in the same transaction as the payment row (same database, two tables) and keep the event purely informational.

The premise is false, so I cannot explain it as stated: for membership tests on about 10,000 items, a set is not slower than a list — it is dramatically faster. `x in some_list` is an O(n) linear scan, roughly 10,000 equality comparisons per check in the worst case (about 5,000 on average). `x in some_set` is O(1) on average: one hash, one bucket probe, one equality. Switching 10,000 IDs from a list to a set should have made the hot path hundreds of times faster, not slower.

So the observed slowdown is real, but its cause is elsewhere. The usual suspects, in order of likelihood:

1. **The set is being rebuilt on every check.** If the code does `if uid in {row.uid for row in fetch_all_users()}` — or builds the set per request, per call, or inside an outer loop — the O(n) construction cost dominates, and you have simply added work. The list version may have been built once and cached.
2. **The elements are not what you think.** If the IDs are wrapped in objects with an expensive or pathological `__hash__` (hashing a large payload, or a custom class computing the hash from mutable state), the set's "O(1)" is really O(size of the hash input). A list of the same objects pays equality costs only on collisions.
3. **You are measuring different things.** The list may have been interned or cached, the set allocated per call, or the benchmark included construction time.

What to do:

- **Keep the set.** It is the correct structure for membership tests at this scale. If it is immutable after construction, use a `frozenset` (marginally faster, and it signals intent).
- **Build it once** (at startup, or in a cache with an invalidation hook) and reuse it; never build it inside a hot loop.
- **If the IDs are dense integers in a known range** (say, below 10^7), a `bytearray` or bitarray indexed by ID is even faster and smaller: `seen[uid] = 1` — O(1) with no hashing at all.
- **Profile before changing anything else.** `python -m cprofile -s cumulative` or py-spy on the slow path will show whether the time is in the membership test, in set construction, or in hashing. If the profile shows the set lookup itself is slow, the element type is the problem, and the fix is to store plain `int`/`str` IDs in the set rather than wrappers.

Bottom line: the data structure is correct; the usage is what to investigate. A set of 10,000 plain IDs is about as fast as membership testing gets in Python.

```python
"""Thread-safe per-key token-bucket rate limiter.

Properties
----------
- Per-key token bucket with configurable ``capacity`` and refill ``rate``
  (tokens per second).
- Thread-safe: all shared state is guarded by a single ``threading.Lock``.
- Keys expire after ``expiry`` seconds (default 10 minutes) of inactivity.
  Expired buckets are removed lazily during normal calls; there are no
  background threads or timers.
- Time is read from a monotonic clock (``time.monotonic`` by default, or an
  injected stand-in for tests), so wall-clock changes cannot break it.
- Invariant: no operation holds the lock while performing I/O or calling
  user-supplied code. The clock is read *before* the lock is acquired, and
  the only work done under the lock is arithmetic on in-memory state.
"""

from __future__ import annotations

import threading
import time
from typing import Callable

DEFAULT_EXPIRY_SECONDS = 600.0  # 10 minutes


class _Bucket:
    __slots__ = ("tokens", "last_refill", "last_used")

    def __init__(self, capacity: float, now: float) -> None:
        self.tokens = capacity
        self.last_refill = now
        self.last_used = now


class RateLimiter:
    def __init__(
        self,
        capacity: float,
        rate: float,
        *,
        expiry: float = DEFAULT_EXPIRY_SECONDS,
        clock: Callable[[], float] = time.monotonic,
    ) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be > 0")
        if rate < 0:
            raise ValueError("rate must be >= 0")
        if expiry <= 0:
            raise ValueError("expiry must be > 0")
        self._capacity = float(capacity)
        self._rate = float(rate)
        self._expiry = float(expiry)
        self._clock = clock
        self._lock = threading.Lock()
        self._buckets: dict[str, _Bucket] = {}

    def allow(self, key: str, tokens: float = 1.0) -> bool:
        """Try to consume ``tokens`` from ``key``'s bucket.

        Returns True if the request is allowed, False if it is rate-limited.
        A request for more tokens than the bucket capacity is always denied.
        """
        if tokens <= 0:
            return True
        if tokens > self._capacity:
            return False
        now = self._clock()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._buckets.get(key)
            if bucket is None:
                bucket = _Bucket(self._capacity, now)
                self._buckets[key] = bucket
            self._refill_locked(bucket, now)
            bucket.last_used = now
            if bucket.tokens >= tokens:
                bucket.tokens -= tokens
                return True
            return False

    def remaining(self, key: str) -> float:
        """Tokens currently available for ``key`` (does not consume any)."""
        now = self._clock()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._buckets.get(key)
            if bucket is None:
                return self._capacity
            self._refill_locked(bucket, now)
            bucket.last_used = now
            return bucket.tokens

    def active_keys(self) -> int:
        """Number of buckets not yet expired (sweeps first)."""
        now = self._clock()
        with self._lock:
            self._sweep_locked(now)
            return len(self._buckets)

    # -- internals; caller must hold ``_lock`` --------------------------

    def _refill_locked(self, bucket: _Bucket, now: float) -> None:
        elapsed = now - bucket.last_refill
        if elapsed > 0 and self._rate > 0:
            bucket.tokens = min(self._capacity, bucket.tokens + self._rate * elapsed)
            bucket.last_refill = now

    def _sweep_locked(self, now: float) -> None:
        if not self._buckets:
            return
        expired = [
            key
            for key, bucket in self._buckets.items()
            if now - bucket.last_used >= self._expiry
        ]
        for key in expired:
            del self._buckets[key]
```

        rl = RateLimiter(capacity=10, rate=50.0, clock=time.monotonic)

Design notes against the requirements: per-key buckets with configurable capacity and refill rate (`RateLimiter(capacity, rate)`); a single `threading.Lock` guards the bucket map and every bucket field; keys expire after 10 minutes of inactivity (`last_used` is refreshed on every operation for that key) and are swept lazily inside `allow`/`remaining`/`active_keys` — no background threads or timers; all timing uses an injectable monotonic clock (default `time.monotonic`), and a backwards clock jump is clamped so it can only delay a refill, never create tokens; the lock is never held while doing I/O or calling user code — the clock is read before the lock is taken, and only in-memory arithmetic happens under it.

**Why it fails in production but not in unit tests.** Python integers have arbitrary precision, so the binary partition search and every comparison in the function are exact even for 64-bit record IDs. The only place a float enters is the final even-length step: `(max(left_a, left_b) + min(right_a, right_b)) / 2`. The sum of two 64-bit IDs can be as large as about 1.8e19, far beyond the 2^53 exact-integer range of a float64, and `/` converts to float64, rounding to the nearest representable value (the spacing near 2^64 is 2048). So the median comes back rounded: for the repro input `a = [9223372036854775806]`, `b = [9223372036854775807]` (i.e. 2^63−2 and 2^63−1) the exact median is 9223372036854775806.5, but the function returns 9.223372036854776e+18 = 9223372036854775808.0 — off by 1.5. The unit tests used small integers whose sums stay below 2^53, where the float conversion is exact, which is why they passed. Odd-length inputs never hit the bug (they return the integer `max(left_a, left_b)` directly).

**Fixed function** (same O(log n) partition search; the final combination is done in exact integer arithmetic — an `int` when the median is integral, an exact `Fraction` otherwise; no float is ever formed from the data values):

```python
from fractions import Fraction


def median_of_sorted_arrays(a, b):
    if len(a) > len(b):
        a, b = b, a
    n = len(a) + len(b)
    if n == 0:
        return None
    lo, hi = 0, len(a)
    while lo <= hi:
        i = (lo + hi) // 2
        j = (n + 1) // 2 - i
        left_a  = a[i-1] if i > 0 else float('-inf')
        right_a = a[i]   if i < len(a) else float('inf')
        left_b  = b[j-1] if j > 0 else float('-inf')
        right_b = b[j]   if j < len(b) else float('inf')
        if left_a <= right_b and left_b <= right_a:
            if n % 2:
                return max(left_a, left_b)
            x, y = max(left_a, left_b), min(right_a, right_b)
            s = x + y
            if s % 2 == 0:
                return s // 2
            return Fraction(s, 2)
        elif left_a > right_b:
            hi = i - 1
        else:
            lo = i + 1
```

For even total length, `max(left_a, left_b)` and `min(right_a, right_b)` are always real array elements (the left partition holds exactly n/2 elements, so at least one of the two left sentinels is a real value, and symmetrically for the right), so `s` is an `int` and the parity test is safe. Verification: 19,879 randomized trials with 64-bit-magnitude values (each array length 0–12, combined length 1–24) all match an exact `Fraction`-based brute force, plus small-value regression cases that mirror the original unit tests. If the API contract must stay `float`, the exact value should be converted only at the boundary and the precision limit documented; returning `int`/`Fraction` is the correct fix.

    out = []

**Verdict: correct.** For all inputs satisfying the stated precondition (a and b sorted), `merge_sorted(a, b) == sorted(a + b)`. Proof sketch: loop invariant — after each iteration, `out` is the sorted merge of `a[:i]` and `b[:j]`, and every element of `a[i:]` and `b[j:]` is >= every element of `out`. Base case i = j = 0 holds vacuously. Step: if `a[i] <= b[j]`, then `a[i]` is <= `b[j]` and (by sortedness) <= every later element of `b`, and <= every later element of `a`, so appending it keeps `out` sorted and preserves the invariant; the `b[j]` branch is symmetric. When the loop ends, one list is exhausted; by the invariant the remaining tail of the other is sorted and >= everything already appended, so the two `extend` calls complete a fully sorted merge containing every element exactly once. The `<=` comparison also makes the merge stable (equal keys from `a` precede equal keys from `b`), which the 5,000-tagged stability trials confirm. Empirically: 10 edge cases (empty lists, single elements, all-equal, interleaved, negatives), 20,000 randomized trials with heavy duplication, and 5,000 stability trials all pass. The only caveat is the precondition: for unsorted inputs the function is unspecified (e.g. `merge_sorted([2, 1], [])` returns `[2, 1]`), which is consistent with its name and contract.
