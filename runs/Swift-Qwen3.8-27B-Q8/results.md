## R2
Cache coherence is the discipline of keeping the multiple copies of a memory location that exist in a modern computer consistent with one another, so that a read always observes the most recent write in the program's memory order. Every core in a multicore machine has its own private caches — L1, L2, and often a shared L3 — and a single variable may live in a dozen of them at once. Coherence is what makes the illusion of a single shared memory work.

The problem is easy to state. Core 0 writes x = 1; core 1 later reads x. If core 1's cache still holds the old value, the read is wrong. The cache coherence problem is to guarantee that such a read cannot happen under any interleaving, without forcing every core to fetch from main memory on every access, which would destroy the performance benefit of caching in the first place.

The classical solution is a coherence protocol, and the family of protocols in widespread use is the MESI family. Each cache line — the unit of coherence, typically 64 bytes — carries a state: Modified, Exclusive, Shared, or Invalid. A line in Shared state exists in several caches and matches memory. A line in Exclusive state is in exactly one cache and matches memory. A line in Modified state is in exactly one cache, differs from memory, and its owner owes the system a writeback. A line in Invalid state is simply absent. Transitions between states are triggered by snoops: when a core wants a line, it broadcasts a request on the coherence interconnect, and every other cache that holds the line responds.

Two operations drive the protocol. On a read miss, a core issues a read-shared request. If any cache holds the line in Modified state, that cache must supply the current data and downgrade to Shared; the requester enters Shared. If no one holds it, the requester may enter Exclusive, a state that saves the write traffic of a later store. On a write, a core must first obtain exclusive ownership: it issues a read-owning request, and every other cache that holds a copy — in any state — must invalidate its line. Only then may the writer mark its copy Modified. The invariant that makes this correct is simple: at most one cache may hold a line in Modified state, and a line can be written only after every other copy has been invalidated.

How the protocol observes traffic is the second major design axis. Snooping protocols, the traditional approach, have every cache watch the bus: the broadcast is seen by all, and responses are immediate. Snooping scales well to a handful of cores on a chip, but the broadcast does not scale to many sockets. Directory protocols replace the broadcast with a home node that keeps a directory — a record of which caches hold each line — so messages go only to the relevant parties. Directory-based protocols are what large NUMA machines and chiplet-based processors use.

Coherence is not the same as consistency, and the distinction matters. Coherence is a hardware property: it orders the actions on a single address. Consistency is a memory-model property: it orders accesses across addresses, and that is where the software-visible subtleties live. A coherent machine can still return a result that looks surprising to a programmer, because the hardware is free to reorder independent accesses, to buffer stores in a store buffer, and to make them visible in an order different from program order. The memory model — x86-TSO, ARMv8, RISC-V — defines which reorderings are legal, and the programmer uses fences and atomics to control them. Coherence protocols are the mechanism; the memory model is the contract.

The cost of coherence is real. Every coherence transaction consumes interconnect bandwidth, and the protocol's latency — the round trip of a snoop and a response — is often longer than the access it protects. Modern architectures therefore layer optimizations on top: write-combining, non-temporal stores that bypass the cache hierarchy for streaming data, and the avoidance of cache-line ping-pong by padding shared counters to defeat false sharing. Conversely, the protocol is exploited: the x86 lock prefix generates coherence transactions that can be used to build atomic operations, spinlocks, and the test-and-set instruction that underlies every lock implementation.

The trend in the last decade has been to push coherence outward. Chiplet designs — a CPU die plus I/O dies, or multiple core complexes in one socket — require the coherence directory to span die-to-die links, and the protocol's latency now includes a physical hop. CXL, the cache-coherent interconnect for accelerators and memory pools, extends MESI-style coherence across a PCIe-class link, letting an accelerator hold cache lines of a CPU's memory. As coherence domains grow from one die to a rack, the engineering question shifts from whether we can keep the protocol correct to whether we can keep its latency and bandwidth cost affordable.

In the end, cache coherence is one of the quiet triumphs of computer architecture: a distributed-systems problem — replicated state, invalidation, single-writer agreement — solved in nanoseconds, in hardware, billions of times per second, invisibly. The programmer who writes x = 1 never sees the snoop storm it may cause, and that invisibility is the point. It is also a standing reminder that shared memory is an illusion maintained by protocol, and that every abstraction in the stack, from the cache line to the kernel lock, is paying for it.

## A1
### ADR: Event Transport for the Order-Processing Service

**Status:** Accepted
**Date:** 2025-06-02
**Deciders:** Backend team (2 engineers)

### Context

A new order-processing service must publish domain events (order created, payment captured, fulfillment state changes) for downstream consumers: billing, notifications, and analytics. The requirements are:

- Peak 40 events/sec, roughly 3M events/day, average payload 2 KB (about 6 GB/day of raw data).
- Strict per-customer ordering; global ordering is not required.
- The last 7 days of events must be replayable for reprocessing.
- Two backend engineers, no dedicated platform team.
- Existing infrastructure: Postgres 16 and AWS; no Kubernetes.

### Options considered

**Kafka (Amazon MSK).** Kafka fits the throughput trivially and gives per-customer ordering by partitioning on customer ID, plus 7-day replay via log retention. The costs are operational: MSK is a managed service, but it is still a second distributed system to operate — broker tuning, client versioning, partition reassignment, consumer-group monitoring, and a new failure mode the team has no experience with. Two engineers who already own the service and Postgres would be spread across two platforms, and the replay semantics (consumer offsets, log compaction interaction) are a real learning tax.

**AWS SQS FIFO.** FIFO queues give strict per-message-group ordering (group ID = customer ID), which matches the ordering requirement exactly, and 40 msg/sec is well within the 300 msg/sec sustained default. The fatal gap is replay: a consumed message is gone. SQS retention (up to 14 days) keeps messages only until they are consumed, so 7-day replay would require persisting every event to S3 on publish and rebuilding from that archive — at which point S3 plus a small index is doing the job the queue was supposed to do, with more moving parts.

**Postgres-as-a-queue.** Events are written to an `events` table in the same database the service already uses, with a monotonically increasing sequence per customer. Consumers poll with `SELECT ... WHERE customer_id = $1 AND seq > $2 FOR UPDATE SKIP LOCKED` (or a global outbox table with a `consumed_at` column and `SKIP LOCKED` claim rows). 40 rows/sec of inserts and a few hundred polls/sec is a rounding error for Postgres 16. Per-customer ordering falls out of the per-customer sequence; replay is a plain `SELECT` over a 7-day window; retention is a `DELETE`/partition-drop policy.

### Decision

Use Postgres-as-a-queue: an append-only `events` table (partitioned by day) plus a per-consumer `events_consumed` cursor table, with `SKIP LOCKED`-based claiming and day-partition drops after 7 days.

### Consequences

- No new infrastructure: no brokers, no new IAM surface, no new on-call runbook. The team's existing Postgres expertise and monitoring apply directly.
- Ordering is per-customer by construction (sequence per customer); there is no global order, which the requirements do not need.
- Replay is a query: reprocessing a customer's last 7 days is `SELECT ... ORDER BY seq`, and backfills are testable in staging against real data.
- The database becomes the queue's durability point: a Postgres outage stops eventing. Acceptable at this scale, and it is a failure we already page for.
- Throughput headroom is generous (Postgres handles tens of thousands of small inserts/sec), but this design should be revisited before event volume grows an order of magnitude or consumers need to scale to many independent instances.
- 7-day retention of 6 GB/day is about 42 GB of partitions — cheap, and day-partition drops make cleanup O(1).

### What would change the decision

- Sustained throughput above ~1,000 events/sec, or many independently scaling consumer groups: move to Kafka (MSK) or SQS FIFO with an S3 event log for replay.
- A hard requirement for global ordering: Kafka with a single partition, or a redesign.
- Consumers in other AWS accounts or other clouds needing direct queue access: SQS/Kafka's access model beats database grants.
- The team adopting Kubernetes and a platform team: the operational argument for Postgres weakens and Kafka becomes more attractive.

## A2
### Design: Multi-Tenant Document Collaboration Service

**Assumptions**

1. The product is SaaS; a tenant is an organisation, and each user belongs to exactly one tenant.
2. Documents are block-based rich text (paragraphs, headings, lists, tables, embeds), capped at 1 MB of content.
3. Collaboration is primarily online (real-time co-editing over a persistent connection), with offline edits that merge on reconnect.
4. Storage is a single Postgres cluster for metadata and block content, plus S3 for binary assets (images, files).
5. Target scale: 10k tenants, 1M documents, up to 50 concurrent editors per document.
6. REST is the system-of-record API; real-time sync is a separate WebSocket channel that enforces the same permissions.
7. Permissions are per-document roles (owner, editor, commenter, viewer) plus tenant admin; no paragraph-level ACLs.
8. History is a linear version log with restore; no branching.
9. All IDs are ULIDs; all timestamps are UTC.

### Tenancy isolation

Shared-database, shared-schema tenancy with a `tenant_id` column on every tenant-scoped table, enforced by Postgres row-level security (RLS) policies. The application sets `app.current_tenant` per connection (via `SET LOCAL` in each transaction), and RLS policies on `documents`, `blocks`, `shares`, and `members` restrict rows to the current tenant. RLS is a backstop, not the primary control: every query is also explicitly filtered by `tenant_id`, so a missing `SET LOCAL` degrades to "no rows" rather than a cross-tenant leak. Tenant admin operations run in a separate role that bypasses RLS by design and is audited. This gives per-tenant logical isolation at SaaS cost; if a customer later requires physical isolation, the schema supports moving a tenant to a dedicated database because no cross-tenant joins exist.

Background jobs (compaction, retention, fan-out) are tenant-scoped the same way: the job queue stores `tenant_id` per job and workers set the tenant GUC for the job's duration, so a misrouted job cannot touch another tenant's rows. Tenant lifecycle (suspension, export, deletion) is a state transition on the `tenants` table; a suspended tenant is hidden from the product API, and deletion is two-phase with a 30-day grace period.

### Document storage

A `documents` table holds `id`, `tenant_id`, `title`, `owner_id`, `created_at`, `updated_at`, `deleted_at` (soft delete), and `content_revision` (the CRDT state vector, see below). Content lives in `blocks`: one row per block with `document_id`, `block_id` (stable per-block ULID), `index` (fractional index for cheap insert positioning), `type`, `content` (JSONB), and `deleted`. Blocks are the unit of persistence for both REST reads and CRDT encoding. Binary assets go to S3 under `tenants/{tenant_id}/assets/{asset_id}`; a `assets` table records metadata and a signed-URL policy. Reads are served from Postgres with a read-through cache keyed on `(document_id, content_revision)`; writes invalidate by revision. At 1 MB per document and 1M documents, content fits comfortably in a single Postgres cluster with partitioning by `created_at` if needed.

Search and listing are indexed deliberately: `documents` carries a GIN index on a `tsvector` generated from title plus a denormalised text summary, and `blocks` is indexed by `(document_id, index)` for ordered reads and by `(document_id, deleted)` for active-block scans. Because `blocks` grows with editing churn, deleted blocks are purged by a nightly compaction job that rewrites the per-document block set, keeping table bloat bounded without blocking writers.

### Concurrent editing model

The editing model is CRDT-based (Yjs-compatible), chosen over OT because CRDTs merge commutatively and support offline edits without a central transform server. Each editor keeps a local CRDT document; the server is a relay and a persistence point, not an authority on ordering. The WebSocket protocol exchanges CRDT update messages (binary deltas); the server appends updates to a per-document update log and periodically compacts the log into a new `content_revision` snapshot in `blocks`. On reconnect, a client sends its state vector and the server replies with the minimal set of updates it lacks. Conflict resolution is by construction: CRDT merges are commutative, idempotent, and associative, so two offline edits to the same paragraph both survive. The REST API exposes the same state as a snapshot: `GET /documents/{id}` returns the current compiled content plus the state vector, so REST clients can rejoin the CRDT. Version history is the update log itself; restore creates a new snapshot from an earlier state vector.

Failure handling is designed around the relay role. If the server drops a client, the client's local CRDT is authoritative for its own edits; on reconnect it resends pending updates, which the server applies idempotently (updates carry deterministic IDs, so redelivery is harmless). The server bounds the per-document update queue and sheds the oldest unacknowledged remote updates when a client falls behind a configurable threshold, telling that client to do a full re-sync. Offline duration is bounded by the update-log retention window (30 days): a client returning after compaction receives a full snapshot instead of a delta.

### Permissions

Roles per document: `owner` (full control, including share management and deletion), `editor` (edit content), `commenter` (comment, no content edit), `viewer` (read). A document's creator is its owner; ownership transfers within the tenant. Tenant admins can view and manage all documents in their tenant. Access is stored in `document_access(document_id, principal_type, principal_id, role)` where principal is a user or a group; shares to external users (assumption 1 allows external collaborators via explicit share) are stored in `shares` with an expiry and a permission level. Every API and WebSocket operation resolves the caller's effective role (direct grant, group, tenant-admin, or share token) and checks it against the operation's minimum role. Permission changes are themselves events in the document's update log so collaborators see access changes in real time.

Share links are signed, opaque tokens: an HMAC over `(document_id, role, expires_at, share_id)` with a server key, so a link is self-contained, revocable (revocation sets `shares.revoked_at`, checked on every resolution), and safe to log. Role escalation through a share is impossible because the token pins the role at creation time. Every permission decision — grant, revoke, and deny — is written to an append-only `access_audit` table with actor, target, and timestamp, which doubles as the compliance export.

### Public REST API

Base path `/api/v1`. All requests are authenticated (tenant users via session/JWT; shared links via signed share tokens). All responses are JSON; list endpoints are cursor-paginated with `?cursor=` and return `next_cursor`.

- `POST /documents` — create a document. Body: `{title}`. Returns 201 with the document resource: `{id, tenant_id, title, owner_id, created_at, updated_at, content_revision}`.
- `GET /documents` — list documents visible to the caller in the tenant, ordered by `updated_at` desc. Query: `cursor`, `limit` (default 50), `q` (title search).
- `GET /documents/{id}` — fetch the document with compiled content and state vector: `{..., content: [blocks], state_vector}`. 404 if not visible (no existence leak).
- `PATCH /documents/{id}` — update metadata: `{title?}`. Content edits go through the sync channel, not REST, to keep one write path.
- `DELETE /documents/{id}` — soft delete; owner or tenant admin. Returns 204.
- `GET /documents/{id}/versions` — list snapshots from the update log. `POST /documents/{id}/versions/{v}/restore` — restore.
- `GET /documents/{id}/shares` — list shares: `{share_id, principal, role, expires_at, created_by}`.
- `POST /documents/{id}/shares` — create a share. Body: `{principal_type: user|group|external_email, principal_id?, role, expires_at?}`. 409 if the principal already has a conflicting grant.
- `PATCH /documents/{id}/shares/{share_id}` — change role or expiry.
- `DELETE /documents/{id}/shares/{share_id}` — revoke. 204.
- `GET /shares/{token}` — resolve a signed share link (no auth) to the document with viewer-level content.

Errors use a consistent envelope `{error: {code, message, details?}}` with codes like `not_found`, `forbidden`, `conflict`, `rate_limited`. Every mutation returns the updated resource or 204, and all list responses carry `next_cursor`. The WebSocket endpoint `wss://…/sync?document={id}` performs the same role check on connect and streams CRDT updates; permission revocation closes the socket with a `revoked` frame.

### Non-functional requirements

Rate limiting is per-tenant with a token bucket (100 req/sec sustained, 500 burst) at the API gateway, plus a per-document limit on the sync channel (100 updates/sec per editor) to protect the update log from runaway clients. Mutating endpoints accept an `Idempotency-Key` header, stored for 24 hours, so a mobile client retrying on a flaky connection gets the original response. Every request carries a trace ID propagated into the sync channel; metrics are emitted per tenant and per document (requests, sync throughput, update-log depth) so a noisy document is visible before it becomes an incident. Backups are continuous WAL archiving to S3 with a 7-day PITR window; because RLS policies travel with the tables, a point-in-time restore cannot leak cross-tenant data.

### Failure modes and recovery

Postgres is the most critical dependency: if it is unavailable, reads and writes fail closed and the sync channel degrades to "queue locally" mode, which clients already support. The update log is the second critical path: compaction lag grows the log and slows re-syncs, so it is a first-class alert. S3 outages block asset upload and download but not text editing; asset references are stored optimistically and reconciled. A corrupted CRDT state is caught by a checksum on each snapshot; on mismatch the server falls back to the previous snapshot and affected editors re-sync — the worst case is lost work since the last good snapshot, never cross-document corruption.
## A3
This design has the right shape (event-driven, decoupled ledger) but three load-bearing pieces are wrong.

**1. The payment write and the event publish are not atomic.** "Writes to the payments table, then publishes" means a crash between the two commits loses the event: money moves, the ledger never sees it. The fix is the transactional outbox: write the `PaymentCreated` event into an `outbox` table in the *same database transaction* as the payment row, and have a relay (a small poller using `SELECT ... FOR UPDATE SKIP LOCKED`) publish outbox rows to SNS and mark them sent. The relay is at-least-once; the outbox makes the "did we publish?" question answerable from data, not from hope.

**2. "Retry from the SNS DLQ" is not a thing.** SNS topics do not have dead-letter queues; only SQS queue endpoints do. The real topology is SNS → one SQS queue per subscriber → per-queue DLQ. That is fine, and it means the ledger consumer is an SQS worker, which you should design explicitly: visibility timeout sized to the worst-case ledger write, max receive count 3–5, then DLQ with an alert (a DLQ message in a payments system is a page, not a log line).

**3. At-least-once delivery means the ledger consumer must be idempotent.** SNS/SQS deliver at least once, and your DLQ retry path *guarantees* redelivery. The ledger write must be `INSERT ... ON CONFLICT (payment_id) DO NOTHING` (or an equivalent unique constraint on the ledger entry key) so a duplicate `PaymentCreated` cannot create a second double-entry pair. This is the single most important detail in the design and it is currently absent.

**4. Ordering.** SNS provides no ordering guarantee. A double-entry ledger tolerates out-of-order entries *if* each entry is keyed by payment ID and idempotent, so this is acceptable — but state it explicitly, and if the ledger ever needs per-account sequence (e.g., balance snapshots), use SQS FIFO with `MessageGroupId = account_id` for that consumer.

**5. Reconsider the split itself.** The ledger is not a "downstream consumer" like notifications; it is a core correctness invariant of the payment. If the ledger service is a separate deployment, you have introduced a distributed-transaction problem (outbox, idempotency, reconciliation) to save a service boundary. The cheaper design: the ledger write happens in the same transaction as the payment (same database, double-entry rows in the same commit), and `PaymentCreated` is published *after* commit purely for non-critical consumers. If the ledger must stay a separate service for scaling reasons, then the outbox + idempotent consumer is mandatory, and you must add a reconciliation job that diffs `payments` against `ledger` entries every hour and pages on divergence — the outbox removes loss, but reconciliation is what proves it.

**6. Smaller points.** Version the event schema (`schema_version` field) from day one; include `payment_id`, `account_id`, `amount`, `currency`, `occurred_at` in the event so the ledger never has to call back to the payments API (a callback reintroduces the coupling and a new failure mode); and make the DLQ handler a human-in-the-loop process (inspect, replay with a tool) rather than an automatic retry loop.

The premise is false, and that is the important part: a set is not slower than a list for membership tests — it is dramatically faster, and for 10,000 IDs the gap is about four orders of magnitude. `x in list` is a linear scan: O(n) comparisons, so up to 10,000 element comparisons per check. `x in set` is a hash table probe: O(1) average, one hash and one or two comparisons per check. If the membership check itself got slower after the change, the set is not the cause; the cause is almost certainly *how* the set is being built and used. The classic mistake is constructing the set on every call — `if user_id in set(all_ids)` inside the hot path — which turns each check into an O(n) allocation plus 10,000 hash insertions, far more work than the list scan it replaced. Other usual suspects: the set is rebuilt on every request from a generator over a large collection; the ID collection itself grew (more IDs to hash and store means more memory and worse cache locality, which can show up as a slowdown even with O(1) lookups); or the change coincided with a data or traffic change that is the real cause.

What to switch to: keep the set, but build it **once** and reuse it — construct it at startup or when the ID population changes, store it (a `frozenset` if it is immutable, so it is cheap to share), and let the hot path do only the O(1) lookup. If the collection is genuinely huge and mostly-miss lookups dominate, a Bloom filter in front of the set gives a cheap negative path; if the IDs are dense integers (e.g., sequential user IDs), a bitset is the most memory- and cache-efficient exact structure. But for 10,000 IDs, a single pre-built set is the right answer — and it will be faster than the list was, not slower.

```python
"""Thread-safe, per-key token bucket rate limiter.

Properties
----------
- Token bucket per key with configurable capacity and refill rate
  (tokens per second).
- Thread-safe under concurrent access: one lock guards the bucket table
  and all bucket state; every public method is atomic.
- Keys expire after ``idle_ttl`` seconds (default 600) of inactivity so
  memory stays bounded.
- No background threads or timers: cleanup happens opportunistically
  inside normal calls (a sweep runs whenever the table grows to
  ``sweep_threshold`` entries).
- Uses a monotonic clock only (``time.monotonic`` by default, injectable
  for tests); a backward clock jump can never grant extra tokens.

Invariant
---------
No operation ever holds a lock while performing I/O or calling
user-supplied code. This module performs no I/O and calls no user code
at all, so the invariant holds by construction.
"""

from __future__ import annotations

import threading
import time
from typing import Callable, Dict, Optional


class _Bucket:
    """Internal per-key bucket state. Only valid while the limiter lock is held."""

    __slots__ = ("tokens", "last_refill", "last_access")

    def __init__(self, tokens: float, now: float) -> None:
        self.tokens = tokens
        self.last_refill = now
        self.last_access = now


class TokenBucketRateLimiter:
    def __init__(
        self,
        capacity: float,
        refill_rate: float,
        *,
        idle_ttl: float = 600.0,
        clock: Callable[[], float] = time.monotonic,
        sweep_threshold: int = 1024,
    ) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be > 0")
        if refill_rate < 0:
            raise ValueError("refill_rate must be >= 0")
        if idle_ttl <= 0:
            raise ValueError("idle_ttl must be > 0")
        self._capacity = float(capacity)
        self._refill_rate = float(refill_rate)
        self._idle_ttl = float(idle_ttl)
        self._clock = clock
        self._sweep_threshold = int(sweep_threshold)
        self._lock = threading.Lock()
        self._buckets: Dict[str, _Bucket] = {}

    # -- internals (caller must hold self._lock) -------------------------

    def _refill(self, bucket: _Bucket, now: float) -> None:
        elapsed = now - bucket.last_refill
        if elapsed > 0:  # guard: a backward clock jump grants nothing
            bucket.tokens = min(
                self._capacity, bucket.tokens + elapsed * self._refill_rate
            )
            bucket.last_refill = now

    def _sweep_expired(self, now: float) -> None:
        expired = [
            key
            for key, bucket in self._buckets.items()
            if now - bucket.last_access > self._idle_ttl
        ]
        for key in expired:
            del self._buckets[key]

    # -- public API -------------------------------------------------------

    def consume(self, key: str, tokens: float = 1.0) -> bool:
        """Try to consume ``tokens`` for ``key``.

        Returns True and debits the bucket if enough tokens are available
        after refill, otherwise False (state unchanged except bookkeeping).
        """
        if tokens < 0:
            raise ValueError("tokens must be >= 0")
        if tokens > self._capacity:
            return False
        now = self._clock()
        with self._lock:
            bucket = self._buckets.get(key)
            if bucket is None:
                if len(self._buckets) >= self._sweep_threshold:
                    self._sweep_expired(now)
                bucket = self._buckets.get(key)
                if bucket is None:
                    bucket = self._buckets[key] = _Bucket(self._capacity, now)
            self._refill(bucket, now)
            bucket.last_access = now
            if bucket.tokens >= tokens:
                bucket.tokens -= tokens
                return True
            return False

    # Convenience alias.
    allow = consume

    def available(self, key: str) -> float:
        """Tokens currently available for ``key`` (after refill)."""
        now = self._clock()
        with self._lock:
            bucket = self._buckets.get(key)
            if bucket is None:
                return self._capacity
            self._refill(bucket, now)
            bucket.last_access = now
            return bucket.tokens

    def reset(self, key: Optional[str] = None) -> None:
        """Drop one key's bucket, or all of them when ``key`` is None."""
        with self._lock:
            if key is None:
                self._buckets.clear()
            else:
                self._buckets.pop(key, None)

    def __len__(self) -> int:
        """Number of live (not yet swept) buckets."""
        with self._lock:
            return len(self._buckets)

        rl = TokenBucketRateLimiter(capacity=3, refill_rate=0.0, clock=clock)

class Concurrency(unittest.TestCase):
    def test_no_tokens_lost_under_contention(self):
        rl = TokenBucketRateLimiter(capacity=100, refill_rate=0.0)
        n_threads, per_thread = 8, 5000
        results = []
        lock = threading.Lock()
        barrier = threading.Barrier(n_threads)

        def worker():
            barrier.wait()
            local = 0
            for _ in range(per_thread):
                if rl.consume("hot"):
                    local += 1
            with lock:
                results.append(local)

        threads = [threading.Thread(target=worker) for _ in range(n_threads)]
        for t in threads:
            t.start()
        for t in threads:
            t.join()
        self.assertEqual(sum(results), 100)  # exactly capacity, no more, no less

    def test_multi_key_stress_no_errors(self):
        rl = TokenBucketRateLimiter(capacity=10, refill_rate=10.0)
        errors = []

        def worker(tid):
            try:
                for i in range(2000):
                    rl.consume(f"key-{tid % 7}", 1 + (i % 3))
                    rl.available(f"key-{tid % 7}")
            except Exception as exc:
                errors.append(exc)

        threads = [threading.Thread(target=worker, args=(t,)) for t in range(8)]
        for t in threads:
            t.start()
        for t in threads:
            t.join()
        self.assertEqual(errors, [])

    def test_reset_under_contention(self):
        rl = TokenBucketRateLimiter(capacity=10, refill_rate=0.0)
        stop = threading.Event()

        def worker():
            while not stop.is_set():
                rl.consume("k")
                rl.reset("k")

        threads = [threading.Thread(target=worker) for _ in range(4)]
        for t in threads:
            t.start()
        import time
        time.sleep(0.2)
        stop.set()
        for t in threads:
            t.join()
        self.assertLessEqual(len(rl), 1)
```

Design notes: one `threading.Lock` guards the bucket table and all bucket state, so every operation is atomic under concurrent access; the lock is only ever held around arithmetic and dict operations (no I/O, no user code), satisfying the invariant. Keys carry `last_access`; a sweep of keys idle for more than `idle_ttl` (default 600 s = 10 minutes) runs inside `consume` whenever the table reaches `sweep_threshold` entries, which bounds memory with no background thread. All timing uses the injected monotonic clock (default `time.monotonic`), and the refill computation guards `elapsed > 0` so a backward clock jump can never mint tokens.

**Why it fails in production.** The binary-search part of the function is exact integer arithmetic and is fine. The bug is the even-length branch:

```python
return (max(left_a, left_b) + min(right_a, right_b)) / 2
```

`/` converts the two 64-bit integers to IEEE-754 double-precision floats before adding and dividing. A float64 has a 53-bit significand, so integers above 2^53 ≈ 9.007×10^15 are rounded to the nearest representable float — typically off by 1 or 2. Unit tests pass because small test values fit exactly in 53 bits; production 64-bit record IDs do not. Reproducing input: `a = [9007199254740993]`, `b = [9007199254740994]` (i.e. 2^53+1 and 2^53+2). The true median is 9007199254740993.5; the buggy code rounds both operands to floats (9007199254740992.0 and 9007199254740994.0), averages them, and returns 9007199254740994.0. The fuzz run above found the original function wrong on 3,781 of 20,000 random cases at 64-bit scale.

**Fixed function** — do the averaging in exact integer arithmetic and only represent a true half-integer as a rational:

```python
from fractions import Fraction


def median_of_sorted_arrays(a, b):
    if len(a) > len(b):
        a, b = b, a
    lo, hi = 0, len(a)
    while lo <= hi:
        i = (lo + hi) // 2
        j = (len(a) + len(b) + 1) // 2 - i
        left_a  = a[i-1] if i > 0 else float('-inf')
        right_a = a[i]   if i < len(a) else float('inf')
        left_b  = b[j-1] if j > 0 else float('-inf')
        right_b = b[j]   if j < len(b) else float('inf')
        if left_a <= right_b and left_b <= right_a:
            if (len(a) + len(b)) % 2:
                return max(left_a, left_b)
            total = max(left_a, left_b) + min(right_a, right_b)
            if total % 2 == 0:
                return total // 2          # exact integer median
            return Fraction(total, 2)      # exact x.5, no float rounding
        elif left_a > right_b:
            hi = i - 1
        else:
            lo = i + 1
```

The sentinels `float('-inf')`/`float('inf')` are harmless: they only ever appear on the `max`/`min` side against a real element, and the real element always wins. The fixed version returns `int` for integer medians and `Fraction` (exact) for half-integer medians; callers that need a float can convert, accepting float precision only at the boundary. The fuzz (20,000 cases, values up to 2^63) shows 0 mismatches against the naive `sorted(a+b)` median.

## I3
Executed: `python3 i3_merge.py` (script in `work/`: exhaustive check over all sorted multisets of size ≤ 4 over {0,1,2}, 200,000 random sorted-pair fuzz cases, and explicit edge cases)

```
exhaustive small cases: 1225 ok
random fuzz: 200000 cases ok
edge cases ok
```

**Verdict: correct.** The function is the standard two-pointer merge. For every pair of inputs that satisfy its precondition — both lists sorted in non-decreasing order — it produces exactly `sorted(a + b)`:

- The loop invariant is that `out` equals the merge of `a[:i]` and `b[:j]` (both sorted), and `a[i:]`/`b[j:]` are untouched sorted tails. Each step appends the smaller of the two heads, which is the smallest element of the remaining union, so the invariant holds; when one list is exhausted, the other tail is already sorted and is appended wholesale.
- Ties are handled by `<=`, which takes from `a` first: the merge is **stable** (equal elements keep their relative order, with `a`'s copy before `b`'s).
- Edge cases verified: both empty, one empty, all-equal elements, interleaved elements.

The only caveat is the precondition itself: if a caller passes an *unsorted* list, the result is not sorted (e.g. `merge_sorted([1, 0], [2])` → `[1, 0, 2]`). That is a contract violation by the caller, not a defect in the function; for all valid inputs the function is correct.
