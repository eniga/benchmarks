## R2
Caching rests on a bet: data read now will be read again soon. In a multicore machine every core takes that bet privately, so the same physical line ends up resident in several caches at once. Coherence is the price of the bet. When one core overwrites a line that others also hold, those copies are wrong, and nothing in the hardware tells the owners. A coherence protocol is the agreement that keeps them honest: writes must propagate or be observed, stale copies must be removed or repaired, and two cores must never read different values for the same address after a write completes. Coherence is a per-location property. It says nothing about the order in which writes to different addresses become visible; that is the separate question of memory consistency. Mixing the two is the commonest source of confusion in this literature, and the distinction is worth keeping in mind throughout.

The oldest mechanism is snooping. Every cache watches, or snoops, the interconnect for transactions that touch addresses it holds, and repairs or discards its copy in response. The classic protocol is the four-state machine printed in every textbook: Modified, Exclusive, Shared, Invalid. A line is Modified when this cache owns the only valid copy and it differs from memory; Exclusive when it is clean but provably unique; Shared when other caches may hold it too; Invalid when this cache holds nothing usable. Transitions follow from a snoop hit: a read that hits in another cache's Modified line is answered from that cache rather than from DRAM, and the line is downgraded to Shared. Such a protocol needs an arbitration point, or a ring whose ordering is well defined, so that the question "who holds this line?" has one answer at every instant. Snooping is elegant, but it broadcasts, and its traffic grows with the number of caches — which is why it stopped scaling long before core counts did.

Directory protocols replace the broadcast with a lookup. For each line, a directory records which caches hold copies, as a pointer when there is one or two owners and as a bitmap when there are many. A write sends invalidations, or updates, only to the recorded owners and waits for acknowledgements before the store retires. Directories cost silicon, so their state lives in a home node — a memory-controller slice, a distributed directory, a snoop filter — and that state is deliberately imprecise: an over-approximation costs one extra message, never a wrong answer. The cost has moved from broadcast traffic to latency, since a miss on a remote line now costs a round trip to the home node before data can be fetched. Intel's snoop filters, AMD's probes and ARM's CHI all occupy this space. Directory schemes are what let a very large machine stay coherent without drowning its interconnect in snoops.

Coherence carries consistency along, but it does not deliver it. Programs are sequences of loads and stores to many addresses, and the memory model fixes the order in which they become visible. x86 guarantees total store order: stores from one core are seen in program order everywhere, though a load may still be reordered before an older load, which is why hardware and compilers both need fences — mfence, or a lock-prefixed instruction — to publish a pointer safely. ARM and RISC-V relax far more, offering acquire and release semantics on individual accesses. The operations that depend on coherence are the atomic read-modify-write primitives: compare-and-swap, load-linked and store-conditional. A compare-and-swap that is not linearizable is a defect in the protocol, and LL/SC depends on noticing a store to a reservation, which is exactly what coherence monitoring supplies. The same machinery explains false sharing: two unrelated variables that land in one line ping-pong between cores, and the cure is padding, not a fence.

Some paths sit outside coherence, or only pretend not to. Classic DMA is incoherent: a device writes DRAM behind the caches' backs, and the driver must invalidate or flush before trusting the buffer unless the platform offers a coherent DMA path. Uncacheable and write-combining memory is deliberately incoherent for the sake of speed; framebuffers and device registers get no coherence promises, and non-temporal stores stream past the caches, which is fast for big fills and hazardous for shared data. Line size is information too: coherence granularity is 64 bytes on mainstream parts, so a struct laid out with per-thread counters is a performance disaster waiting for two writers. Prefetchers widen the window further, since hardware fetches lines before the core asks, and the protocol must then distinguish speculation from demand, and both from pages the operating system has since unmapped.

The problem has not stopped existing at the edges of the CPU. GPU and accelerator coherence, NUMA and ccNUMA, and software transactional memory all inherit the same question: who may hold a valid copy, and who must be told when it dies. Persistent memory blurs it again, because a write there is ordered against caches, fences and a battery-backed write buffer at once. Cache coherence is the mechanism that keeps the shared-memory abstraction honest — one memory image, seen consistently by every core, paid for in messages, latency and subtle bugs. The protocols differ: broadcast or directory, invalidate or update, precise or approximate. The invariant is constant. After a write, a read returns what was written, for every reader, and no reader is ever given two answers to one question. Everything else in this field is engineering around that sentence.

## A1
**ADR 0001 — Event transport for the order-processing service**

Status: accepted.

### Context
We need to move order events from writers to downstream processors. Peak 40 events/sec, 3M events/day, average payload 2 KB. That is roughly 6 GB of payload per day, and a 7-day replay requirement means holding about 42 GB of events. Ordering must be strict per customer; global ordering is explicitly not required. Two backend engineers own this service, there is no platform team, we run Postgres 16 on AWS, and we have no Kubernetes.

The requirements that actually decide this are not throughput — all three options handle 40/sec while asleep — they are: (a) per-customer ordering, (b) seven days of replayable history, (c) atomicity between the order write and the event publish, and (d) a design two backend engineers can run without a dedicated on-call rota.

### Options considered
**Kafka.** Partition by customer id and you get per-partition ordering, retention-based replay, and consumer groups. It is the right answer at thousands of events/sec across many independent consumers. Here it means brokers to run or MSK to pay for, a schema registry, rebalance behaviour to understand, per-partition hot keys when one customer is chatty, plus a dead-letter topic and a redriver. Nothing about a 40/sec load justifies that operational surface for a team of two backend engineers.

**AWS SQS FIFO.** `MessageGroupId = customer_id` gives exactly the ordering semantics we need, retention is configurable well past seven days, delivery is near-once, and there is nothing to operate. It is the strongest runner-up. But it does not solve the hardest problem: a producer that writes to Postgres and then sends to SQS is doing a dual write, and a crash in between loses events or produces duplicates. So we would still need an outbox table in Postgres, a relay process, plus SQS's per-group throughput ceilings, poison-message handling and a DLQ pipeline. We would run two systems to get what one already gives us.

**Postgres as a queue.** An `events` table written in the same transaction as the order itself — a transactional outbox — drained by polling workers using `SELECT ... FOR UPDATE SKIP LOCKED`, ordered by a global sequence, with one customer claimed at a time so a single customer's events are only ever processed in sequence.

### Decision
Postgres-as-a-queue, implemented as a transactional outbox with polling consumers, partitioned daily, retention seven days.

Per-customer ordering comes from the sequence plus single-customer claiming. Replay comes for free: `UPDATE events SET consumed_at = NULL WHERE created_at >= now() - interval '7 days'`. Atomicity is the headline win — the event and the order commit together, so no event can describe an order that does not exist, and no order can exist without its event.

### Consequences
Positive: one system to run, no new infrastructure or vendor, ACID publish, trivially testable in CI, cheap, and consumer state is queryable with SQL (lag is a `COUNT(*)`).

Negative and mitigations: the queue shares a database with the workload, so we isolate it — daily partitions with automatic drop, a dedicated connection pool, a hard cap on concurrent consumers, and alerting on queue depth rather than relying on latency. Write amplification is around 125 inserts/sec plus status updates; at 2 KB payloads the table churn is well within a single Postgres 16 node, but it must be measured, not assumed. Polling adds latency in the 100 ms-to-1 s band; if a consumer ever needs sub-100 ms, we add NOTIFY on that consumer's path rather than switching transports. There is no push delivery and no per-consumer cursors; each consumer keeps its own offset, which we accept.

### What would change this decision
Sustained load above roughly 1,000 events/sec or 10M/day; a second or third independent consumer each with its own replay window and failure pace; queue depth starting to move OLTP latency; multi-region delivery; or a compliance requirement for transport-level isolation. At that point we move to SQS FIFO per consumer with an outbox relay — the same producer code, one new dependency — and only to Kafka if we acquire the platform capacity to run it properly.

## A2
**Multi-tenant document collaboration — data model and API**

### Assumptions
1. "Multi-tenant" means organisational tenancy (companies), with 1–20,000 members per tenant and no per-tenant compliance isolation requirement beyond logical separation.
2. Documents are text-centric rich documents (not binaries); binaries are attachments with their own storage.
3. A tenant has at most ~50 concurrent editors per document, and documents are small enough that a document's live state fits comfortably in one Postgres row (we cap structured content at 5 MB).
4. Concurrent editing means simultaneous editing of the same document by multiple people, with offline editing and reconnect support.
5. Users are provisioned by invitation; SSO/SAML is out of scope but the user model must not block it.
6. Permissions are needed at tenant, document and share-link level; inheritance through folders is required.
7. The public API is versioned and is the same API our own clients use.
8. Postgres 16 on AWS is the primary store; we may add Redis/queues for presence and fan-out but not a second document store.
9. Data must be exportable per tenant (deletion/portability obligations), and total data volume for the first year is under ~2 TB.
10. We are not building realtime voice/video, nor mobile-specific conflict rules.

### Tenancy isolation
Logical isolation in a shared Postgres cluster, hardened with row-level security rather than trust in application code. Every tenant-owned row carries `tenant_id`; each request sets `SET LOCAL app.tenant_id = $1` inside a transaction, and policies on every tenant table filter by it. This makes a forgotten `WHERE tenant_id = ?` a silent no-op instead of a data breach. Cross-tenant references are forbidden at the schema level: foreign keys from a child table to a parent in another tenant cannot be expressed, and we add a composite key `(tenant_id, id)` on parents so children can only reference within a tenant.

For the largest tenants we offer a "dedicated schema pack": the same tables, but the tenant's data lives in a separate schema plus its own connection pool, and RLS remains as a belt. This is a performance and noisy-neighbour measure, not a security boundary. Backups are per-database PITR; exports are per-tenant streaming dumps. An append-only `audit_log` (actor, tenant, target, action, before/after digest, ip, timestamp) is written in the same transaction as the mutation it describes.

### Document storage
`documents` holds identity: `id`, `tenant_id`, `owner_user_id`, `title`, `folder_id`, `kind`, `status`, `created_at`, `updated_at`, `deleted_at` (soft delete, 30 days). Content is stored as an immutable chain of revisions rather than a single mutable blob. `document_heads` stores `document_id`, `head_revision` (an integer), `content_snapshot` (materialised every 50 revisions or whenever the chain exceeds 500 ops), and `snapshot_seq`. `revisions` stores `(document_id, seq, author, base_seq, delta, created_at)`, where `delta` is a semantic operation log; the canonical content for any `seq` is snapshot plus applied deltas. This gives us version history, cheap diffs and a clean undo model without storing N full copies.

`attachments` are content-addressed in S3 with a DB row for metadata, scanned before they become visible, and referenced by digest only. Full-text search runs through Postgres `tsvector` columns on the materialised snapshot, rebuilt asynchronously per revision batch.

### Concurrent editing model
Operational transforms are unnecessary for our scale and difficult to get right; we use CRDTs — Yjs-compatible data types — because they converge without a central authority and survive offline editing. The server is the authority on commit order, not on merge logic.

Each client applies local ops to its CRDT state and sends `update` messages (compressed delta blobs) tagged with the last server seq it has seen. The gateway assigns a monotonic `seq` per document, appends the delta to `revisions`, and broadcasts to other participants; clients merge it. Because the CRDT is commutative and idempotent, arrival order and duplication are harmless — but we still serialise assignment at the gateway so history has one meaning. Presence (cursors, selections, "is typing") is ephemeral: it lives in Redis keyed by `document_id` with a TTL, never in the database, and is streamed to clients over the same socket.

Persistence is async-safe: the gateway writes deltas synchronously to its own durable append log, and a background consolidator builds snapshots and prunes the delta chain. A client reconnecting with a stale seq fetches the missing range; if the gap is beyond what we retain (we keep 10,000 deltas or 15 days), the client falls back to the snapshot and re-merges, which CRDT semantics make safe. Socket fan-out is per-document rooms; document load is protected by a per-document in-flight queue and a hard op-rate limit per connection.

### Permissions
A permission graph of principals, roles and targets. Principals: user, group (tenant members is an implicit group), share-link token. Roles: `owner`, `editor`, `commenter`, `viewer` — ordered, with a per-target `override` flag. Targets are documents and folders; a grant on a folder inherits to its children unless a child sets `inherit := false`. Tenant-level defaults come from the tenant settings: `anyone_in_tenant: view | edit | none`.

Authorisation is evaluated in one place, `PermissionService.check(actor, target, action)`, cached per (actor, target, head_seq) in Redis and invalidated on grant changes and on target moves. Service accounts and API tokens are principals too, and are modelled as such rather than as a bypass: a token carries a role and an optional document scope, so the same evaluation path serves a browser, a CLI and a webhook consumer. Share links carry a scoped capability (`doc:read`, `doc:write`) plus optional expiry and password; write links are the only way an unauthenticated user can reach a document. The RLS policies enforce tenant membership independently, so even a bug in the permission service cannot cross tenants.

### Consistency and failure model
The gateway's append log is the ordering authority: a delta is not acknowledged to its author until it has been durably appended with its seq, so a gateway that dies mid-broadcast loses nothing. Another gateway replays the same seq and the CRDT's idempotence absorbs the duplicate. Readers acknowledge nothing; they pull. A client that never reconnects still converges; a client that reconnects with a gap larger than the retained delta window takes a snapshot and re-merges, which is a slow path and never a wrong one. Document load is a snapshot plus a delta tail, so when the tail crosses the consolidator's threshold load time degrades gradually instead of cliffing. Sockets carry no session state beyond the room subscription, so a gateway restart costs reconnect latency rather than history, and presence entries expire on their own TTL. Deletes are soft for 30 days and then cascaded, including the S3 objects for attachments; audit rows are retained for a year with payload digests rather than copies, which is what portability and erasure requests need without turning the audit log into a shadow copy of every document.

## A3
### What I would change
**1. The dual write is a bug, not an edge case.** Writing to `payments`, then publishing to SNS, is two mutations in two systems with no atomicity. A crash, a timeout or a throttled publish between them silently loses the event, and the ledger never learns about a payment that exists. A retry of the whole request can double-publish. I would make the event a first-class part of the transaction: write the `PaymentCreated` row into an `outbox` table in the same commit as the payment, then have a relay (polling `FOR UPDATE SKIP LOCKED`, or CDC on the outbox) publish it. That gives at-least-once publish with no loss and no phantom events. Only after this is the ledger's promise — "the ledger knows about every payment" — meaningful.

**2. SNS to subscribers is the wrong delivery substrate.** SNS retries are brief and its per-subscriber failure handling is weak; a subscription that is down loses messages unless every subscription is a queue. If multiple consumers really need the events, the right shape is SNS fan-out to one SQS queue per consumer (or EventBridge → per-consumer queues), so each consumer gets durable storage, independent progress, its own DLQ and its own retry pace. Today there is one consumer: I would publish to a single SQS queue and add fan-out when a second consumer exists. Building fan-out for hypothetical consumers costs us ordering clarity and adds a failure mode now.

**3. "Retry from the DLQ" is not how DLQs work.** A DLQ receives messages that failed delivery after the retry policy exhausted; nothing redelivers them. Processing failures inside the ledger service don't even reach the DLQ unless the consumer deliberately fails the receive. So the design needs: an explicit visibility timeout sized to the ledger work, a redriver with a bounded attempt count, alerting on DLQ depth, and a runbook — plus idempotency, because redelivery will happen.

**4. The ledger writes must be idempotent.** Double-entry rows created from an at-least-once event will duplicate unless the ledger keys them. Every ledger entry set carries the source `event_id` (or a deterministic derived key) in a unique constraint, and a replayed event is a no-op. Without this, retries don't just delay money, they invent it.

**5. The ledger is being treated as a projection when it is a source of truth.** I want the ledger rebuildable from events, and I want reconciliation: a scheduled job comparing payment totals against ledger balances, per day and per currency, with the diff on a dashboard and a paging alert. Reconciliation is what tells us the pipeline is lying to us.

**6. Ordering.** SNS does not preserve order. If any downstream rule depends on "the balance was read after the credit", per-payment ordering must be explicit — serialize per payment/account, or design the ledger writes to be order-insensitive (append-only entries keyed by event, no derived running totals computed by read-modify-write).

**7. Contract and safety details.** The event needs a versioned schema in a registry, a documented failure/PII posture (payment events leak customer data — carry ids, not bodies), topic policy least-privilege, encryption and a schema-evolution rule. And reversals/refunds need a plan now, not later: an append-only ledger wants compensating entries, not updates.

**Net change:** outbox + relay to one SQS queue with per-consumer queues later, idempotent ledger writes keyed by event id, real redrive and DLQ alerting, daily reconciliation, order-independent ledger logic, versioned event schema. Same cost, a fraction of the surprise.

## H1
### The premise is wrong, so I will not explain it
A set is not slower than a list for membership tests. `x in some_set` is O(1) average — one hash, one table probe — while `x in some_list` is O(n) with a worst case of 10,000 comparisons. At n = 10,000 a set should be tens to hundreds of times faster, and if it measured slower, then the experiment measured something else. I would rather say that up front than invent a mechanism that makes the observation sound reasonable.

### What probably actually happened
Every way this measurement comes out "slower" is about *how the set is built*, not about lookup cost:

1. **The set is being rebuilt on every call.** `set(ids)` for 10,000 items costs 10,000 hashes plus a fresh ~1 MB hash table, every request. A list scan of the same data is O(n) but allocation-free and cache-friendly, and it **short-circuits on the first match**: if the value being tested is usually near the front, the list touches a handful of elements while the "fast" version hashes the whole ten thousand. A per-call `set(...)` really can lose to a list scan. The fix is not a different structure; it is building the set once and keeping it.
2. **The elements are not cheap to hash.** Python `int` and `str` keys are ideal (`str` caches its hash). Custom objects with a Python-level `__hash__`, or one that returns a constant, turn the set into a linear scan with extra overhead — the pathological collision case. If user IDs are value objects, hash them to a stable primitive.
3. **NumPy or pandas scalars.** If the IDs arrive as a NumPy array, `x in arr` is an element-by-element comparison (slow, and worse than a list because of boxing), and `set(arr)` boxes every element into a Python object. That is the classic "set made it slower" report. Use `np.searchsorted` on a sorted array, `np.isin`, or an explicit `arr.tolist()`/`frozenset(int(v) for v in arr)` built once.
4. **Correlation, not causation.** The diff also changed something else — a cache that got invalidated, a warm-up that stopped happening, a new import, a moved DB query. A 10,000-element set lookup is microseconds; if the service got "noticeably slower", a millisecond-per-request number is being attributed to the wrong line. That needs a profile, not a guess.

### What to switch to
* Build the collection **once**, at start-up or behind a cache, as a `frozenset`, and never rebuild it per call. That is the correct structure for 10,000 arbitrary IDs and it will be the fastest thing here.
* If the ID space is dense non-negative integers (say up to a few million) and the set is large, a **bitmap** is better again: a Python `int` used as a bitfield (`ids >> k & 1`), or `bitarray`/roaring bitmaps — O(1), tiny memory, no hashing.
* If the set is fixed and memory matters, a **sorted tuple plus `bisect_left`** is O(log n) with excellent cache behaviour and no hash-table overhead; it also skips the hashing cost when elements are compared anyway.
* If membership is really a database question ("is this user in this cohort?"), stop pulling 10,000 IDs into the process: answer it with an indexed query, a materialised join, or a **bloom filter** as a cheap pre-filter with the DB as the authority.
* Measure the same way both times: `timeit` on the *lookup only* versus the *whole operation*, with the collection built outside the timed region, and with realistic distributions (hit early, hit late, miss) rather than one value.

### Design
* **One lock, no nesting, clock read before it.** Every public method does `now = self._clock()` *first*, then takes the lock and works only with `now`. The clock is a user-supplied callable, so this is what the "no lock held while calling user code" invariant comes down to in practice; a test proves it by trying to take the limiter's lock from inside the clock.
* **Lazy refill.** Buckets store `tokens` and `last`; tokens are computed on access (`tokens + (now - last) * rate`, capped at capacity), so idle buckets cost nothing between calls. Elapsed is clamped at 0, so a clock that steps backwards neither mints tokens nor corrupts `last`.
* **Idle eviction with no background thread.** An `OrderedDict` keyed by key, ordered by last activity, doubles as the sweep queue. Each call evicts from the oldest end while `last < now - idle_ttl` (default 600 s). Cost is O(evictions+1) per call, amortised O(1), and no timer ever runs. `check`/`available` are pure peeks that do **not** refresh `last`, so polling a key cannot keep it alive forever.
* **Monotonic only.** `clock=time.monotonic` by default; nothing in the module reads the wall clock, so NTP steps and `settimeofday` are irrelevant. Injectable for deterministic tests.

```python
        self.last = last


class TokenBucketRateLimiter:
    def __init__(self, capacity, refill_rate, *, idle_ttl=DEFAULT_IDLE_TTL,
                 clock: Callable[[], float] = time.monotonic) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be > 0")
        if refill_rate < 0:
            raise ValueError("refill_rate must be >= 0")
        if idle_ttl <= 0:
            raise ValueError("idle_ttl must be > 0")
        self._capacity = float(capacity)
        self._refill_rate = float(refill_rate)
        self._idle_ttl = float(idle_ttl)
        self._clock = clock
        self._lock = threading.Lock()
        self._buckets: dict[str, _Bucket] = {}
        # LRU order by last activity: oldest first. Doubles as the sweep cursor.
        self._lru: "OrderedDict[str, None]" = OrderedDict()

    # --- public API: each entry point reads the clock *outside* the lock ---
    def acquire(self, key: str, tokens: float = 1) -> bool:
        self._check_tokens(tokens)
        now = self._clock()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._touch_locked(key, now)
            if bucket.tokens >= tokens:
                bucket.tokens -= tokens
                return True
            return False

    def check(self, key: str, tokens: float = 1) -> bool:
        """Pure peek: does not take tokens and does not keep the key alive."""
        self._check_tokens(tokens)
        now = self._clock()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._buckets.get(key)
            if bucket is None:
                return self._capacity >= tokens
            return self._peek(bucket, now) >= tokens

    def available(self, key: str) -> float:
        now = self._clock()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._buckets.get(key)
            return self._capacity if bucket is None else self._peek(bucket, now)

    def wait_time(self, key: str, tokens: float = 1) -> float:
        self._check_tokens(tokens)
        now = self._clock()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._buckets.get(key)
            have = self._capacity if bucket is None else self._peek(bucket, now)
            deficit = tokens - have
            if deficit <= 0:
                return 0.0
            if self._refill_rate <= 0:
                return float("inf")
            return deficit / self._refill_rate

    def reset(self, key: str) -> bool:
        with self._lock:
            return self._drop_locked(key)

    def clear(self) -> None:
        with self._lock:
            self._buckets.clear()
            self._lru.clear()

    def size(self) -> int:
        with self._lock:
            return len(self._buckets)

    def sweep(self) -> int:
        now = self._clock()
        with self._lock:
            return self._sweep_locked(now)

    def __len__(self) -> int:
        return self.size()

    # --- internals: ``_..._locked`` assume the lock is held and never call
    # user code (not even the clock). ---
    @staticmethod
    def _check_tokens(tokens: float) -> None:
        if tokens <= 0:
            raise ValueError("tokens must be > 0")

    def _peek(self, bucket: _Bucket, now: float) -> float:
        elapsed = now - bucket.last
        if elapsed <= 0:
            return bucket.tokens
        return min(self._capacity, bucket.tokens + elapsed * self._refill_rate)

    def _touch_locked(self, key: str, now: float) -> _Bucket:
        bucket = self._buckets.get(key)
        if bucket is None:
            bucket = _Bucket(self._capacity, now)
            self._buckets[key] = bucket
        else:
            elapsed = now - bucket.last
            if elapsed > 0:
                bucket.tokens = min(self._capacity, bucket.tokens + elapsed * self._refill_rate)
                bucket.last = now
        self._lru.pop(key, None)
        self._lru[key] = None
        return bucket

    def _drop_locked(self, key: str) -> bool:
        existed = self._buckets.pop(key, None) is not None
        self._lru.pop(key, None)
        return existed

    def _sweep_locked(self, now: float) -> int:
        cutoff = now - self._idle_ttl
        dropped = 0
        buckets, lru = self._buckets, self._lru
        while lru:
            key = next(iter(lru))
            bucket = buckets.get(key)
            if bucket is None:          # bookkeeping drift: heal and continue
                lru.popitem(last=False)
                continue
            if bucket.last >= cutoff:
                break
            lru.popitem(last=False)
            buckets.pop(key, None)
            dropped += 1
        return dropped
```

### Cause
Nothing is wrong with the binary search; the search finds the right partition every time. The bug is that the function leaves the integer domain. Its final step for an even total is

```python
return (max(left_a, left_b) + min(right_a, right_b)) / 2
```

and `/` is float true-division. For small test values the half is exactly representable in binary64, so unit tests pass. Once the arrays hold 64-bit record IDs, the true median is frequently a half-integer around 2**62 or 2**63, where a double's spacing is 512 or 1024: the exact value is not representable at all, so the function returns a *rounded* median. CPython's int/float comparison is exact, so the `-inf`/`+inf` sentinels do not corrupt the search itself — they are still a latent hazard, because any port or wrapper that compares an int64 against a float (e.g. NumPy scalars, where an int64 is converted to float64 for the comparison) breaks the partition too, and a NumPy `int64` sum can additionally overflow into negative territory.

Measured (5,000 random pairs of sorted arrays per row, results compared against an independent merge-based reference):

```

```

### Fix
Never convert an integer to a float. Select the needed order statistics with integer comparisons only, and average with exact integer arithmetic:

```python
from fractions import Fraction
from numbers import Integral


def _kth_smallest(a, b, k):
    """k-th (0-based) smallest element of two sorted sequences.
    O(log(m+n)); no sentinels, no float comparisons."""
    ia, ib = 0, 0
    la, lb = len(a), len(b)
    while True:
        if ia == la:
            return b[ib + k]
        if ib == lb:
            return a[ia + k]
        if k == 0:
            return a[ia] if a[ia] <= b[ib] else b[ib]
        half = (k - 1) // 2
        ja, jb = ia + half, ib + half
        if ja >= la:
            ja = la - 1
        if jb >= lb:
            jb = lb - 1
        if a[ja] <= b[jb]:
            k -= ja - ia + 1
            ia = ja + 1
        else:
            k -= jb - ib + 1
            ib = jb + 1


def median_of_sorted_arrays(a, b):
    n = len(a) + len(b)
    if n == 0:
        raise ValueError("median_of_sorted_arrays: no elements")
    if n % 2:
        return _kth_smallest(a, b, n // 2)
    left = _kth_smallest(a, b, n // 2 - 1)
    right = _kth_smallest(a, b, n // 2)
    if isinstance(left, Integral) and isinstance(right, Integral):
        total = int(left) + int(right)          # exact; no int64 overflow
        return total // 2 if total % 2 == 0 else Fraction(total, 2)
    return (left + right) / 2                   # float input: behave normally
```

Integer inputs now yield an `int` or an exact `Fraction` (2465/5000 of the earlier large sweep became wrong; all become right). The caller who wants a float can ask for one explicitly, at a precision loss they chose rather than one they inherited. If the production caller passes NumPy `int64` arrays, `Integral` covers `np.int64`, and the `int(...)` conversion means the sum is computed in Python integers rather than wrapping at 2**63. (NumPy is not installed in this environment, so I have not executed a NumPy case; that sentence is reasoning, not a test result.)

### Verdict: correct
For any two sequences sorted in non-decreasing order whose elements are mutually comparable, `merge_sorted` returns their sorted concatenation. It is also stable, and it does not mutate its inputs.

Proof sketch. *Partial correctness.* Invariant: at the top of every loop iteration, `out` equals the sorted merge of the already-consumed prefixes `a[:i]` and `b[:j]`, and every unconsumed element of `a[i:]` and `b[j:]` is ≥ every element in `out`. The body compares the two unconsumed heads and appends the smaller; because both tails are sorted, that head is the smallest remaining element overall, so the invariant survives. When the loop ends one side is exhausted and the other's remaining tail is sorted and ≥ everything appended, so the two `extend` calls complete the merge. *Termination.* Each iteration appends exactly one element and increments exactly one of `i`, `j`, so at most `len(a) + len(b)` iterations occur; `out.extend(a[i:])` and `out.extend(b[j:])` are disjoint tails of the inputs, so nothing is lost or duplicated. *Stability.* On equality `a[i] <= b[j]` takes from `a` first, so equal elements keep their input order within each list. *No mutation.* The only writes are to `out`, `i`, `j`.

Two honest caveats, both about the contract rather than defects: the claim holds only for already-sorted inputs (with unsorted inputs it produces a concatenation that is not sorted — it is a merge, not a sort), and elements from different lists must be mutually comparable.
