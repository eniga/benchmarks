## R2

Cache coherence is the discipline that keeps the multiple copies of a memory location held in a multicore machine consistent with one another. Since the early 1990s, nearly every high-performance processor has given each core, and often each core's individual pipeline stages, private caches. A cache is a latency optimization: it holds recently used data close to the core that touched it. The cost of that optimization is duplication. The same cache line can live in the L1 cache of four different cores, and if one core writes it, the others silently hold stale bytes. Cache coherence is the set of protocols and hardware mechanisms that prevent that staleness from violating the programmer's expectation that memory behaves as if it were a single shared array.

The contract that coherence protocols enforce is deliberately weaker than the stronger property of cache consistency. Coherence promises that all cores observe a single total order of writes to each individual address: once a write to a location becomes globally visible, subsequent reads of that location must observe that write or a later one. It says nothing about the order in which writes to different addresses become visible; that ordering belongs to memory consistency models, such as the total store order of x86 or the weaker models of ARM and RISC-V. Conflating the two is a common source of confusion: a machine can be perfectly coherent and still exhibit reorderings that surprise a programmer who assumes sequential consistency.

The classical solution to coherence is snooping. Every cache listens to the system interconnect and watches the addresses of transactions issued by other agents. The protocol is usually a variant of MSI, for Modified, Shared, and Invalid, sometimes extended with an Extra state to become MESI or MOESI. Each cache line carries one of these states. When a core reads a line that is not in its cache, it issues a bus read. If no other cache holds the line dirty, one of them supplies the data, and the line becomes shared in all caches that fetched it. When a core writes to a shared line, it must first obtain exclusive ownership. In write-invalidate protocols, the writer broadcasts an invalidate, the other caches drop their copies, and the writer proceeds. Invalidate protocols dominate modern designs because they save bandwidth: stale copies are discarded rather than rewritten.

Snooping scales well to a handful of cores on a single chip, but it does not scale to many sockets or to a large mesh. Every invalidate must reach every participant, so the interconnect becomes a bottleneck. The alternative is directory-based coherence. Each memory controller, or a dedicated home agent, keeps a directory for each line: a small record of which caches hold the line and in what state. A writer asks the home agent, and the home agent sends invalidates only to the caches that actually hold a copy. Directory protocols are the basis of most multi-socket server coherence, including Intel's UPI-based systems and AMD's Infinity Fabric. The directory is itself a cache of metadata, and it must be kept coherent with the lines it describes, which reintroduces a smaller version of the original problem.

Modern chip multipprocessors layer several additional complications on top of the basic protocol. Write-back caches mean that a dirty line can be destroyed by an eviction, so the protocol must track which cache owns the only copy of the data. Coherence also has to be maintained across non-cache agents: devices that perform DMA, accelerators, and I/O memory. On ARM systems, the coherent interconnect and the concept of device memory with different shareability attributes exist precisely to decide which agents must see which writes.

Software sees coherence through the lens of the memory model, but it cannot ignore the hardware entirely. Locks and atomics are implemented with cache-coherent operations: an atomic compare-and-swap must atomically read and write a line, which means it must hold the line in an exclusive state, which means it generates invalidates. This is why contended atomics are expensive: every successful update evicts the line from every other core, and the next contender must fetch it again, a phenomenon known as cache line ping-ponging. Pseudosharing, in which two logical variables occupy the same line, causes the same traffic for no logical reason, and it is an insidious performance bug in concurrent code.

The boundaries of coherence also define the boundaries of a machine. Coherence protocols do not, by themselves, span a network of machines. Distributed systems achieve a similar discipline with entirely different tools: quorums, vector clocks, and consensus algorithms such as Raft. When a cluster of servers caches the same object, no interconnect snoops the writes, and the application must reason about staleness explicitly. Understanding where coherence ends is as important as understanding how it works, because the failure mode of assuming coherence where it does not hold is a correctness bug, not a performance bug.

In summary, cache coherence is the invisible plumbing of parallel computing. It lets each core enjoy a fast, private view of memory while preserving the illusion of one shared memory. The protocols that deliver it, from the humble MSI snooping of the 1990s to the directory-based fabrics of today's servers, are a continuing negotiation between bandwidth, latency, and power. For the systems programmer, coherence is not just a hardware curiosity: it shapes the cost of every atomic operation, every lock, and every decision about where data lives.

## A1

### ADR: Event transport for the order-processing service

**Status:** Proposed
**Date:** (review pending)
**Deciders:** The two backend engineers owning the service

### Context

A new order-processing service must move order events (created, paid, shipped, cancelled, refunded) from the API layer to downstream processors for inventory, billing, and notifications.

Requirements: peak 40 events/sec, about 3M events per day, average payload 2 KB (about 6 GB/day of event data). Strict per-customer ordering: events for the same customer must be processed in the order they were emitted; global ordering is not required. Replay of the last 7 days must be possible for reprocessing (about 42 GB of retained data). The team is two backend engineers with no dedicated platform team. Existing infrastructure: Postgres 16 in production and AWS; no Kubernetes.

### Options considered

**1. Kafka (self-hosted or AWS MSK).** Kafka is the canonical answer to this problem: a partitioned, replicated log with consumer offsets gives per-partition ordering and native replay for any retention window. Setting the partition key to customer_id gives exactly the per-customer ordering we need, and a 7-day retention setting makes replay trivial. The problem is that running Kafka well is a platform job. Two backend engineers without a platform team would own broker upgrades, partition reassignment, consumer-lag monitoring, KRaft/ZooKeeper operations, and capacity planning on top of the product service. Even with AWS MSK, the team must understand consumer-group semantics, rebalancing, and schema evolution to operate it safely. At 40 events/sec the throughput headroom is enormous: we would be paying for and operating infrastructure sized for a problem an order of magnitude larger than our load.

**2. AWS SQS FIFO.** FIFO queues give per-message-group ordering (MessageGroupId = customer_id), 14-day retention, at-least-once or exactly-once delivery, and no infrastructure to run. 40 msg/sec is well within the default 300 msg/sec FIFO limit. The problem is replay: SQS FIFO has none. Once a message is received and deleted it is gone, so meeting the 7-day replay requirement means writing every event to a second store (S3 or Postgres) anyway. At that point SQS is only a fast path in front of a log we already have. FIFO queues also carry operational quirks — deduplication-ID management, throttling under burst load, throughput-mode changes — that a two-person team would learn the hard way.

**3. Postgres-as-a-queue.** Use the Postgres 16 instance we already run. Events are rows in an events table (id, customer_id, type, payload jsonb, created_at, processed_at). Workers claim work with SELECT ... FOR UPDATE SKIP LOCKED, filtered to one customer at a time, which gives per-customer ordering by construction. Replay is a query: rerun the processor over the last 7 days of rows. Retention is a scheduled delete. The trade-off is that Postgres under sustained queue load needs attention — vacuuming, index bloat, connection pooling. At our scale (40 inserts/sec, 40 claims/sec) this is trivially within Postgres's comfort zone, but it is a real operational difference from a purpose-built broker.

### Decision

**Postgres-as-a-queue.**

At 40 events/sec and 6 GB/day, the deciding factor is not throughput — all three options clear it easily — it is the cost of meeting the replay and ordering requirements with two engineers and no platform team. Postgres gives all three requirements with zero new infrastructure: per-customer ordering via single-customer-at-a-time claiming, 7-day replay via a plain query over retained rows, and 7-day retention via a scheduled delete. The event log doubles as the audit trail, which the other options would have required a second store to provide.

### Consequences

- **Ordering:** a worker claims one customer at a time — it takes a Postgres advisory lock keyed on customer_id, then processes that customer's oldest pending row. Events for one customer are strictly ordered; different customers are processed in parallel.
- **Replay:** reprocessing is a SELECT over the last 7 days of rows run by a backfill job. A processed-log table keyed on (event_id, processor) makes replays idempotent.
- **Throughput:** 40/sec is a small fraction of what Postgres comfortably sustains for point inserts and claims. We monitor claim latency and queue depth as primary signals.
- **Backpressure:** queue depth is a maintained counter; we alert when it exceeds a threshold.
- **Cost:** no new service to run; 7 days of events is about 42 GB of storage on the existing instance.
- **Team load:** the two engineers own one new table, one worker process, and one backfill job.

### What would change the decision

- Sustained load above roughly 5,000 events/sec, or many independent consumer groups each needing the full stream: move to Kafka (MSK), because fan-out and throughput stop being trivial in Postgres.
- A requirement for global ordering, or for consumers to start from arbitrary offsets with exactly-once guarantees: Kafka.
- If a platform team appears, or the number of services needing event fan-out grows: re-evaluate Kafka. Until then, each consumer reads the same events table with its own processed-log.
- If Postgres queue depth or vacuum pressure becomes a measurable problem under load: first fix is partitioning the events table by day; second is moving to SQS FIFO with a Postgres write-through for replay.

## A2

### Assumptions

1. Tenants are B2B organizations; each tenant has many members (users) and one or more admins.
2. Documents are collaborative text (rich text stored as blocks), up to about 1 MB each; file attachments are stored separately.
3. Users within a tenant can edit the same document simultaneously; near-real-time synchronization (sub-second) is required, but the public API is REST (no WebSockets).
4. Infrastructure: one Postgres 16 database (shared database, shared schema), S3 for version snapshots and attachments, and a standard API gateway in front.
5. Authentication is via bearer tokens (JWT) carrying tenant_id and user_id; the API is HTTPS-only.
6. Permissions are role-based at the document level (owner, editor, commenter, viewer), plus tenant-level admin.
7. Documents are soft-deleted; full version history is retained for one year.
8. Target scale: about 10,000 tenants, about 100,000 documents, about 1,000 concurrent editors.

### Tenancy isolation

Shared database, shared schema, row-level isolation. Every table that holds tenant data carries a tenant_id column, and every query is scoped by it. Two layers enforce this:

1. **Application layer.** A repository/data-access layer injects the authenticated tenant_id into every query. No repository method can be called without a tenant context; code review plus a lint rule (no raw SQL outside the repository) keeps this honest.
2. **Database layer.** Postgres Row-Level Security as a backstop. Each connection sets app.tenant_id from the auth context, and RLS policies on every tenant table enforce tenant_id = current_setting('app.tenant_id'). A bug that forgets the WHERE clause returns zero rows instead of another tenant's data.

Cross-tenant access is impossible by construction: no API path takes a tenant_id as a parameter; the tenant comes only from the token. Tenant admins see only their own tenant.

### Request lifecycle

Every request follows the same path: the gateway validates the bearer token and extracts (tenant_id, user_id); middleware attaches that context to the request; the repository layer injects tenant_id into every query, and Postgres RLS re-checks it at the database level; the authorization layer resolves the caller's effective role on the target document; the handler runs; and the response is serialized. A failure at any layer produces the standard error envelope. Because the tenant context is derived only from the token, no handler can ever receive a request aimed at a different tenant, and the RLS backstop means that even a tenant-scoping bug fails closed: rows are invisible, not leaked.

### Document storage

Tables:

- **documents**: id (uuid), tenant_id, title, owner_id, created_by, created_at, updated_at, deleted_at, revision (integer, monotonically increasing per document), content (jsonb, the current block tree).
- **document_versions**: id, document_id, tenant_id, revision, author_id, created_at, storage_key (S3), size_bytes. A full snapshot per revision, kept in S3; Postgres holds only the metadata.
- **attachments**: id, document_id, tenant_id, filename, content_type, size_bytes, storage_key, uploaded_by, created_at.
- **shares**: as described in the permissions section.

Content model: the document body is an array of blocks, each with a stable uuid, a type (paragraph, heading, list, table, embed), and field data. Block ids are stable across edits, which is what makes concurrent editing tractable: operations reference blocks, not positions. The current state lives in documents.content (jsonb, updated transactionally with the revision bump). Full snapshots go to S3 for versioning, so Postgres never grows with edit history.

### Concurrent editing model

Server-sequenced operations (operational-transformation style), with the server as the single source of truth:

- An edit is a batch of operations: insert_block, update_block_fields, delete_block, move_block — each referencing stable block ids.
- A client sends POST /documents/{id}/operations with base_revision and the operation batch.
- The server applies the operations to the authoritative state at base_revision, transforming them against any operations that landed in between (a transform function defined per operation pair; conflicting operations on the same block resolve last-writer-wins at the field level). It bumps revision, stores the new state, and returns the new revision.
- If the client's base is stale and a transform fails (a referenced block was deleted), the server returns 409 with the latest state; the client re-bases and retries.
- Near-real-time delivery over REST: GET /documents/{id}/changes?since_revision=N is long-polled (or polled by the client every ~1 second) and returns the operation batches since N. A WebSocket service can be added later in front of the same operation log without changing the model.

Why not CRDTs: CRDTs give better offline merge semantics, but for a server-sequenced document editor with sub-second sync, OT with a central sequencer is simpler to implement, simpler to debug, and gives a clean audit trail (every revision is an applied operation batch). We accept that offline edits require a rebase on reconnect.

Example: at revision 100, Alice inserts a new block after block B0, and Bob, also based on revision 100, edits the text of B0. Bob's operation applies cleanly at revision 101, because block ids are stable and his update targets the same block that Alice inserted next to. If Bob had instead deleted B0, the server would reject Alice's insert with a 409 and the latest state, and her client would re-attach the new block at the nearest surviving anchor.

### Permissions

- **Roles:** owner > editor > commenter > viewer. The creator is the owner. Tenant admins implicitly have owner rights on every document in their tenant (but do not become the owner).
- **shares table:** id, document_id, tenant_id, principal_type (user | group | tenant), principal_id, role, created_by, created_at; unique on (document_id, principal_type, principal_id). A tenant-type share grants a role to everyone in the tenant (the default for new documents: tenant/viewer, or tenant/editor depending on the organization default).
- **Effective permission** is the maximum of the direct user share, the group shares, the tenant share, and the implicit admin/owner rights.
- **Enforcement:** authorization middleware resolves (tenant_id, user_id) from the token; each route declares the minimum role (read: viewer; edit: editor; share/manage: owner or tenant admin; delete: owner or tenant admin). The check happens after tenancy scoping, so a user can never even see another tenant's document id in an error (404, not 403, for cross-tenant access).

### Public REST API

All paths are tenant-scoped by the token; pagination is cursor-based (?cursor=&limit=); errors use a standard envelope {"error": {"code", "message", "details"}}.

Documents:

- GET /v1/documents?q=&updated_after=&cursor= — list the caller's documents (those with viewer+ access), newest first.
- POST /v1/documents — body {"title", "blocks"}; 201 with the document. Supports Idempotency-Key.
- GET /v1/documents/{id} — {"id", "title", "revision", "blocks", "updated_at"}.
- PUT /v1/documents/{id} — full-document replace; requires If-Match: <revision>; 409 on mismatch.
- POST /v1/documents/{id}/operations — {"base_revision", "operations": [...]}; 200 {"revision"} or 409 {"revision", "blocks"} for re-basing.
- GET /v1/documents/{id}/changes?since_revision= — operation batches since the revision (long-pollable).
- GET /v1/documents/{id}/revisions and GET /v1/documents/{id}/revisions/{n} — version list and snapshot.
- DELETE /v1/documents/{id} — soft delete; 204.

Shares:

- GET /v1/documents/{id}/shares — list shares with resolved principal names.
- PUT /v1/documents/{id}/shares/{principal_type}/{principal_id} — body {"role"}; upserts the share (owner/admin only).
- DELETE /v1/documents/{id}/shares/{principal_type}/{principal_id} — remove the share.

Status codes: 401 (unauthenticated), 403 (insufficient role), 404 (not found or another tenant's), 409 (revision conflict), 422 (invalid operations). Rate limits return 429 with Retry-After.

### Scaling and failure modes

At the assumed scale (10,000 tenants, 100,000 documents, 1,000 concurrent editors), a single Postgres 16 instance is sufficient: document reads are point lookups by (tenant_id, id), and the write path does one row update per operation batch. The hot spot is the documents row of a heavily edited document; operation batches are small (a few blocks), and the revision bump serializes writers, so a single document's write rate is bounded by its editor count — at our scale, tens of writes per second at most. If a single document ever becomes a bottleneck, the fix is to split its content into per-section rows, not to change the model.

Failure modes: if Postgres dies mid-batch, the transaction rolls back and the client retries (the operation is idempotent with respect to its base_revision). If S3 is unavailable, editing continues — S3 is only needed for snapshot persistence, which is retried asynchronously — and reads of old revisions degrade gracefully. Version snapshots are written after the revision is committed, so a crash in between at worst loses one restorable snapshot, never the current state.

## A3

The design has the right shape for fan-out but the wrong consistency model for a ledger. I would change the following.

**1. Make the event atomic with the payment (transactional outbox).** As written, the payment row commits first and the SNS publish is a separate step. If the publish fails (or the publishing process crashes), the payment exists with no ledger entry, and nothing in the design recovers that case — the DLQ only catches failures on the consumer side. Write the payment row and an outbox row (payment_id, event payload, published_at NULL) in one Postgres transaction; a relay polls the outbox, publishes to SNS, and marks the row published. Now the event is guaranteed to exist whenever the payment does, and the relay gives at-least-once delivery with bounded lag.

**2. Make the ledger idempotent, not retry-driven.** SNS is at-least-once: redelivery after a crash, a relay republish, or a manual DLQ re-drive will all produce duplicate PaymentCreated events. The ledger must treat payment_id as a natural idempotency key — a unique constraint on the ledger entry keyed by payment_id, so a duplicate insert is a no-op. Then "retry from the DLQ" becomes safe, and the DLQ becomes a monitoring and repair path rather than the correctness mechanism.

**3. Build reconciliation as a job, not as an afterthought.** A periodic reconciliation that compares payments to ledger entries (the ledger is a projection of the payments table) catches anything the event path missed, and it is what actually makes the system correct end-to-end. Without it, a single lost message is a silent accounting hole.

**4. Handle ordering explicitly.** SNS gives no ordering guarantees. If the ledger needs per-account ordering (sequential entry numbers, running balances), say so: either apply entries out of order and idempotently, or route through per-account FIFO queues. The current design silently assumes an ordering it does not have.

**5. Keep SNS, but subscribe through SQS.** The stated reason for SNS (multiple future consumers) is valid, but each subscription should be an SQS queue, not a direct Lambda: per-consumer retry policy, per-consumer DLQ, visibility timeouts, and the ability to replay one consumer's queue without affecting the others.

**6. Minor.** Version the event schema; put payment_id, amount, currency, created_at, and an idempotency key in the event so consumers never have to call back; never publish from inside the payment transaction (the outbox relay is the only publisher); and alert on outbox lag, not just DLQ depth.

## H1

The premise is false, so I will not explain it as stated: a set is not slower than a list for membership tests — it is dramatically faster. List membership is O(n): a linear scan that, for 10,000 IDs, performs up to 10,000 comparisons per check. Set membership is O(1) in expectation: one hash plus (usually) one equality comparison. For 10,000 elements the set is typically two to three orders of magnitude faster per check. If the service got noticeably slower after the change, the slowdown has a different cause. The usual suspects, in order of likelihood:

1. **The set is rebuilt on every request.** If the code does `ids = set(user_ids)` inside the hot path (e.g., per request or per call), the O(n) construction cost is paid on every check and cancels the O(1) win — and can even be slower than the list scan if the list was cached. Fix: build the set once, cache it (a frozenset if it never changes), and invalidate it when the ID list changes.
2. **The change shipped with other changes.** The "membership check" diff may have landed in a deploy that also included a slower query, a new middleware, or a config change. Check the deploy, not just the diff.
3. **The IDs are expensive to hash.** Plain ints and short strings hash cheaply, but if the "user IDs" are actually large objects with a costly __hash__ (or the check is `x in set` where x is a large string recomputed each time), hashing can dominate. For 10,000 elements this is unusual but measurable.
4. **The check is not what it seems.** If the code iterates the set to build something (e.g., a filter), the iteration cost is the same as for a list and the "improvement" was never in the membership test.

**What to switch to:** keep the set — it is the correct structure for membership tests at this scale (use frozenset for an immutable ID list). If the universe of IDs is bounded and dense (e.g., integer IDs below a few million), a boolean array or bitset indexed by ID is even faster (O(1) with a smaller constant and no hashing), but that is an optimization, not a fix. The right next step is to profile the hot path (cProfile or perf) to find where the time actually went.

### Module: `work/rate_limiter.py`

```python
"""Per-key token-bucket rate limiter.

Properties:
- One token bucket per key, with configurable capacity and refill rate
  (tokens per second).
- Thread-safe: all state is guarded by a single ``threading.Lock``.
- Keys expire after ``idle_ttl`` seconds (default 600 = 10 minutes) of
  inactivity, so memory stays bounded. Cleanup happens opportunistically
  inside normal calls; there are no background threads or timers.
- Only ``time.monotonic()`` is used, so wall-clock changes cannot break it.
- Invariant: no operation ever holds the lock while performing I/O or
  calling user-supplied code. The limiter's public methods take only
  hashable values and do no I/O; the lock is held only around in-memory
  bookkeeping.
"""

from __future__ import annotations

import threading
import time
from typing import Any


class _Bucket:
    __slots__ = ("tokens", "updated")

    def __init__(self, capacity: float, now: float) -> None:
        self.tokens = float(capacity)
        self.updated = now


class TokenBucketRateLimiter:
    """Per-key token bucket rate limiter.

    Parameters
    ----------
    capacity:
        Maximum number of tokens a bucket can hold (burst size).
    refill_rate:
        Tokens added per second while the bucket is below capacity.
    idle_ttl:
        Seconds of inactivity after which a key's bucket is discarded.
        Defaults to 600 (10 minutes).
    """

    def __init__(self, capacity: float, refill_rate: float, idle_ttl: float = 600.0) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        if refill_rate < 0:
            raise ValueError("refill_rate must be non-negative")
        if idle_ttl <= 0:
            raise ValueError("idle_ttl must be positive")
        self._capacity = float(capacity)
        self._refill_rate = float(refill_rate)
        self._idle_ttl = float(idle_ttl)
        self._buckets: dict[Any, _Bucket] = {}
        self._lock = threading.Lock()

    # -- public API -------------------------------------------------------

    def allow(self, key: Any, n: int = 1, now: float | None = None) -> bool:
        """Try to consume ``n`` tokens for ``key``.

        Returns True and consumes the tokens if enough are available,
        otherwise returns False and consumes nothing. ``now`` is a test
        hook; production callers leave it as None and the monotonic
        clock is used.
        """
        if n <= 0:
            raise ValueError("n must be positive")
        if now is None:
            now = time.monotonic()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._buckets.get(key)
            if bucket is None:
                bucket = _Bucket(self._capacity, now)
                self._buckets[key] = bucket
            # Refill advances ``bucket.updated`` to ``now`` only when
            # ``now`` is newer; the timestamp must never move backwards.
            # Different threads may hold slightly stale monotonic readings,
            # and a backwards update would let the same time window refill
            # twice. Any access (granted or denied) at a newer timestamp
            # therefore counts as activity.
            self._refill_locked(bucket, now)
            if bucket.tokens >= n:
                bucket.tokens -= n
                return True
            return False

    def try_acquire(self, key: Any, n: int = 1, now: float | None = None) -> bool:
        """Alias for :meth:`allow`."""
        return self.allow(key, n=n, now=now)

    def remaining(self, key: Any, now: float | None = None) -> float:
        """Tokens currently available for ``key`` (without consuming any).

        Note: this call also refreshes the key's activity timestamp and
        may trigger the idle sweep, like any other call.
        """
        if now is None:
            now = time.monotonic()
        with self._lock:
            self._sweep_locked(now)
            bucket = self._buckets.get(key)
            if bucket is None:
                return self._capacity
            self._refill_locked(bucket, now)
            return bucket.tokens

    def live_keys(self, now: float | None = None) -> int:
        """Number of buckets currently held in memory (after a sweep).

        ``now`` is a test hook; production callers leave it as None.
        """
        if now is None:
            now = time.monotonic()
        with self._lock:
            self._sweep_locked(now)
            return len(self._buckets)

    # -- internals (caller holds self._lock) ------------------------------

    def _refill_locked(self, bucket: _Bucket, now: float) -> None:
        elapsed = now - bucket.updated
        if elapsed > 0:
            bucket.tokens = min(self._capacity, bucket.tokens + elapsed * self._refill_rate)
            bucket.updated = now

    def _sweep_locked(self, now: float) -> None:
        """Drop buckets idle for longer than ``idle_ttl``.

        Runs on every public call, so no background thread is needed.
        Cost is O(live keys), which is bounded by the number of distinct
        keys active within the last ``idle_ttl`` seconds.
        """
        expired = [k for k, b in self._buckets.items() if now - b.updated > self._idle_ttl]
        for k in expired:
            del self._buckets[k]
```

Design notes:

- **Per-key buckets, configurable capacity and refill rate:** constructor takes `capacity` and `refill_rate`; one `_Bucket` per key.
- **Thread safety:** a single `threading.Lock` guards the bucket map and every bucket; all state changes happen under it.
- **10-minute inactivity expiry:** each bucket records the newest timestamp seen for its key; `_sweep_locked` drops buckets idle longer than `idle_ttl` (default 600 s). The sweep runs inside every public call, so memory is bounded without any background thread or timer.
- **Monotonic clock:** only `time.monotonic()` is used (the `now` parameter is a test hook defaulting to it), so wall-clock changes cannot affect it.
- **Lock invariant:** the public API accepts only hashable values and performs no I/O; no user-supplied code is ever called, so the lock is never held during I/O or user code. One subtlety the concurrency test caught: the bucket timestamp must never move backwards, because different threads can hold slightly stale monotonic readings; a backwards update would let the same time window refill twice. Refill therefore only advances the timestamp.

class TestThreadSafety(unittest.TestCase):
    def test_concurrent_allows_never_exceed_capacity_plus_refill(self):
        # rate 0 => exactly `capacity` allows total, no matter the threading.
        capacity = 1000
        rl = TokenBucketRateLimiter(capacity=capacity, refill_rate=0.0)
        n_threads, per_thread = 16, 250
        granted = []
        lock = threading.Lock()
        barrier = threading.Barrier(n_threads)

        def worker():
            barrier.wait()
            local = 0
            for _ in range(per_thread):
                if rl.allow("shared"):
                    local += 1
            with lock:
                granted.append(local)

        threads = [threading.Thread(target=worker) for _ in range(n_threads)]
        for t in threads:
            t.start()
        for t in threads:
            t.join()
        self.assertEqual(sum(granted), capacity)

    def test_concurrent_distinct_keys(self):
        rl = TokenBucketRateLimiter(capacity=10, refill_rate=0.0)
        errors = []

        def worker(tid):
            try:
                for i in range(200):
                    rl.allow(f"key-{tid}", n=1)
                    rl.remaining(f"key-{tid}")
            except Exception as e:  # pragma: no cover
                errors.append(e)

        threads = [threading.Thread(target=worker, args=(t,)) for t in range(8)]
        for t in threads:
            t.start()
        for t in threads:
            t.join()
        self.assertEqual(errors, [])
        self.assertEqual(rl.live_keys(), 8)

    def test_concurrent_refill_accounting(self):
        # 100 tokens/sec, capacity 100. One token consumed at t=0 (99 left).
        # 8 threads make 50 attempts each, with timestamps interleaved
        # across t in [0, 49/50]. Total tokens that can ever be available
        # is 99 + 100 * (49/50) = 197, so total grants must be ~197 and
        # must never approach the 400 attempts made. (Before the
        # no-backwards-timestamp fix, the same time window could refill
        # repeatedly and all 400 attempts were granted.)
        rl = TokenBucketRateLimiter(capacity=100, refill_rate=100.0)
        rl.allow("k", now=0.0)  # consume 1 at t=0
        granted = []
        lock = threading.Lock()
        barrier = threading.Barrier(8)

        def worker():
            barrier.wait()
            local = 0
            for i in range(50):
                if rl.allow("k", now=(i % 50) / 50.0):
                    local += 1
            with lock:
                granted.append(local)

        threads = [threading.Thread(target=worker) for _ in range(8)]
        for t in threads:
            t.start()
        for t in threads:
            t.join()
        total = sum(granted)
        # Upper bound is the regression check: the pre-fix code granted
        # all 400 attempts by refilling the same window repeatedly.
        self.assertLessEqual(total, 198)  # 197 + float slack
        # The bucket is never starved to absurdity either (the cap at
        # capacity can shed some tokens, but most of the 197 available
        # must be claimable by 400 attempts).
        self.assertGreaterEqual(total, 100)


class TestLockInvariant(unittest.TestCase):
    """The limiter never performs I/O or invokes user-supplied callbacks
    while holding its lock: the public API accepts only hashable values
    and does purely in-memory bookkeeping under the lock, so the
    invariant holds by construction. These tests show that even a
    pathologically slow key (whose __hash__ sleeps) cannot deadlock the
    limiter or starve other threads indefinitely."""

    def test_slow_key_cannot_deadlock(self):
        import time as _time

        class SlowKey:
            def __init__(self, v):
                self.v = v

            def __hash__(self):
                _time.sleep(0.05)
                return hash(self.v)

            def __eq__(self, other):
                return isinstance(other, SlowKey) and self.v == other.v

        rl = TokenBucketRateLimiter(capacity=1, refill_rate=0.0)
        k = SlowKey(1)
        self.assertTrue(rl.allow(k))
        self.assertFalse(rl.allow(k))  # capacity 1, rate 0

        done = []

        def other():
            rl.allow("plain")
            done.append(True)

        th = threading.Thread(target=other)
        th.start()
        th.join(timeout=1.0)
        self.assertEqual(done, [True])

    def test_no_user_callback_api_exists(self):
        # Document the invariant structurally: none of the public methods
        # accept a callable.
        import inspect

        sig = inspect.signature(TokenBucketRateLimiter.allow)
        for param in sig.parameters.values():
            self.assertNotIn("Callable", str(param.annotation))

## I2

Executed: `python3 median_repro.py` (Python 3.14.6), which runs the original function, a reproduction input, the fixed function, and a 5000-case randomized cross-check against a naive merge-and-middle median.

**Why it fails in production but not in unit tests.** The binary-search part of the algorithm is exact integer arithmetic and is fine. The bug is the final line for even-sized inputs:

```python
return (max(left_a, left_b) + min(right_a, right_b)) / 2
```

Python's `/` is true division, which converts the operands to IEEE-754 double-precision floats. A double has a 53-bit significand, so any 64-bit record ID above 2^53 is rounded when it enters the division. Unit tests use small integers (well below 2^53), where the float round-trip is exact, so they pass; production arrays of 64-bit record IDs hit the rounding and get a wrong median.

**Reproduction input:**

```python
a = [2**62]          # [4611686018427387904]
b = [2**62 + 2]      # [4611686018427387906]
```

The true median is (2^62 + 2^62 + 2) / 2 = 2^62 + 1 = 4611686018427387905. The original returns `4.611686018427388e+18`, whose exact value is 4611686018427387904 — off by 1.

**Fixed function** (exact integer arithmetic; returns an int when the median is integral, an exact `Fraction` for a half-integer):

```python
from fractions import Fraction

def median_of_sorted_arrays(a, b):
    if len(a) > len(b):
        a, b = b, a
    lo, hi = 0, len(a)
    while lo <= hi:
        i = (lo + hi) // 2
        j = (len(a) + len(b) + 1) // 2 - i
        left_a  = a[i-1] if i > 0 else float('-inf')
        right_a = a[i]   if i < len(a) else float('inf')
        left_b  = b[j-1] if j > 0 else float('-inf')
        right_b = b[j]   if j < len(b) else float('inf')
        if left_a <= right_b and left_b <= right_a:
            if (len(a) + len(b)) % 2:
                return max(left_a, left_b)
            total = max(left_a, left_b) + min(right_a, right_b)
            if total % 2 == 0:
                return total // 2
            return Fraction(total, 2)
        elif left_a > right_b:
            hi = i - 1
        else:
            lo = i + 1
```
