## T2
Cache coherence is the problem of keeping multiple copies of the same memory location consistent when several processors can read and write it. In a uniprocessor, memory is a single shared array and there is no question of which copy is authoritative. In a multicore machine, however, each core usually keeps its own private cache, and a line of memory can therefore live in several caches at once. If one core writes a line that another core has cached, the two copies diverge; without a coherence mechanism the second core would silently read a stale value. Cache coherence is the set of protocols and hardware that prevent this: they guarantee that every core observes a single, well-defined order of writes to each memory location, as if the writes had been applied to a central memory one at a time.

The standard model for reasoning about coherence is sequential consistency, introduced by Leslie Lamport. A system is sequentially consistent if the result of any execution is the same as if the memory operations of all processors were interleaved in some single total order, and the operations of each individual processor appear in that order in the order they were issued. This is a strong and intuitive guarantee: a programmer can pretend that all cores share one memory and that instructions execute in program order, even though in reality each core's operations may be reordered and buffered.

The hardware that provides coherence is organized around the cache line, the smallest unit (typically 64 bytes) that moves between a cache and memory. Each line is tracked with a state, and the most common protocol is MESI. MESI stands for the four states a line can be in: Modified, Exclusive, Shared, and Invalid. A line is Modified when the owning cache has written it and no other cache holds a copy, so the copy in memory is stale and the owner must supply the new value if anyone else asks. Exclusive means the line is in exactly one cache and is clean (matching memory); it is a fast path for the common case where one core reads a line that no one else has. Shared means the line is in several caches and all of them agree with memory. Invalid means the line is not currently valid in this cache. Transitions between these states are driven by bus transactions such as Read, Read-Shared, Read-Exclusive (or Read-For-Ownership), and Invalidate. When a core wants to write a line it holds in Shared state, it issues a transaction that forces every other cache to invalidate its copy, and the writing core takes the line into Modified. This is the write-invalidate policy, and it is the heart of how coherence is maintained.

An alternative is write-update (or write-broadcast), in which a write updates every copy of the line in every cache rather than invalidating them. Write-invalidate is far more common because it is cheaper: invalidating a line is a single broadcast, whereas updating would require sending the new data to every cache that holds the line. Write-invalidate does, however, create a "write-write" traffic pattern known as false sharing when two cores write to different variables that happen to sit in the same cache line; each write invalidates the other core's line, causing a ping-pong of cache transfers. This is a classic pitfall, avoided by padding hot variables into separate lines.

Coherence is not the same as consistency, and the distinction matters. Coherence concerns the ordering of writes to a single location as seen by different cores; it is a property of the cache-interconnect hardware. Memory consistency, by contrast, is a broader property of the whole memory system, describing the ordering of reads and writes across different locations and the visibility of one core's writes to another. Modern architectures deliberately relax strict sequential consistency to gain performance, allowing loads to be reordered with older stores and letting a store become visible only after its store buffer drains. They provide explicit fence or barrier instructions, such as x86's mfence or ARM's dmb, to restore ordering where it is needed. The C and C++ memory models formalize these relaxations with concepts such as "sequentially consistent" atomics versus "relaxed" atomics, and with happens-before and synchronizes-with edges that define when one thread's write is guaranteed to be visible to another.

The practical consequence of all this is that correctness in concurrent code depends on understanding both coherence and consistency. Coherence ensures that a write to a location is not lost and that all cores eventually agree on its value; consistency determines when and in what order that value becomes visible. A bug that looks like a race condition is often, in fact, a memory-ordering bug: a value was written, but the reading core observed it before a dependent value, or observed a stale copy because the necessary barrier was missing.

In summary, cache coherence is the mechanism by which multicore processors present a single, coherent view of memory despite each core caching data privately. It is implemented with protocols such as MESI operating on cache lines, using write-invalidate to keep copies from diverging. It is a hardware property that is distinct from, but complementary to, memory consistency, which governs the ordering and visibility of operations across cores and locations. Together with the explicit synchronization and memory-ordering tools exposed by the language and the architecture, they let a programmer build correct concurrent software on hardware that is, in its raw form, far more permissive than a single shared memory would suggest.

## A1
**ADR: Data synchronization strategy for the offline-first field app**

**Context.** The app lets field technicians edit job records while offline for up to 72 hours, then sync when connectivity returns. Each record is owned by exactly one technician, so two different people never edit the same record. The same technician, however, may edit the same record from two devices while offline. Records are flat, with about 40 scalar fields. A regulatory requirement states that every field change must be attributable to a named person and carry a server-assigned timestamp, and that the change history must be human-readable during an audit without tooling. We have one backend engineer and a Postgres backend.

**Options considered.**
1. *CRDT library.* Adopt a conflict-free replicated data type library so that concurrent edits from the two devices merge automatically without a server round trip.
2. *Server-authoritative per-field last-write-wins with an append-only change log.* The server is the single source of truth. Each field change is sent to the server, which stamps it with a server timestamp and the editing person, applies a per-field last-write-wins rule, and appends the change to an immutable, human-readable log.
3. *Record-level optimistic concurrency with manual conflict resolution.* The client sends the whole record with a version number; if the version is stale the server rejects the write and the user must resolve the conflict by hand.

**Decision.** We adopt option 2: server-authoritative per-field last-write-wins with an append-only change log.

**Rationale.** The single-owner-per-record constraint removes the hardest case that CRDTs are designed for: merging genuinely divergent edits from different people. Here the only conflicts are between one technician's two devices, and those are best resolved by a simple, deterministic rule rather than by version vectors or merge functions. Per-field last-write-wins handles this cleanly: for each field, the change with the latest server-assigned timestamp wins, and because the server assigns the timestamp, the ordering is total and unambiguous even when the two devices were offline and their local clocks disagree.

The regulatory requirement is the deciding factor. An append-only change log in which each row records the person, the server timestamp, the field, and the old and new values is exactly the artifact an auditor needs: it is a plain table that can be printed or exported and read without any tooling. A CRDT's internal metadata (version vectors, tombstones, merge state) is not human-readable and would have to be translated into an audit log anyway, at which point we have built the change log regardless and the CRDT has added complexity for no audit benefit. Record-level optimistic concurrency (option 3) would force a field technician, possibly offline and in the field, to resolve conflicts between their own two devices by hand, which is a poor user experience and a likely source of dropped or mis-resolved changes.

The single backend engineer and Postgres backend also favor option 2. It is straightforward to implement: a `jobs` table for current field values, and an append-only `job_field_changes` table for the log. A REST sync endpoint accepts a batch of field changes from a device, stamps and stores them, and returns the authoritative state. There is no new infrastructure, no CRDT runtime to operate, and no conflict-resolution UI to build and test.

**Consequences.**
- The server assigns timestamps at receipt, so the server clock is the source of truth; devices do not need synchronized clocks.
- Clients must track, per field, the last server timestamp they have applied, so they can detect and discard changes the server has already superseded.
- The change log grows without bound; we will need a retention and archival policy, but archiving is straightforward because the log is append-only and immutable.
- Photos are uploaded separately and are out of scope for this decision.
- The 72-hour offline window is handled by queueing changes locally on the device and replaying them on reconnect; because the rule is per-field last-write-wins, replay order does not affect correctness.
- A field edited on both devices while offline resolves to whichever change reaches the server last; the other change is still recorded in the log, so nothing is silently lost.

**What would change this decision.**
- If two technicians could ever edit the same record, the single-owner assumption breaks and we would need a real merge (a CRDT or a field-level merge policy) rather than last-write-wins.
- If the regulator required that both conflicting values be preserved and presented for human adjudication (no silent overwrite), we would move to manual conflict resolution or a CRDT with a visible history.
- If any field had non-trivial merge semantics, such as an ordered list that both devices extend concurrently, per-field last-write-wins on the whole list would be too coarse and we would need per-item merging for that field.
- If the number of devices per technician grew large or the offline window grew much longer, the replay-and-merge load would increase and we would revisit the design.

## A2
**Write path for a three-region order service**

**Assumptions.**
1. Every customer belongs to exactly one home region, and that assignment is stable and known to all regions (a small customer-to-home-region mapping is replicated to every API edge).
2. The API edge in each region can redirect a client to the home region's edge (HTTP 307/308), and clients follow the redirect.
3. The 80 ms p99 write-latency budget applies to the write as handled by the home region's edge (the redirect hop is not counted against it).
4. Intra-region round trips and a local synchronous commit are well under 80 ms (local commit p99 under 20 ms).
5. Replication between regions is asynchronous.
6. A region's isolation is detectable by the edges via health checks and heartbeat timeouts.
7. Orders are created only through the API; there are no direct writes to the store.
8. The client supplies an Idempotency-Key so that retries do not create duplicate orders.

**Partitioning and routing.** Orders are partitioned by customer, and a customer belongs to one home region, so all orders for a customer live in, and are written by, the home region. This is the key structural fact: it means there is exactly one writer for any given customer's orders, which eliminates the dual-write conflicts that make multi-region writes hard.

The API edge in each region resolves the customer's home region from the locally replicated mapping. If the request already landed in the home region, the write is handled locally. If it landed elsewhere, the edge issues a redirect to the home region's edge and the client re-issues the request there. Redirecting rather than proxying keeps the latency budget honest: the write is performed, and its latency measured, in the home region, where a local write comfortably fits in 80 ms. Proxying the write across regions would add at least one inter-region round trip, and the Frankfurt-Virginia RTT alone is 90 ms, which already exceeds the entire budget.

**The write path (in the home region).** First, the edge authenticates the request and re-checks the customer's home region. Second, it validates the order and checks the Idempotency-Key against a local idempotency table; a replay with the same key and body returns the original result, and a replay with a different body returns 409. Third, it assigns an order ID (a UUIDv7, which is globally unique and time-ordered, so no cross-region coordination is needed to mint IDs). Fourth, it persists the order with a synchronous commit to the home region's primary store (Postgres), so that the order is durable before the response is sent. Fifth, it returns 201 with the order ID and status "accepted".

The synchronous local commit is the linchpin. Because the write is local (in the home region) and the commit is synchronous, the end-to-end latency is dominated by validation plus one local commit, which is well within 80 ms at p99. This synchronous commit before the 201 is returned is what guarantees that an accepted order is never lost.

The idempotency table is written in the same synchronous transaction as the order, so the deduplication guarantee is as durable as the order itself: a retried request cannot create a second order even if the first response was lost in transit. The latency budget breaks down roughly as a few milliseconds for authentication and validation, a sub-millisecond idempotency lookup, and one synchronous local commit in the low tens of milliseconds, leaving headroom under the 80 ms p99 target even under load.

**Replication and reads.** After the home region commits an order, it replicates it asynchronously to the other two regions. Replication is one-way, from the home region to the others, which is sufficient because the home region is the only writer. The replicas serve reads: a GET for an order is answered from the local region's replica, giving low-latency reads anywhere, with a bounded staleness. If a strong read is required, the client reads from the home region.

Because replication is asynchronous, a read immediately after a write may not see the write if it is served from a non-home replica. The API documents this: reads are eventually consistent with a bounded staleness, and a read-your-own-writes guarantee is provided for reads served from the home region.

The replication itself is log-based: the home region ships its committed write-ahead log (or an equivalent ordered change stream) to the two replicas, which apply changes in commit order, so each replica is a strict, ordered suffix of the home region's history. Because only the home region writes, the replicas never need to merge concurrent writes from each other; they only replay a single ordered stream. A replica that falls behind is caught up by continuing to apply the stream, and a replica that is lost is rebuilt by taking a full snapshot and then replaying the stream from the snapshot's sequence number.

**Failure behavior when a region is isolated.** If the home region is isolated, writes for that region's customers cannot be durably committed, so the edges do not accept them: they return 503 with a Retry-After, and the client retries. Nothing is lost because nothing is accepted that cannot be durably stored; reads in the other regions continue from their replicas (stale but available). If a non-home region is isolated, writes are unaffected (they all go to home regions) and reads in the isolated region fail over to the remaining replicas. In a split-brain, because each customer has exactly one home region and the home region is the single writer, there is no dual-writer conflict: if the home region is partitioned from the others, it continues to accept and commit writes for its customers and replicates them when the partition heals, while the other regions serve stale reads in the meantime. There is no scenario in which two regions both believe they are the writer for the same customer.

**Public API contract.** `POST /orders` (handled in the home region) takes a body of customer_id and items plus an Idempotency-Key header, and returns 201 with the order_id and status "accepted"; it returns 307 or 308 if the request is not in the home region, 409 if the idempotency key is reused with a different body, and 503 if the home region is unavailable. `GET /orders/{order_id}` returns the order and its status, served from the local replica (eventually consistent) or the home region (strong), and returns 404 for an unknown order. Order status progresses accepted, processing, shipped, delivered (or failed). Errors are 400 for validation, 404 for an unknown order, and 503 for an unavailable home region.

**Why this meets the requirements.** Partitioning by customer with a single home region gives a single writer per customer, which is what makes the write path simple and correct. Routing to the home region via redirect keeps the write local, so the 80 ms p99 budget is met. The synchronous local commit before the 201 is returned guarantees that an accepted order is never lost. One-way asynchronous replication from the home region provides low-latency reads everywhere without reintroducing dual-writer conflicts. The failure behavior is defined so that isolation degrades reads (stale but available) rather than risking loss or duplication of writes.

## A3
Your design is a standard cache-aside pattern, and it is mostly sound, but the fire-and-forget delete is the weak point, and there are a few races and failure modes worth fixing.

**1. The fire-and-forget delete is the main correctness risk.** If the delete fails (network blip, Redis down, timeout), the stale value stays in the cache until the 10-minute TTL expires. For a product catalog, that means a stale price or stock level can be served for up to 10 minutes after a change. Fire-and-forget is the right call for write availability (a cache failure should not fail a write), but it is the wrong call for consistency. Fix: make the invalidation reliable. Either do a synchronous delete with a bounded retry, or push the delete through a small outbox or retry queue so that a failed delete is retried until it succeeds. If a delete ultimately cannot be delivered, force a short TTL on the key or mark it stale so the staleness window is bounded and small rather than 10 minutes.

**2. There is a read/write race that can repopulate a stale value.** Sequence: a read misses and starts loading the row from Postgres; a write commits and deletes the key; the read then finishes and writes the (now stale) row it loaded back into Redis. The cache now holds a stale value for up to the TTL, even though a delete happened. This is the classic cache-aside race. Fixes, in increasing order of cost: (a) shorten the TTL so the window is small; (b) have the writer set the key to the new value after the DB commit (write-through) instead of deleting, so a late read cannot overwrite it with stale data; or (c) use versioned keys, including a version or generation from the DB row in the cache key or value, and have the reader verify the version before caching, discarding the value if the row changed while it was loading.

**3. Cache stampede on hot keys.** When a hot key expires, many concurrent misses all load from Postgres at once, which can spike the database. Fix with request coalescing (single-flight): let one request load the value while the others wait for it, or use a short mutex around repopulation. Stale-while-revalidate (serve the stale value briefly while refreshing in the background) also smooths this out.

**4. No negative caching.** Repeated reads of a nonexistent key miss every time and hammer Postgres. Cache the miss as a short-TTL tombstone so that absent keys are not re-checked on every request.

**5. Redis outage behavior is unspecified.** If Redis is down, reads should fall through to Postgres (via a circuit breaker so you do not pile up timeouts), and writes should still succeed (your fire-and-forget delete already ensures this). Make the fall-through explicit and tested.

**6. Minor issues.** The serialized Postgres row in Redis should carry a schema or format version so that a schema change does not silently deserialize into the wrong shape. Consider key namespacing (per-tenant, per-entity) and the maxmemory eviction policy, and be aware of hot keys that exceed a single shard.

**What I would change, in priority order.** (1) Make invalidation reliable (synchronous delete with retry or an outbox, with a bounded staleness fallback). (2) Close the read/write repopulation race with write-through or versioned keys. (3) Add stampede protection (single-flight or stale-while-revalidate). (4) Add negative caching. (5) Add a circuit-breaker fall-through to Postgres on Redis outage. (6) Reconsider the 10-minute TTL for volatile fields such as price and stock, using a shorter TTL or field-level invalidation for those.

The pool:
```python
import threading, time

class _Waiter:
    __slots__ = ("event", "conn")
    def __init__(self):
        self.event = threading.Event()
        self.conn = None

class ConnectionPool:
    def __init__(self, factory, close, max_size, idle_timeout=60.0):
        if max_size < 1:
            raise ValueError("max_size must be >= 1")
        self._factory = factory
        self._close = close
        self._max_size = int(max_size)
        self._idle_timeout = float(idle_timeout)
        self._lock = threading.RLock()
        self._idle = []          # (conn, released_at)  -> available
        self._in_use = 0         # checked out
        self._waiters = []       # FIFO of _Waiter

    def _live(self):
        return self._in_use + len(self._idle)

    def acquire(self, timeout=None):
        deadline = None if timeout is None else time.monotonic() + timeout
        while True:
            waiter = None
            with self._lock:
                if self._idle:
                    conn, released_at = self._idle.pop()
                    self._in_use += 1
                    stale = (time.monotonic() - released_at) > self._idle_timeout
                    action = "idle"
                elif self._live() < self._max_size:
                    self._in_use += 1
                    conn, stale, action = None, False, "create"
                else:
                    waiter = _Waiter()
                    self._waiters.append(waiter)
                    conn, stale, action = None, False, "wait"
            if action == "wait":
                remaining = None if deadline is None else deadline - time.monotonic()
                if remaining is not None and remaining <= 0:
                    with self._lock:
                        self._waiters.remove(waiter)
                    raise TimeoutError("timed out waiting for a connection")
                if waiter.event.wait(remaining):
                    return waiter.conn
                with self._lock:               # a release may have raced us
                    if waiter.event.is_set():
                        return waiter.conn
                    self._waiters.remove(waiter)
                raise TimeoutError("timed out waiting for a connection")
            if action == "create":
                return self._factory()          # no lock held here
            if stale:
                self._close(conn)               # no lock held here
                return self._factory()          # no lock held here
            return conn

    def release(self, conn):
        with self._lock:
            if self._waiters:
                waiter = self._waiters.pop(0)   # head of the FIFO
                waiter.conn = conn
                waiter.event.set()
                return                          # stays checked out; _in_use unchanged
            self._in_use -= 1
            self._idle.append((conn, time.monotonic()))
```

How the requirements are met:
- **FIFO fairness.** Waiters are appended to the tail of `_waiters` in the order they call `acquire` (serialized by `_lock`), and `release` always hands the connection to `_waiters.pop(0)`, the head. A late arrival either creates a new connection (pool not full) or joins the tail; it never takes an existing connection ahead of a longer-waiting thread.
- **No lock held while calling `factory`/`close`.** Both are invoked only after the `with self._lock` block has exited.
- **No lock held while a thread is blocked waiting.** The blocking `waiter.event.wait(...)` happens outside `_lock`.
- **Idle timeout, no background threads/timers.** When `acquire` pops an idle connection it compares `time.monotonic()` against the recorded release time; if it is stale the connection is closed and a fresh one created, lazily, at that moment.
- **Monotonic clock only.** All timing uses `time.monotonic()`.

The tests (`work/test_c1.py`) cover: happy path reuse; `acquire(timeout)` raising `TimeoutError`; strict FIFO ordering of 6 waiters on a size-1 pool (served order `[0,1,2,3,4,5]`); a late arrival not jumping the queue; stale connections being closed and replaced; no background closer firing and no extra threads; the pool lock being free while a thread is blocked in `acquire`; and a blocking factory not deadlocking the pool. A first bug I hit and fixed: `release` originally decremented `_in_use` on the direct-handoff-to-waiter path, which made the count go negative and deadlocked the FIFO test; the fix is to leave `_in_use` unchanged when a connection is handed straight to a waiter.

```python
def resolve(graph):
    order, done = [], set()
    def visit(node, stack):
        if node in done:
            return
        if node in stack:
            raise ValueError(f"cycle through {node}")
        stack.add(node)
        for dep in graph.get(node, ()):
            visit(dep, stack)
        stack.discard(node)
        done.add(node)          # mark done only AFTER deps are processed
        order.append(node)
    for node in graph:
        visit(node, set())
    return order
```

The optimization. The original is O(n^2). The replacement is a Fenwick tree (Binary Indexed Tree) over coordinate-compressed values, O(n log n):
```python
def count_smaller_before_fast(values):
    if not values:
        return []
    sorted_unique = sorted(set(values))
    rank = {v: i + 1 for i, v in enumerate(sorted_unique)}  # 1-indexed
    m = len(sorted_unique)
    bit = [0] * (m + 1)
    def update(i):
        while i <= m:
            bit[i] += 1
            i += i & (-i)
    def query(i):
        s = 0
        while i > 0:
            s += bit[i]
            i -= i & (-i)
        return s
    out = []
    for v in values:
        r = rank[v]
        out.append(query(r - 1))   # earlier values with rank < r  => strictly smaller
        update(r)
    return out
```
For each index i, the answer is the number of earlier elements strictly smaller than `values[i]`. Coordinate compression is order-preserving (duplicates share a rank), so querying the Fenwick prefix sum over ranks `< rank(values[i])` counts exactly the earlier strictly-smaller values; we add `values[i]` to the tree only after querying, so only j < i are counted.

## L1
**(a) Tier ordering and the rule.** The tiers from lowest to highest are `registry < catalog < index < metrics` (in `corelib/locking.py`, `TIER_RANK` assigns registry=0, catalog=1, index=2, metrics=3). The rule: a thread may only acquire locks in strictly ascending tier order — holding a lock of tier X, it may acquire a lock of tier Y only if Y > X (or Y == X, since re-acquiring the same tier is permitted). Acquiring a lower tier while holding a higher one is forbidden.

**(b) Naming convention.** Helper functions whose names end in `_locked` assume the caller already holds the tier named in their docstring and do not acquire a lock themselves. Examples: `_bump_generation_locked` in `svc/catalog_ops.py` (docstring "Caller must hold ``catalog``") and `_rollup_locked` in the shard classes (e.g. `svc/bundle_00.py`, docstring "Caller must hold ``catalog``"); also `_incr_locked` in `svc/metrics_sink_02.py` and `_write_shard_locked` in `svc/reindex_07.py`.

**(c) Families and tiers** (each family is `svc/<name>_00.py` through `svc/<name>_25.py`):
- bundle: `catalog`
- cache: `catalog`
- digest: `metrics`
- dispatch: `registry`
- ledger: `registry`
- probe: `metrics`
- router: `registry`
- session: `registry`
- stream: `index`
- tracker: `catalog`

**(d)** `ascending("metrics", "catalog")` returns `False`, because `TIER_RANK["metrics"] = 3` and `TIER_RANK["catalog"] = 1`, and `3 <= 1` is `False`. Acquiring metrics and then catalog is a higher-to-lower (descending) acquisition, which violates the strictly-ascending rule.

## L2
**(a) The violation.** The path starts in `rebuild_shard` in `svc/reindex_07.py`. It acquires `locks.index` (`with locks.index:`), and while still holding index it calls `refresh_catalog_entry(shard, payload)` in `svc/catalog_ops.py`, which acquires `locks.catalog` (the `with locks.catalog:` inside `refresh_catalog_entry`). The order of acquisition is index (rank 2) then catalog (rank 1) — descending, which violates the strictly-ascending rule. The second acquisition (catalog) occurs in `refresh_catalog_entry` in `svc/catalog_ops.py`.

Similar-but-legal paths I considered and rejected:
- `sweep` in `svc/audit_11.py`: holds catalog, then acquires index via `_touch_index_stat`. catalog (1) to index (2) is ascending, so it is legal.
- `rebuild_from_snapshot` in `svc/reindex_03.py`: acquires catalog via `read_catalog_snapshot` and releases it before acquiring index. The acquisitions are sequential, not nested, so it is legal.
- `incr` in `svc/metrics_sink_02.py`: re-acquires the same tier (metrics) while holding it. Re-entrant same-tier acquisition is permitted, so it is legal.
- `compact` in `svc/legacy_notes_04.py`: acquires only catalog (a single tier). Legal. (Its docstring describes a legacy index-then-catalog path that deadlocked, but the current code does not perform that acquisition.)

**(b) The memory-budget breach.** The ceiling is `HARD_MEMORY_BUDGET = 2 GiB` (2,147,483,648 bytes), stated in `corelib/limits.py`; the rule there is that the total commit of all enabled pools must be strictly less than this budget, where a pool's commit is `pool_commit(workers, prefetch_depth) = workers * prefetch_depth * BUFFER_BYTES` and `BUFFER_BYTES = 1 MiB`.

Pools (from the ingest pool modules), with worker count, prefetch depth, and enabled flag:
- `ingest_primary` (`ingest/pool_ingest.py`): 96 workers, depth 4, enabled.
- `parse_fanout` (`ingest/pool_parse.py`): 128, depth 3, enabled.
- `enrich_lookup` (`ingest/pool_enrich.py`): 64, depth 8, enabled.
- `export_writer` (`ingest/pool_export.py`): 192, depth 5, enabled.
- `replay_shadow` (`ingest/pool_replay.py`): 256, depth 12, **disabled — excluded**, because a pool constructed with `enabled=False` is never started and commits nothing.

Arithmetic (1 MiB per worker-depth unit):
- ingest_primary: 96 x 4 = 384 MiB
- parse_fanout: 128 x 3 = 384 MiB
- enrich_lookup: 64 x 8 = 512 MiB
- export_writer: 192 x 5 = 960 MiB
- Total (enabled): 384 + 384 + 512 + 960 = 2240 MiB = 2,348,810,240 bytes.

Budget: 2 GiB = 2048 MiB = 2,147,483,648 bytes. Breach: 2240 MiB - 2048 MiB = **192 MiB** (201,326,592 bytes) over; the enabled pools exceed the budget by 9.375% (2240/2048 = 1.09375).
