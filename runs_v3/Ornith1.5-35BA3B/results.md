## T2

A 900-word essay on cache coherence.

Cache coherence is the problem of keeping multiple caches that hold copies of the
same memory address agreeing with one another so that any reader observes a value
consistent with the order in which writes were issued. It exists wherever more
than one agent can cache writable state that another agent may also write: the
multiple cores of a shared-memory multiprocessor, a CPU and its L1.2.3 tiers when
those tiers are independently coherent, and, by extension, any distributed system
that replicates writable state at the edge of latency. The moment you allow a
write to land in a private cache and hide it from other agents, you have created
a coherence problem; everything after that is about detecting and reconciling the
divergence.

The canonical failure is a stale read. Suppose core A and core B both cache line
X. A reads X, gets 7. B writes 9, but the write stays in B's private cache under
a write-back policy, so the shared memory still says 7. If A now writes X and
reads it back, or if some third agent reads X, the system behaves as if B's write
never happened, or as if A's write vanished. In a single-threaded program on a
single core this is impossible because of local visibility: a core always sees its
own writes. The hazard is purely cross-agent, which is why coherence is described
as a multi-agent property rather than a per-core one.

Two broad families of solutions dominate. In the snooping family, all caches that
might hold a line share a bus or a crossbar and "snoop" each other's traffic. When
B broadcasts a write, A's controller snoops it and invalidates or updates its own
copy. Snooping is simple and scales well within a single coherence domain, but it
is fundamentally broadcast-bound: the shared medium becomes the bottleneck as core
count grows, which is why large machines partition into domains and route across
them with directory-based protocols. In the directory family, a centralized (or
sharded) directory tracks, for every line, which remote holders exist and in what
state. Writes are sent as directed messages to the exact holders rather than
broadcast to everyone. This scales to many domains and to physical distribution,
at the cost of latency — you must round-trip to the directory before a write can
be guaranteed globally visible, and the directory is a concurrency hotspot that
must be sharded.

The state machines that implement these solutions are the same idea wearing
different clothes. The classic MESI protocol marks each line Modified, Exclusive,
Shared, or Invalid. Modified means the line is dirty and unique locally; it must
be written back before someone else can read it. Exclusive means clean and unique;
it can become Modified locally with no broadcast. Shared means others may have
clean copies; a local write must first evict them, typically with an invalidate
broadcast that flips their states to Invalid. Invalid means no usable copy. Every
cache coherence protocol is, at its heart, a way of moving lines along these
states while ensuring that exactly one copy can be dirty at a time and that every
reader either sees the latest write or is blocked until it does.

The ordering question is what coherence actually guarantees. A common
misconception is that coherence implies global ordering of all writes. It does
not; it guarantees per-line ordering: writes to a single line are seen in a
consistent order by all agents, and a reader of that line always observes the
most recent write to it. Writes to different lines are generally NOT globally
ordered by coherence alone — that is the job of the memory model and its
release/acquire semantics, barriers, and atomics. Confusing the two is the root
of most bugs attributed to "incoherent" hardware. Coherence keeps one line
consistent; memory ordering keeps the sequence of operations meaningful.

Write-back versus write-through is the central policy tradeoff. Write-back lets a
write complete by updating only the local cache, which is fast and low-bandwidth,
but it creates dirty copies that must eventually be flushed, and it is what makes
coherence necessary in the first place. Write-through writes to the next level on
every write, so there is less dirtiness to track but far more traffic. Most
processor caches use write-back precisely because the bandwidth it saves is worth
the coherence complexity. The coherence protocol is the tax you pay for that
saving.

Modern complications layer on top of this clean picture. Virtual caching introduces
aliasing: two virtual addresses can map to one physical line, and two caches can
hold the same physical data under different virtual tags, so snooping by virtual
address misses. Solutions such as physically tagged caches or directory entries
keyed on physical address exist mainly to defeat aliasing. Spread across sockets
and NUMA nodes, the single coherence domain becomes multiple domains connected by
a fabric, and the directory replaces the bus. In GPUs and accelerators, coherence
may be relaxed deliberately — hardware coherence is optional and software manages
explicit flush/invalidate — because the latency of hardware coherence does not
pay for the access patterns those workloads exhibit.

At the distributed-systems layer the same tension reappears under different names:
"cache coherence" becomes replication consistency, and the MESI states become
read-replica freshness. The insight from hardware is that strong, automatic,
global coherence is expensive and latency-bound, that per-object/per-line ordering
is cheap and usually all you need, and that most real systems buy performance by
weakening global guarantees while preserving local visibility and per-item
consistency. Whenever you design a caching tier, ask the same question hardware
engineers asked a half century ago: which lines must be strictly coherent, and
which can tolerate eventual consistency? Answer that, and most of the difficulty
is already gone.

## A1

ADR-0003: Field-Level Server-Authoritative Merge with an Append-Only Change Log

Context
We ship an offline-first mobile app used by field technicians who record jobs.
Each job record is owned by exactly one technician, and the backend enforces
ownership at assignment time, so we never have two technicians legitimately
editing the same record simultaneously. A technician may use two devices (phone
and tablet) and may edit the same record from both while offline; devices can be
offline for up to 72 hours. A record is a flat set of about 40 fields (text,
numbers, enums, timestamps, and a list of photo references; photos upload
separately). The binding constraint is regulatory: every field change must be
attributable to a named person with a server-assigned timestamp, and the stored
change history must be human-readable during an audit with no tooling. We have
three engineers (two mobile, one backend), no platform team, and a Postgres 16
REST backend.

Decision
We will use server-authoritative, per-field last-write-wins merge on write, backed
by an append-only, server-timestamped change log. Client devices keep the full
record locally and edit fields independently while offline. On reconnect, the
device uploads only the fields it changed since its last successful sync; the
server applies each field change, stamps it with the technician identity and a
server timestamp, appends an immutable row to the change log, and resolves
conflicts between the two devices by field. Per-field winners are written back to
the record. We reject a CRDT library and full record-level optimistic concurrency
with manual conflict resolution.

Why per-field server-authoritative merge
Because ownership is exclusive, conflicts are narrow: they only ever arise from a
single technician editing one record on two devices. That is a small, well-defined
conflict set, which makes heavy machinery unnecessary. Per-field merge keeps the
semantics obvious: for each field, the last write (by a server-assigned sequence)
wins, and every lost and winning write is recorded. This gives us exactly the two
regulatory properties we need — attribution and an auditable, human-readable
history — without inventing merge semantics that a regulator would have to trust.

Why an append-only change log
The change log is the audit system of record. Each row is (record, field, old
value, new value, technician_id, server_timestamp, write_sequence) and is never
modified or deleted. This satisfies "attributable to a named person with a
server-assigned timestamp" directly, and "human-readable during an audit without
tooling" because the log is a plain, ordered, immutable list of what changed,
when, and by whom. A flat append log in Postgres is trivial to read with psql,
export to CSV, or present in an audit UI, and it degrades gracefully.

Why we rejected the alternatives
A CRDT library would give us automatic, conflict-free convergence, but our fields
are heterogeneous (text, enums, timestamps, photo lists) with no natural CRDT
per type, we would have to hand-build a CRDT per field, and — critically — CRDT
convergence is not attributable: it does not record who changed what or assign a
server timestamp to each field edit, so it does not satisfy the regulatory
requirement without an additional log anyway. We would be building a CRDT and a
change log, and paying for both. Full record-level optimistic concurrency with
manual conflict resolution would force the technician to resolve conflicts, which
is unacceptable in a regulated field workflow where records must be complete and
correct on sync; it also makes the per-field history messy. Server-authoritative
per-field merge keeps resolution off the user and keeps one clear owner of truth.

Why server, not client, is the authority
Attribution and timestamps must be issued by a party the technician cannot
impersonate. If the client assigned timestamps, a device could replay or
fabricate history. The server is the only trustworthy issuer of the timestamp and
the write sequence that orders conflicting field writes. The client is a cache of
the record plus a queue of pending field edits; the server is the source of truth.

Consequences
Strengths: meets both regulatory requirements with a straightforward model;
conflict resolution is deterministic and offline-testable; the change log doubles
as the audit export; Postgres gives us durability and simple querying. Costs: we
must track per-field "last write" metadata on the device (a small per-field
vector clock or last-synced snapshot); the server needs a write path that applies
field edits atomically and appends to the log under the same transaction; 72-hour
offline windows mean large pending queues, so we must bound and surface sync
conflicts. Trade-offs we accept: last-write-wins can silently drop a concurrent
field edit, but because the dropped write is preserved in the change log with its
attribution, the regulator can see exactly what happened — we trade automatic
value-convergence for complete, attributable history, which is what is required.

What would change this decision
If the regulatory requirement relaxed to "best-effort history," a CRDT or
client-side merge would become attractive for smoother convergence. If records
became collaboratively editable by multiple owners, per-field LWW would be
insufficient and we would move toward versioned, per-field vectors or a richer
conflict framework. If offline windows grew to weeks or edits became highly
structured, we would reconsider a purpose-built sync protocol. As it stands, the
narrow conflict shape and the hard audit requirement make server-authoritative
per-field merge with an append-only log the right call.

## A2

Design: Order Service Write Path (three regions: Frankfurt, Virginia, Singapore)

Assumptions (numbered; held throughout unless explicitly revised)
1. Each customer is owned by exactly one "home region," and all of that
   customer's orders live in that region. Orders are partitioned by customer; a
   customer never moves regions. This makes partition-routing deterministic.
2. "Never lost, once accepted" means an order that receives an acceptance
   response must survive any single-region failure and be durably persisted. An
   order that fails to get an acceptance response may be retried; we do not
   guarantee it will not be created twice, so order creation must be idempotent on
   a client-provided idempotency key.
3. The 80 ms p99 budget is measured at the API edge inside the customer's home
   region. Cross-region calls are only permissible if they fit the budget.
4. Writes are accepted only in the customer's home region; reads for the owning
   region are local, and reads from other regions are eventually consistent.
5. Inter-region replication is asynchronous and ordered per partition (per
   customer key), implemented by shipping the order's write-ahead log / commit
   entries to the other regions, not by synchronous RPC.
6. The three regions have independent failure domains; a region can be isolated
   (network partition) for seconds to minutes. During isolation the home region
   keeps accepting writes if it is the home region; a non-home region serving
   cross-region reads serves stale data.
7. Clocks are synchronized to within a few milliseconds (NTP); we use logical
   sequence numbers, not wall-clock, for ordering.
8. "Once accepted, never lost" does not require cross-region linearizability; it
   requires durability plus reliable asynchronous delivery to the other regions.

Design
Partitioning. The order space is hashed by customer id into a home region. All
writes and the authoritative copy for a customer live in that region; the region
owns a contiguous range of the hash space and is the single writer for it. We
replicate each partition to the other two regions for local read availability and
disaster recovery, using asynchronous, per-key ordered replication.

Write path. On order creation the API edge routes to the customer's home region
(consistent hashing means the edge can compute the owner from the customer id
without a lookup, avoiding a routing round-trip). The home-region writer does, in
order: (a) validate the request and the idempotency key; (b) append the order to
the local write-ahead log and fsync; (c) only after the fsync completes, return
acceptance to the client; (d) stream the entry to the other two regions
asynchronously over the ordered replication channel. Because acceptance is returned
after durable local append but before cross-region propagation, the 80 ms budget
is met by local disk latency, not inter-region RTT. The idempotency key makes
duplicate submissions (client retries after a timeout) converge to one order.

Reads. Reads in the home region are served from the local primary and are
consistent. Cross-region reads are served from the local replica and are
eventually consistent; the API contract states that status reads from a non-home
region may lag by the replication delay. This keeps cross-region reads fast (local
RTT) at the cost of bounded staleness, which is acceptable for order status.

Failure behaviour. If the home region is isolated, it continues to accept and
durable-accept writes for its customers (it remains the single writer), so no
accepted order is lost; the other regions simply stop receiving updates until the
partition heals, after which replication catches up in key order. If a non-home
region is isolated, its local reads go read-through to the primary on the next
read or serve cached-stale data; no writes are lost because it was not the writer.
We explicitly do NOT fail writes over a partition: failing an accepted order to
"protect consistency" would violate the never-lost constraint, so availability of
the home writer is prioritized over cross-region consistency. On heal, ordered
replay reconciles replicas deterministically.

API contract. Order creation: POST /orders with a client-generated idempotency
key; returns 202 Accepted with an order id and a monotonic sequence number on
durable acceptance, or 409/409-on-duplicate on a known key, or 422 on validation.
Status: GET /orders/{id} returns the order and a region tag plus a "staleness
bound" (max age of the served copy) so clients know whether a read was local or
cross-region. Creation is idempotent on the key; status is eventually consistent
off-home.

Revisions to assumptions. None changed. Assumption 3 was the linchpin: by placing
the budget at the edge within the home region, local fsync — not inter-region
round-trips — fits 80 ms, which is what makes the durable-but-not-synchronously
replicated design correct. If the budget were measured across regions (assumption
3 relaxed), we would have to reject writes during cross-region commit and lose the
latency target, so we hold it.

## A3

Design review: write-through cache with delete-on-write and fire-and-forget deletes

The proposal (Redis on the read path, load-through on miss with a 10-minute TTL,
delete-on-write, fire-and-forget deletes) is a very common pattern and is fine as
a performance optimization, but three parts of it are wrong as stated, and two of
them are correctness bugs, not performance issues.

1. Delete-on-write is the right instinct but the reasoning is wrong. Deleting on
   write (rather than updating) is indeed the recommended Redis pattern, but not
   "so we never have to worry about the DB and Redis disagreeing about the value."
   It is recommended because a delete is a single, cheap, low-contentency
   operation, whereas an update races the in-flight reads that already loaded the
   old value. Deletion is correct, but the guarantee it provides is narrower: it
   guarantees no STALE read after the delete completes, not that the cache and DB
   always agree. You must still accept the window between a write's DB commit and
   the completion of its delete.

2. Fire-and-forget deletes are the actual bug. "Deletes are fire-and-forget
   because the TTL is a backstop anyway" is incorrect reasoning and will produce
   stale reads. The TTL only bounds how long a STALE (pre-write) value can live
   after a MISS; it does nothing to guarantee that a value written to the cache on
   a miss reflects the latest DB write. If the delete is lost, the next miss loads
   the old value from the DB and re-populates Redis, and that value now lives for a
   fresh 10 minutes. The failure modes that lose a fire-and-forget delete are real
   and common: Redis restart/flush, the delete landing after a concurrent re-populate
   (the classic lost-update-against-cache race), network drops, or OOM eviction of
   the key between write and delete. Each of them permanently serves stale data for
   up to a TTL. So fire-and-forget is not acceptable where read-your-writes
   consistency matters. Make delete-at-least-once: retry the delete with bounded
   attempts, and ideally idempotent (a delete is naturally idempotent). Even better,
   make it exactly-once relative to re-population by versioning: store a version or
   timestamp with the cached value and invalidate on write using a compare-and-set
   style check, or publish the delete on the same commit log as the write so they
   are ordered and neither is lost.

3. The TTL backstop means the design has no read-your-writes guarantee by design.
   If any caller (or the same user) expects to see their own write on a subsequent
   read, this design can violate it for up to 10 minutes after a delete is lost.
   Decide explicitly whether read-your-writes is required. If yes, the 10-minute
   TTL is far too long and fire-and-forget delete is the failure point; shorten the
   TTL or, better, drop the TTL as the correctness mechanism and rely on reliable
   deletes, keeping TTL only as a memory-safety net for edge cases.

Other things I would change:
- Cache stampede / thundering herd: on a miss under concurrency, many threads will
  reload the same row simultaneously. Add single-flight locking (or a short fresh
  TTL / jittered TTL) so one loader wins and others wait or serve a slightly stale
  copy.
- What gets cached: a product catalogue is largely static and reads-heavy, which
  is a good fit. But if any "writes" are frequent or the working set is large,
  10-minute TTLs multiply memory. Consider per-key TTL or a size-bounded eviction
  (LRU/LFU) rather than a flat 10 minutes for every key.
- Consistency class should be documented: state clearly that the cache is
  eventually consistent with up-to-10-minute staleness and that deletes are
  best-effort-until-fixed. Consumers (e.g., an order-total or pricing display)
  that must not show stale data should read through to the DB or bypass the cache.
- Observability: emit delete-success/delete-retry metrics and a "cache hit with
  age" metric so stale-read windows are visible.

Verdict: keep the architecture (Redis read-through with delete-on-write), but
replace fire-and-forget deletes with reliable, retried deletes (at-least-once,
ideally ordered with the write), remove the mistaken claim that TTL makes deletes
safe, and add single-flight on miss. With those changes it is a sound, standard
design; as written it can serve stale data indefinitely after a lost delete.

## L1

(a) Lock tier ordering (from `corelib/locking.py`): registry < catalog < index <
metrics (the `TIERS` tuple, so `TIER_RANK` is registry=0, catalog=1, index=2,

order — holding a higher tier, it must not acquire a lower one (it must release
the higher first), and this applies transitively across calls into helpers.
Reacquiring the same tier is permitted because the tier locks are reentrant.

(b) Helpers whose name ends in `_locked` assume the caller already holds the tier
named in the function's docstring and take no lock of their own. Two examples in

- bundle → catalog

- digest → metrics

(b) Ceiling: `HARD_MEMORY_BUDGET = 2 << 30` = 2,147,483,648 bytes (2 GiB), stated
in `corelib/limits.py`. The commit of each *enabled* pool is
`workers * prefetch_depth * BUFFER_BYTES` with `BUFFER_BYTES = 1 << 20` (1 MiB),
and the sum over enabled pools must stay strictly under the budget (the function
`within_budget` is `total_commit < HARD_MEMORY_BUDGET`). Pools with
`enabled=False` are never started and commit nothing.

Pools (from `ingest/pool_*.py`):

- parse_fanout: workers=128, prefetch_depth=3, enabled=True → 128·3 = 384 MiB

Enabled total: 384 + 384 + 512 + 960 = 2,240 MiB = 2,348,810,240 bytes.
Ceiling: 2,048 MiB = 2,147,483,648 bytes.
Breach: 2,240 − 2,048 = 192 MiB = 201,326,592 bytes over the ceiling
(`within_budget(2,348,810,240)` is `False`).
