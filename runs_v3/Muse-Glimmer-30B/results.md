## T2
Cache coherence is the property that ensures that when multiple processors or cores share a memory system, all accesses to a shared location appear to be performed in a consistent order and that each processor observes the most recent value written by any processor. The problem arises because modern processors are built around private caches that sit between the cores and the shared memory hierarchy. Caches improve performance by reducing latency and bandwidth pressure, but they introduce the risk that a core may operate on a stale copy of data while another core has already updated the authoritative copy. Without a coherence protocol, software could see torn writes, lost updates, or order inversions that break correctness of concurrent programs.

The earliest coherence models were based on snooping, in which each cache monitors the shared bus for transactions that might affect its lines. When a core issues a read or write, the transaction is broadcast to all caches. Listeners invalidate or supply data as required by the protocol. Snooping protocols such as MSI, MESI, and MOESI formalize the states a line can occupy: Modified, Exclusive, Shared, Invalid, and the owner states used to optimize write sharing. The protocol guarantees that at most one cache can hold a Modified copy, and that any Shared copy is consistent with memory. Snooping scales well on a single shared bus but becomes impractical as core counts rise because bus bandwidth and electrical fan-out limit the number of participants. The broadcast nature also creates coherence traffic that grows with the number of cores.

Directory-based protocols replace the broadcast with a directory that tracks which caches hold copies of each line. The directory records sharers and coordinates invalidations or supplies using point-to-point messages. This approach reduces unnecessary traffic and scales to larger systems with multiple sockets and NUMA domains. Directories can be centralized or distributed, and they can be combined with a home agent that owns a region of memory. The trade-off is additional metadata, higher latency for some operations, and more complex software for handling directory updates during migration.

Coherence is typically implemented at the hardware level, but the programming model exposed to software is defined by memory consistency models. Sequential consistency provides the strongest guarantee: all operations appear to execute in a single total order that respects per-processor program order. Most modern architectures relax this to total store order or relaxed consistency to allow more parallelism and to hide latency. The hardware still provides coherence, meaning the value observed is always the latest write, but the order in which independent writes become visible may differ across cores. Programmers must therefore reason about both coherence and consistency.

False sharing is a common performance pathology caused by coherence. When two cores access different words that happen to reside in the same cache line, the protocol will ping-pong the line between caches even though the data are logically independent. Padding and data layout changes are standard mitigations. Another issue is coherence traffic amplification from write-through caches or from software that uses atomic read-modify-write primitives excessively. Prefetching and non-temporal stores can reduce pressure on the coherence domain.

In distributed shared memory systems, coherence is extended across nodes with protocols that combine directory information with network messages. The latency of remote invalidations makes coherence expensive, so systems often rely on software coherence, explicit invalidation, or partitioned data. The rise of heterogeneous computing adds further complexity, as accelerators may have their own caches and different coherence domains. Cache-coherent interconnects such as AMD Infinity Fabric and Intel UPI provide hardware support for multi-socket coherence, while CXL extends coherence to devices.

Verification of coherence is difficult because the state space explodes with core count and line states. Formal models and model checkers are used to prove protocol correctness, and simulation is used to explore performance trade-offs. The choice of protocol, line size, and invalidation policy affects both correctness and efficiency. Cache coherence remains a central concern for system designers because it sits at the intersection of correctness, performance, and energy. As systems grow more parallel and more heterogeneous, the tension between strong coherence guarantees and scalability continues to drive research into new protocols, relaxed models, and software-hardware co-design.

## A3
The proposed read-through cache with delete-on-write and fire-and-forget delete is risky.

Problems:
Cache stampede on miss: multiple readers miss simultaneously and all load from Postgres. No request coalescing.
Delete race: write updates DB then deletes Redis key asynchronously. A read arriving between DB commit and delete sees stale data from Redis. TTL is a backstop but window exists.
Fire-and-forget delete can be lost, leaving stale data until TTL expires. 10-minute TTL means stale reads for up to 10 minutes.
Delete does not guarantee invalidation across replicas; replication lag can resurrect stale key.
No write-through consistency for strong read-after-write.

Changes:
Use write-through or write-invalidate with synchronous delete and confirm. Better: update cache on write with same value as DB, using a transactional outbox or CDC to keep cache consistent.
Add request coalescing on cache miss to avoid thundering herd.
Use versioned keys or CAS to avoid lost updates.
Make delete synchronous and retry on failure; consider using Redis pipeline with DB transaction.
Reduce TTL and add proactive invalidation.
For strong consistency, serve reads from DB for recent writes using a short write buffer or read-your-writes token.

(b) Helper naming convention: functions ending in _locked assume caller already holds the tier named in docstring and take no lock themselves. Examples: _bump_generation_locked in svc/catalog_ops.py, _write_shard_locked in svc/reindex_07.py.

(c) Families and lock tier:
bundle_00-25: catalog
cache_00-25: catalog
digest_00-25: metrics
dispatch_00-25: registry
ledger_00-25: registry
probe_00-25: metrics
router_00-25: registry
session_00-25: registry
stream_00-25: index
tracker_00-25: catalog

(d) ascending("metrics","catalog") returns False. TIER_RANK metrics=3, catalog=1, 3 <=1 is False, so acquiring metrics then catalog is descending and violates hierarchy.
