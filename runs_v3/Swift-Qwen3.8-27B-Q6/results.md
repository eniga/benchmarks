## T2
Cache coherence is the discipline of keeping multiple copies of the same data consistent with one another. It appears at two scales: inside a processor, where every core keeps a private cache of main memory, and across a distributed system, where every replica keeps its own copy of shared state. This essay addresses the single-processor problem, the older and more precisely defined one.

The basic unit of coherence is the cache line, typically sixty-four bytes. Each core's cache holds lines in one of several states, most famously the Modified, Exclusive, Shared and Invalid states of the MESI protocol. A line in the Shared state exists in several caches with the same value. A core that wants to write a line that is Shared elsewhere must first obtain exclusive ownership: it broadcasts an invalidate, the other caches drop their copies, and only then may the writer modify its line. A core that reads a line held Modified elsewhere must first fetch the newest value. Invalidate-on-write and newest-value-on-read are the entire engine of coherence.

Why is this necessary at all? Because caches exist for speed. A core can read its L1 cache in a single cycle, but main memory takes tens of cycles. If each core simply wrote into its own copy, the machine would silently diverge: one core's store would be invisible to another, and programs relying on shared memory, such as a lock variable, would break. Coherence restores the illusion of a single address space: every core sees its own writes immediately, and eventually sees every other core's writes, in an order that respects the programmer's memory model.

The hardware cost is real: every cache must watch the interconnect for transactions that mention its lines, a process called snooping. In a modern chip, coherence traffic itself can dominate power consumption. Designers therefore trade sophistication for efficiency. Directory-based protocols replace broadcast snooping with a central directory that tracks which cores hold which lines, trading memory for bandwidth. Non-inclusive caches reduce the pressure of keeping copies of copies. Prefetching adds further complexity, because the hardware guesses at future coherence events and must be able to cancel its guesses.

Coherence is not the same thing as consistency. Coherence is a property of the hardware: it guarantees that stores to the same address are observed in a single total order by all cores. Consistency is a property of the memory model that the compiler and hardware jointly implement for the programmer. The x86 model is strong: a store becomes visible to other cores in program order, and loads are not reordered past stores. The ARM and RISC-V models are weaker: they permit reorderings that the coherence protocol faithfully delivers, and the programmer must insert explicit barriers when a stronger order is needed. The protocol does not care which model is in force; it guarantees only that the order it produces is a valid one.

The protocol's guarantee is a total order on cache-line transactions, but the memory model decides which of those orders the programmer may rely on. A lock built with compare-and-swap is safe on x86 without a fence because the model promises store-load ordering; on ARM the same lock needs an acquire barrier on the load and a release barrier on the store. The hardware makes both work; the model decides the cost.

Three failure modes illustrate what happens when the discipline slips. First, false sharing: two cores write to different variables that happen to sit on the same line. The protocol cannot see intent; it sees only addresses. The line ping-pongs between cores, each write invalidating the other's copy, and throughput collapses by an order of magnitude. The fix is padding, a purely organizational change the hardware rewards. Second, benign races that stop being benign: a flag checked without a barrier may be hoisted above the initialization it guards, and the protocol faithfully delivers the flag before the data it announces. Third, speculative execution: the processor may execute a store speculatively and discard it, but the coherence traffic it generated is real and visible, which is why attacks such as Spectre could read data across security boundaries.

The deeper lesson is that coherence is a contract between hardware and software, and the hardware's side is deliberately minimal. The protocol guarantees a total order of line transfers; everything above that, the ordering of operations, the visibility of initialization, the atomicity of compound actions, is the memory model's job. Engineers who understand only the hardware picture write code correct on one architecture and broken on another; engineers who understand only the model picture are surprised by false sharing and the power cost of their fences.

At the distributed scale, the same ideas reappear under new names: a write invalidating replicas is an invalidate message; a directory protocol is a metadata service; the memory model is the consistency level a database offers, from read-your-writes to linearizability. The single-processor problem was solved by making the order of operations explicit and separating the guarantee the hardware makes from the guarantee the programmer needs. Distributed systems are still negotiating that same separation, and they fail in the same places: by assuming a stronger order than the protocol provides, or by paying for one they do not need.

Cache coherence, then, is not a hardware curiosity. It is the engineering of shared memory itself: a total order on copies, a minimal hardware guarantee, a memory model on top, and a list of failure modes that punishes anyone who confuses the layers.

## A1
# ADR: Data synchronisation strategy for the offline-first field app

### Status

Accepted.

### Context

Field technicians use an offline-first mobile app (phone and tablet) to edit job records. Constraints:

- Each record is owned by exactly one technician, enforced by the backend at assignment time; two technicians never edit the same record.
- One technician may use two devices and may edit the same record from both while offline.
- Devices are offline for up to 72 hours.
- A record is a flat set of about 40 independent fields (text, numbers, enums, timestamps) plus photo references; photos upload separately.
- Regulator: every field change must be attributable to a named person with a server-assigned timestamp, and the stored change history must be human-readable during an audit without tooling.
- Team: two mobile engineers, one backend engineer. No platform team.
- Backend: Postgres 16 behind a REST API.

The decision: the synchronisation strategy for offline record edits.

### Options considered

### Option 1: CRDT library

Adopt a CRDT library so that concurrent edits from the two devices merge deterministically without a coordinator.

Pros: convergence is guaranteed by construction; no server round-trip to resolve conflicts; well-studied semantics.

Cons: the actual conflict surface is tiny: ownership is exclusive, so the only concurrency is between a technician's own two devices editing flat, independent fields. CRDTs earn their complexity in collaborative editing of shared structured content; for 40 independent scalar fields, per-field last-write-wins registers are already a CRDT, and a full library buys merge machinery we do not need. Worse: CRDT merge metadata is not human-readable, colliding with the regulator's auditability requirement, and the library does not by itself provide the attribution and server-timestamping the regulator requires.

### Option 2: Server-authoritative last-write-wins per field, with an append-only change log

Each field is an independent last-writer-wins register. The server is the single authority. Every edit from any device is recorded as an immutable change event: record id, field, old and new value, technician id, device id, device-local time, and a server-assigned sequence number and timestamp stamped at ingestion. The server applies events per field in deterministic order, resolving conflicts with last-write-wins. The change log itself is the audit trail.

Pros: the conflict model matches the domain exactly (one owner, independent fields). The append-only log is trivially human-readable, directly satisfies the attribution and server-timestamp requirements, and doubles as the audit history. Deterministic server-side ordering removes all client-side merge logic from the mobile code, and Postgres is sufficient: a `change_log` table plus a current-state table, both keyed by record.

Cons: last-write-wins can silently discard a field value (the tablet sets "status" while the 72-hour-stale phone overwrites it with an older value). Mitigations: per-field ordering by a hybrid logical clock (device time + logical counter + device id tie-break), so the later real-world edit wins deterministically; the discarded value is never lost, because both events remain in the log. The server must be available for sync; 72-hour offline windows are fine because edits queue locally and sync is a batch of idempotent events.

### Option 3: Record-level optimistic concurrency with manual conflict resolution

The client sends the whole record with a version number; the server rejects stale writes (409) and the user resolves conflicts field by field in the UI.

Pros: no silent data loss; the user is in control; no new infrastructure.

Cons: with 72-hour offline windows and two devices, conflicts are the norm, not the exception. Manual resolution in the field is poor UX and a compliance risk: a record stuck in "conflict" state may be edited with a stale value, and the resolution itself needs attribution and timestamps, doubling the audit surface. Record-level granularity is coarser than the domain: two devices editing different fields of the same record would conflict needlessly, and the merge UI is non-trivial work for two mobile engineers who already own offline storage.

### Decision

Adopt Option 2: server-authoritative per-field last-write-wins with an append-only change log.

The ownership model removes the hard part (multi-writer collaboration), and the flat record shape makes per-field granularity natural. Option 2 is the only option whose audit trail is the primary data structure rather than a by-product, decisive given the regulator requirement. The known weakness of last-write-wins (silent discard) is contained by deterministic hybrid-logical-clock ordering: every discarded value remains visible in the log.

### Consequences

- Backend: add `change_log` (append-only, one row per field change, server-assigned `seq` and `server_ts`) and a current-state table; the sync endpoint accepts idempotent, batched events; per-field LWW apply by (hlc, device_id).
- Mobile: local outbox of change events; sync is a batch upload plus a state pull; no merge UI, no CRDT dependency.
- Attribution and audit are satisfied by construction; the log is readable without tooling.
- Photos stay out of the change log (separate upload with references), keeping the log small and readable.
- We accept that a stale device can overwrite a newer field value; the log makes this visible.

### What would change the decision

- If records ever become shared between technicians, Option 1 (a real CRDT) or Option 3 becomes preferable.
- If the regulator required that no field value be overwritten without explicit human confirmation, Option 2's LWW would be insufficient.
- If fields developed cross-field invariants, per-field independence would break and record-level concurrency (Option 3) would be needed.
- If offline windows shrank to minutes, a simpler write-through design would suffice.

## A2
# Write path for a three-region order service

### Assumptions

1. An order belongs to exactly one customer, and each customer has exactly one home region (Frankfurt, Virginia, or Singapore). No order spans regions.
2. The p99 80 ms write-latency budget is measured at the API edge of the region that accepts the write, from request receipt to the acceptance response.
3. "Once accepted, an order must never be lost" means: after the API returns an acceptance, the order survives any single-region failure and is eventually visible in all three regions.
4. Home-region reads are strongly consistent with local writes. Non-home-region reads are served from asynchronously replicated copies and may lag by seconds; the API discloses staleness.
5. Inter-region replication is asynchronous, log-based (CDC from the home region's write log), at-least-once, with idempotent apply and per-order sequence numbers.
6. Order identifiers are globally unique (region-scoped ULIDs), so replicated orders never collide.
7. A region being "isolated" means it cannot reach the other two regions but continues to serve its own traffic.
8. The three regions run identical service versions; deployments are coordinated and canary-rolled.
9. The write path may use a local durable log (for example Kafka with min.insync.replicas=2, acks=all) inside the home region; a local log append is assumed to complete in single-digit milliseconds at p99.
10. Cross-region administrative reads (support, finance) have no latency budget and may go to the home region.

### Data partitioning

Partitioning is by customer, and the customer's home region is fixed at account creation and stored in a small, globally replicated routing table (customer id, home region, status). The routing table is the only globally writable state; it changes rarely (a customer re-homing is a planned migration, not a runtime event) and is replicated synchronously to all three regions because it is small and read on every request.

Each region owns the full write path for the customers homed there. Order data lives in per-region Postgres, partitioned by customer id, so a customer's orders are contiguous and a single customer's writes are serialized by one region. There is no cross-region write ownership: a Virginia-homed customer's orders are only ever written in Virginia. This is what makes the failure behaviour simple, and it is the direct consequence of assumption 1.

### The write path

The write path is fully local to the home region; no inter-region round trip occurs on the hot path, which is the only way the 80 ms budget survives the 90–220 ms inter-region RTTs.

1. The edge (regional API gateway) resolves the customer's home region from the routing table. If the request arrived in a non-home region, it is redirected to the home region's edge; the caller retries there. (Assumption 10's administrative paths are the exception.)
2. The API validates the payload and requires an idempotency key scoped to the customer. A replayed key returns the original acceptance; a key reused with a different payload returns 409.
3. The API assigns the order id and appends the order event to the region's local durable log (one topic per region, partitioned by customer id, min.insync.replicas=2, acks=all). The append is the commit point.
4. The API returns 202 with the order id immediately after the log append. At p99 this is validation plus a local log append, comfortably inside 80 ms (assumption 9).
5. A projector, running in the same region, consumes the log and materializes orders into Postgres (partitioned by customer id). Because the log is partitioned by customer, a customer's events are applied in order by a single projector partition, and the per-customer sequence number makes apply idempotent and reorder-safe.

Durability argument: the order is durable the moment the log append is acknowledged by a quorum of local log replicas. A projector crash, a database failure, or even a full region failure cannot lose an accepted order: in the first two cases the log is replayed; in the third, the log ships with the region and is replicated to the other regions as soon as connectivity returns.

### How reads are served

Home-region reads go straight to the local Postgres and are strongly consistent: a customer in Virginia reads their orders from Virginia's database, which is the only writer. Non-home-region reads (for example a support console in Frankfurt viewing a Singapore customer) are served from a local read replica fed by CDC replication of the home region's log. The replica is a projection, never a writer. The read API includes the replica's lag; callers that need current state for a non-home customer are told to read the home region (assumptions 4 and 10). Because replication is log-based and per-customer ordered, a replica can never show a customer's orders out of sequence; it can only be behind.

### Failure behaviour when a region is isolated

Because only the home region writes, isolation cannot create divergent writes: there is no second writer to diverge from.

- Isolated home region: it continues to accept writes and serve home reads normally. Its outbound replication buffers in the local log; nothing is lost. On reconnection, the log tail is shipped and applied idempotently in the other regions. The isolated region's own state is authoritative throughout.
- Isolated non-home region: it serves reads from its last-replicated state, flagged as stale with the measured lag. Writes for customers homed elsewhere are redirected (and will fail if the home region is also unreachable); the isolated region simply cannot accept them, which is correct because it never had write authority.
- If the home region fails permanently (not just isolated), the routing table is updated in a deliberate, operator-driven re-home: the customer's log tail is shipped to the new home region, which adopts the sequence numbers, and the routing table flips once the new home has caught up. Orders remain durable because the log moved with the customer. This is a rare, planned operation, not a runtime path.

The key property: at no point do two regions believe they own the same customer's writes, so there is no split-brain write state to reconcile.

### Public API contract

Order creation:

- `POST /v1/orders` with headers `Idempotency-Key` (required) and the customer's credentials. Body: the order payload.
- `202 Accepted` with `{ "order_id": "...", "status": "accepted", "region": "virginia" }` once the log append is durable. This is the acceptance point of the never-lost guarantee.
- `409 Conflict` if the idempotency key was used with a different payload.
- `422 Unprocessable Entity` for validation failures (before any idempotency key is consumed).
- `404 Not Found` if the customer is not homed to this region (the edge normally redirects; this is the fallback).

Order status:

- `GET /v1/orders/{order_id}` returns `{ "order_id", "status", "version", "region", "replica_lag_ms" }`. `version` is the per-order sequence number; `replica_lag_ms` is null for home-region reads.
- `status` is a monotonic enum: `accepted -> confirmed -> shipped -> delivered`, with `cancelled` reachable from `accepted` or `confirmed`. Transitions are recorded as log events, so a replica can never show a status "newer" than the home region has committed.
- `410 Gone` for orders older than the retention window.

Contract invariants: an order id is globally unique and immutable; the same idempotency key always returns the same order; `version` strictly increases; a `202` response is the point of no return for durability (assumption 3).

### Summary of the trade

The design buys the 80 ms budget and the never-lost guarantee by making the home region the sole writer and by committing to a local durable log before responding. The price is that non-home reads are eventually consistent and that customer re-homing is a deliberate operational procedure. Both prices are explicit in the API contract, so callers can reason about them.

## A3
Keep the overall shape (read-through cache-aside with delete-on-write is a standard, reasonable pattern), but the design as stated has several holes. In order of severity:

1. Fire-and-forget delete is the biggest one. If the delete fails (network blip, Redis outage, key too large), the stale value lives until the 10-minute TTL — up to ten minutes of serving the old row to every reader. "Redis is fast" is not a reliability argument; deletes fail at a small but nonzero rate, and nobody is watching. Make the delete a retried, monitored operation: retry with backoff a few times, then alert and fall back to a short-TTL overwrite. The claim "we never have to worry about the cache and the database disagreeing" is exactly what the fire-and-forget delete breaks.

2. Delete-after-write has a classic race even when the delete succeeds. Sequence: reader misses on key K and starts loading the old row from Postgres; writer commits the new row and deletes K; the reader finishes loading the old row and writes it into Redis. The cache now holds the stale value for up to the full TTL. Mitigations: delete before the write as well as after (double-delete, with a short delay on the second delete), or store a version/generation in the cached value and have the reader discard a write if the generation changed while it was loading, or simply shorten the TTL so the worst case is bounded by minutes, not ten.

3. Ten minutes is a long TTL for a catalogue. Staleness this long is a product decision, not a free default. Make the TTL configurable per key class, and consider probabilistic early expiration so a hot key does not always expire at the same instant.

4. Cache stampede on expiry. When a hot key expires, every concurrent reader misses and hammers Postgres with the same row. Add request coalescing (single-flight): the first miss loads the row, concurrent misses on the same key wait for it. Without this, the most popular products — exactly the ones you most want cached — cause the worst Postgres spikes.

5. Cache penetration for missing keys. Reads for non-existent catalogue ids miss every time and go straight to Postgres forever, because nothing is cached for a miss. Cache a short-TTL tombstone ("not found") for missing keys.

6. Redis failure mode is unspecified. If Redis is down, do reads fall through to Postgres (fail-open with rate limiting), or do they fail? The TTL backstop does nothing when Redis is unavailable. Define a circuit breaker that fails open to Postgres with a concurrency cap, and a path back.

7. The "delete keeps cache and DB agreeing" invariant only holds if every write goes through this one path. Bulk updates, backfills, admin tools and schema migrations that touch Postgres directly will leave stale cache entries. Enforce a single write path (or make the delete part of the transaction outbox), and version the cached value format so a deploy that changes the row shape flushes the cache.

8. No eviction or sizing policy is stated. An unbounded catalogue cache will eventually be evicted under memory pressure or OOM the box. Set maxmemory with LRU (or allkeys-lfu), namespace the keys, and size the cache for the hot set.

9. Observability. Track hit ratio, delete failures, and measured staleness; the whole design is a bet on small staleness and that bet is currently unmeasured.

Net: the architecture is fine; the reliability details are not. Retried-and-alerted deletes (ideally double-delete), single-flight loading, tombstones for misses, versioned values, a fail-open path, a shorter configurable TTL, and an eviction policy turn this from a plausible sketch into a design that will survive production.

```python
"""FIFO-fair connection pool with lazy idle expiry.

Invariants maintained:
  * The user-supplied ``factory`` and ``close`` callables are never invoked
    while the pool's internal lock is held.
  * A thread blocked waiting for a connection never holds the pool's lock.
  * Waiters are served strictly first-come-first-served: a late arrival can
    only create a new connection when no thread is waiting.
"""

from __future__ import annotations

import threading
import time
from collections import deque

__all__ = ["ConnectionPool"]


class ConnectionPool:
    def __init__(self, factory, close, max_size, idle_ttl=60.0, clock=time.monotonic):
        if max_size < 1:
            raise ValueError("max_size must be >= 1")
        self._factory = factory
        self._close = close
        self._max_size = max_size
        self._idle_ttl = idle_ttl
        self._clock = clock
        self._lock = threading.Lock()
        self._free: deque[tuple[object, float]] = deque()  # (conn, freed_at)
        self._waiters: deque[threading.Event] = deque()
        self._live = 0  # connections currently existing (held or free)

    # -- public API ---------------------------------------------------------

    def acquire(self, timeout=None):
        """Hand out a connection or raise TimeoutError after ``timeout`` seconds."""
        deadline = None if timeout is None else self._clock() + timeout
        while True:
            expired = []
            event = None
            creating = False
            conn = None
            with self._lock:
                # Serve the oldest free connection; drop idle-expired ones.
                while self._free:
                    candidate, freed_at = self._free.popleft()
                    if self._clock() - freed_at <= self._idle_ttl:
                        conn = candidate
                        break
                    expired.append(candidate)
                    self._live -= 1  # it is about to be destroyed
                if conn is None:
                    if self._live < self._max_size and not self._waiters:
                        # Only a non-waiting arrival may grow the pool, so a
                        # late arrival can never jump ahead of an older waiter.
                        self._live += 1
                        creating = True
                    else:
                        event = threading.Event()
                        self._waiters.append(event)
            for c in expired:
                self._close(c)  # no lock held
            if conn is not None:
                return conn
            if creating:
                return self._factory()  # no lock held
            # Block for a connection; no lock is held while waiting.
            if deadline is None:
                event.wait()
            else:
                remaining = deadline - self._clock()
                if remaining <= 0 or not event.wait(remaining):
                    with self._lock:
                        try:
                            self._waiters.remove(event)
                        except ValueError:
                            pass  # a release already handed us a slot
                    raise TimeoutError("timed out acquiring a connection")

    def release(self, conn):
        """Return ``conn`` to the pool, waking the oldest waiter if any."""
        event = None
        with self._lock:
            self._free.append((conn, self._clock()))
            if self._waiters:
                event = self._waiters.popleft()
        if event is not None:
            event.set()  # no lock held
```

Design notes:

- FIFO fairness: waiters are a `deque` of `Event`s; `release` pops the leftmost (oldest) waiter and sets its event. A new arrival may grow the pool only when the waiter queue is empty (`self._live < self._max_size and not self._waiters`), so a late arrival can never take a connection ahead of a thread that has been waiting longer.
- Invariants: `factory` and `close` are invoked only after the `with self._lock:` block has exited, and `event.wait()` (the blocked state) is also outside the lock. The tests verify this directly by asserting `pool._lock.locked()` is False inside the factory/close callables and while a thread is blocked in `acquire`.
- Idle expiry: free connections carry their free-since timestamp (monotonic clock); on the next acquire, entries older than 60 s (configurable `idle_ttl`, default 60.0) are closed outside the lock and discarded, and a replacement is created lazily by the same acquire. No background threads or timers.
- One failure found and fixed during the run: the first version decremented the live count only after closing the expired connection, so an acquire on an all-expired pool blocked and raised TimeoutError (the pool could not replace what it had just dropped). Fixed by decrementing the live count under the lock at the moment the connection is decided to be destroyed.

Why it accepted a project it should have rejected: in `visit`, the `if node in seen: return` check runs before the `if node in stack` cycle check. `seen` is global across the whole run and a node is added to it on entry, so when a cycle leads back to a node that is already in `seen`, the function returns silently instead of raising. The `stack` check can therefore only ever fire for a node that has never been seen, which is impossible on a cycle (the first node of the cycle is always already in `seen`). Cycles are never detected; the resolver only ever produced orders for the acyclic graphs in the test suite.

Reproducer input: `{"a": ["b"], "b": ["a"]}` — a depends on b, b depends on a.

Output before the fix (verbatim):

```
input: {'a': ['b'], 'b': ['a']}
buggy: accepted, order = ['b', 'a']
```

Output after the fix (verbatim):

```
fixed: rejected: cycle through a
```

The fix — check the current DFS stack before the global seen set (full file `work/c2/repro.py`):

```python
"""C2: reproduce the resolver accepting a cyclic graph, then verify the fix."""

# --- original (buggy) -------------------------------------------------------
def resolve_buggy(graph):
    order, seen = [], set()

    def visit(node, stack):
        if node in seen:
            return
        if node in stack:
            raise ValueError(f"cycle through {node}")
        stack.add(node)
        seen.add(node)
        for dep in graph.get(node, ()):
            visit(dep, stack)
        order.append(node)
        stack.discard(node)

    for node in graph:
        visit(node, set())
    return order


# --- fixed: check the current DFS stack before the global seen set ----------
def resolve_fixed(graph):
    order, seen = [], set()

    def visit(node, stack):
        if node in stack:
            raise ValueError(f"cycle through {node}")
        if node in seen:
            return
        stack.add(node)
        seen.add(node)
        for dep in graph.get(node, ()):
            visit(dep, stack)
        order.append(node)
        stack.discard(node)

    for node in graph:
        visit(node, set())
    return order


REPRO = {"a": ["b"], "b": ["a"]}  # a depends on b, b depends on a

print("input:", REPRO)
print("buggy:", end=" ")
try:
    print("accepted, order =", resolve_buggy(REPRO))
except ValueError as e:
    print("rejected:", e)
print("fixed:", end=" ")
try:
    print("accepted, order =", resolve_fixed(REPRO))
except ValueError as e:
    print("rejected:", e)

# sanity: acyclic graphs still resolve, in a valid build order
AC = {"app": ["lib", "util"], "lib": ["util"], "util": []}
o = resolve_fixed(AC)
print("acyclic:", o, "valid:", all(o.index(d) < o.index(n) for n in AC for d in AC[n]))

# cycle not reachable from the first top-level node
AC2 = {"x": [], "a": ["b"], "b": ["a"]}
print("late cycle:", end=" ")
try:
    print("accepted:", resolve_fixed(AC2))
except ValueError as e:
    print("rejected:", e)
```

Sanity checks from the same run (verbatim):

```
acyclic: ['util', 'lib', 'app'] valid: True
late cycle: rejected: cycle through a
```

The acyclic graph still resolves in a valid build order, and a cycle that is only reachable from a later top-level node is also rejected, so the fix does not over-reject.

## C3
Executed: wrote `work/c3/check.py` and ran `python3 work/c3/check.py`

Output (verbatim):

```
mf(1,2,3)  = (1, 2, 3)
mf(1,'2,3') = (1, 2, 3)   (expected (1, '2,3'))
collision bug: True
g('a','b','c') = ('a', 'b', 'c')
g('a,b','c')   = ('a', 'b', 'c')   (expected ('a,b','c'))
h(1)      = (1, 0)
h(1, b=5) -> TypeError: memoize.<locals>.wrapper() got an unexpected keyword argument 'b'
8 threads, same key: body executed 8 times (race, no locking)
```

Verdict: **not correct.**

1. Key collisions (the decisive defect). The cache key is `",".join(str(a) for a in args)`, which is not injective. `mf(1, 2, 3)` and `mf(1, "2,3")` both produce the key `"1,2,3"`, so the second call returns the first call's result `(1, 2, 3)` instead of `(1, "2,3")` — shown in the output above. The same happens with any arguments whose stringifications concatenate identically, e.g. `g('a','b','c')` vs `g('a,b','c')`. Any two distinct argument tuples with the same comma-joined string will silently return each other's cached values.
2. Keyword arguments are broken. The wrapper only accepts positional arguments; calling the memoized function with a keyword (`h(1, b=5)`) raises `TypeError` even though the underlying function supports it. Even if it did not, the key is built only from `args`, so calls differing only in keyword arguments would collide.
3. No locking. The check-then-set on `cache` is not atomic: with 8 threads calling the same key concurrently, the body executed 8 times (shown above). This is a performance/correctness race (observers may see intermediate state; the function may run with side effects 8 times).

A correct version would key on the argument tuple itself (requiring hashable arguments, e.g. `key = args`), forward `*args, **kwargs` into the key, and guard the cache with a lock if thread safety is required.

## C4
Executed: wrote `work/c4/bench.py` and ran `python3 work/c4/bench.py`

Replacement: a Fenwick (binary indexed) tree over coordinate-compressed ranks. For each value, the number of earlier strictly-smaller values is a prefix sum over ranks; each step is O(log n), so the whole function is O(n log n) versus O(n²) for the original. Duplicates are handled because the query is over rank `r-1` (strictly smaller), and negative numbers need no special handling because compression, not magnitude, defines the ranks.

```python
"""C4: original O(n^2) vs Fenwick-tree O(n log n) count_smaller_before."""

import random
import time


def count_smaller_before(values):
    """For each i, how many j < i have values[j] < values[i]."""
    out = []
    for i, v in enumerate(values):
        n = 0
        for j in range(i):
            if values[j] < v:
                n += 1
        out.append(n)
    return out


def count_smaller_fast(values):
    """Fenwick tree over coordinate-compressed ranks. O(n log n)."""
    n = len(values)
    if n == 0:
        return []
    uniq = sorted(set(values))
    rank = {v: i + 1 for i, v in enumerate(uniq)}
    m = len(uniq)
    tree = [0] * (m + 1)
    out = [0] * n
    for i, v in enumerate(values):
        r = rank[v]
        s = 0
        j = r - 1
        while j:
            s += tree[j]
            j -= j & -j
        out[i] = s
        j = r
        while j <= m:
            tree[j] += 1
            j += j & -j
    return out


def main():
    random.seed(20260913)

    # --- equivalence: randomised, duplicates, negatives ---
    trials = 0
    for _ in range(300):
        n = random.randint(0, 400)
        style = random.choice(("wide", "dup", "neg", "mixed"))
        if style == "wide":
            data = [random.randint(-10**9, 10**9) for _ in range(n)]
        elif style == "dup":
            data = [random.randint(0, 5) for _ in range(n)]
        elif style == "neg":
            data = [random.randint(-50, -1) for _ in range(n)]
        else:
            data = [random.choice([7, 7, -3, 0, 42, -10**6]) for _ in range(n)]
        if count_smaller_before(data) != count_smaller_fast(data):
            print("MISMATCH on", data)
            return
        trials += 1
    for edge in ([], [1], [5, 5, 5], [3, 1, 2], [-1, -2, -3], [2, 1, 2, 1]):
        assert count_smaller_before(edge) == count_smaller_fast(edge), edge
    print(f"equivalence: {trials} random trials + 6 edge cases, all identical")

    # --- timings ---
    sizes_orig = [2000, 5000, 10000]
    print("\noriginal O(n^2):")
    for n in sizes_orig:
        data = [random.randint(0, 10**6) for _ in range(n)]
        t0 = time.perf_counter()
        count_smaller_before(data)
        dt = time.perf_counter() - t0
        print(f"  n={n:>7}: {dt:8.3f}s")

    big = [random.randint(0, 10**6) for _ in range(200_000)]
    t0 = time.perf_counter()
    r = count_smaller_fast(big)
    dt = time.perf_counter() - t0
    print(f"\nFenwick O(n log n): n=200000: {dt:.3f}s  (result len {len(r)})")
    # spot-check the big run against the original on a 2000 prefix
    assert r[:2000] == count_smaller_before(big[:2000])
    print("spot-check: first 2000 entries of the 200k run match the original")


if __name__ == "__main__":
    main()
```

  n=   2000:    0.044s

  n=  10000:    1.354s

- Equivalence: 300 randomised trials with n from 0 to 400 across four input styles (wide-range, heavy duplicates, all-negative, mixed small-value with duplicates) plus six edge cases (empty, single element, all identical, and three small hand-picked lists) — all identical to the original. ## L1
(a) The tier ordering, shallowest to deepest, is: **registry < catalog < index < metrics** (as declared in `corelib/locking.py`: `TIERS = ("registry", "catalog", "index", "metrics")`). The rule governing two locks: a thread may only acquire locks in **strictly ascending tier order** — while holding a tier it may acquire the same tier (all tier locks are reentrant) or a deeper tier, but never a shallower one (a thread holding `index` must not acquire `catalog`). The rule applies transitively across call boundaries: if a function holding a lock calls a helper that acquires another lock, the pair must still ascend. In code, `ascending(first, second)` returns `TIER_RANK[first] <= TIER_RANK[second]`.

(b) Helpers that do not take a lock themselves are named with a trailing **`_locked`** suffix; the name signals that the caller must already hold the tier named in the helper's docstring, and the helper takes no lock of its own. Two examples from the corpus:
- `_bump_generation_locked` in `svc/catalog_ops.py` — docstring "Caller must hold ``catalog``"; it mutates `_entries` without acquiring anything.
- `_write_shard_locked` in `svc/reindex_07.py` — docstring "Caller must hold ``index``"; it writes `_shards` without acquiring anything.
(others in the corpus: `_incr_locked` in `svc/metrics_sink_02.py`, and `_rollup_locked` in every numbered shard class.)

(c) The numbered shard families in `svc/` (each 26 shards, `_00` through `_25`), with the single lock tier each shard class uses:

| Family | Files | Tier |
|---|---|---|
| `svc/bundle_NN.py` | bundle_00 … bundle_25 | `catalog` |
| `svc/cache_NN.py` | cache_00 … cache_25 | `catalog` |
| `svc/digest_NN.py` | digest_00 … digest_25 | `metrics` |

(d) `ascending("metrics", "catalog")` returns **False**. `TIER_RANK["metrics"]` is 3 and `TIER_RANK["catalog"]` is 1, and `ascending` returns `TIER_RANK[first] <= TIER_RANK[second]`, i.e. `3 <= 1`, which is false. The reason: `metrics` is the deepest tier and `catalog` is shallower, so acquiring `metrics` and then `catalog` would be a descent in the hierarchy — exactly the ordering the rule forbids (a thread holding `metrics` must release it before acquiring `catalog`).

## L2
(a) The violating call path:

- It starts in **`svc/reindex_07.py`, function `rebuild_shard`**.
- First acquisition, in `rebuild_shard` itself:
  ```python
  with locks.index:
      _write_shard_locked(shard, terms)
      generation = refresh_catalog_entry(shard, payload)
  ```
- While still holding `index`, it calls `refresh_catalog_entry(shard, payload)`. The second acquisition happens in **`svc/catalog_ops.py`, function `refresh_catalog_entry`**:
  ```python
  def refresh_catalog_entry(key: str, payload: dict) -> int:
      with locks.catalog:
          ...
  ```
- So the order of acquisitions is **`index` then `catalog`**. `TIER_RANK["index"]` is 2 and `TIER_RANK["catalog"]` is 1, so the pair descends the hierarchy. This violates the rule in `corelib/locking.py` ("A thread holding ``index`` must not acquire ``catalog``; it must release ``index`` first"), and the rule's transitivity clause covers exactly this shape: the violation is invisible in any single function body — `rebuild_shard` only acquires `index`, and `refresh_catalog_entry` only acquires `catalog` — it exists only in the call between the two files. It is a live deadlock hazard: `svc/audit_11.py::sweep` legitimately holds `catalog` while acquiring `index` (the ascending direction), so one thread in `sweep` and one in `rebuild_shard` can each hold the lock the other needs.

Paths considered and rejected as legal:
- `svc/reindex_03.py::rebuild_from_snapshot` → `svc/catalog_ops.py::read_catalog_snapshot` — legal: `read_catalog_snapshot()` (which acquires `catalog`) is called and returns *before* `with locks.index:`; the acquisitions are sequential, not nested, and the pair ascends catalog → index.
- `svc/audit_11.py::sweep` → `svc/audit_11.py::_touch_index_stat` — legal: holds `catalog` (rank 1) and acquires `index` (rank 2); strictly ascending, the direction the module docstring says is permitted.
- `svc/legacy_notes_04.py::compact` — legal: takes only `catalog`. Its docstring describes an old index-then-catalog path, but the current code was rewritten (2023-08 note) to take `catalog` first and no longer acquires `index` at all.
- `svc/metrics_sink_02.py::incr` — legal: re-enters the *same* tier (`metrics` while holding `metrics`); the hierarchy explicitly permits reacquiring the same tier (all tier locks are reentrant `RLock`s).
- `svc/catalog_ops.py::refresh_catalog_entry` → `svc/catalog_ops.py::_bump_generation_locked` — legal: the `_locked` helper takes no lock of its own; the only acquisition on the path is `catalog`.
- `svc/reindex_07.py::rebuild_shard` → `svc/reindex_07.py::_write_shard_locked` — legal: `_locked` helper, no acquisition; the caller already holds `index`.

(b) The ceiling: **`HARD_MEMORY_BUDGET = 2 << 30` (2 GiB = 2,147,483,648 bytes), stated in `corelib/limits.py`**. The same file states the commit formula — for each *enabled* pool the commit is `workers * prefetch_depth * BUFFER_BYTES` with `BUFFER_BYTES = 1 << 20` (1 MiB = 1,048,576 bytes) — and that "the sum over enabled pools must stay strictly under the budget" and "pools constructed with ``enabled=False`` are never started and commit nothing."
