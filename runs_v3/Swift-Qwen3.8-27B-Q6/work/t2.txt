Cache coherence is the discipline of keeping multiple copies of the same data consistent with one another. It appears at two scales: inside a processor, where every core keeps a private cache of main memory, and across a distributed system, where every replica keeps its own copy of shared state. This essay addresses the single-processor problem, the older and more precisely defined one.

The basic unit of coherence is the cache line, typically sixty-four bytes. Each core's cache holds lines in one of several states, most famously the Modified, Exclusive, Shared and Invalid states of the MESI protocol. A line in the Shared state exists in several caches with the same value. A core that wants to write a line that is Shared elsewhere must first obtain exclusive ownership: it broadcasts an invalidate, the other caches drop their copies, and only then may the writer modify its line. A core that reads a line held Modified elsewhere must first fetch the newest value. Invalidate-on-write and newest-value-on-read are the entire engine of coherence.

Why is this necessary at all? Because caches exist for speed. A core can read its L1 cache in a single cycle, but main memory takes tens of cycles. If each core simply wrote into its own copy, the machine would silently diverge: one core's store would be invisible to another, and programs relying on shared memory, such as a lock variable, would break. Coherence restores the illusion of a single address space: every core sees its own writes immediately, and eventually sees every other core's writes, in an order that respects the programmer's memory model.

The hardware cost is real: every cache must watch the interconnect for transactions that mention its lines, a process called snooping. In a modern chip, coherence traffic itself can dominate power consumption. Designers therefore trade sophistication for efficiency. Directory-based protocols replace broadcast snooping with a central directory that tracks which cores hold which lines, trading memory for bandwidth. Non-inclusive caches reduce the pressure of keeping copies of copies. Prefetching adds further complexity, because the hardware guesses at future coherence events and must be able to cancel its guesses.

Coherence is not the same thing as consistency. Coherence is a property of the hardware: it guarantees that stores to the same address are observed in a single total order by all cores. Consistency is a property of the memory model that the compiler and hardware jointly implement for the programmer. The x86 model is strong: a store becomes visible to other cores in program order, and loads are not reordered past stores. The ARM and RISC-V models are weaker: they permit reorderings that the coherence protocol faithfully delivers, and the programmer must insert explicit barriers when a stronger order is needed. The protocol does not care which model is in force; it guarantees only that the order it produces is a valid one.

The protocol's guarantee is a total order on cache-line transactions, but the memory model decides which of those orders the programmer may rely on. A lock built with compare-and-swap is safe on x86 without a fence because the model promises store-load ordering; on ARM the same lock needs an acquire barrier on the load and a release barrier on the store. The hardware makes both work; the model decides the cost.

Three failure modes illustrate what happens when the discipline slips. First, false sharing: two cores write to different variables that happen to sit on the same line. The protocol cannot see intent; it sees only addresses. The line ping-pongs between cores, each write invalidating the other's copy, and throughput collapses by an order of magnitude. The fix is padding, a purely organizational change the hardware rewards. Second, benign races that stop being benign: a flag checked without a barrier may be hoisted above the initialization it guards, and the protocol faithfully delivers the flag before the data it announces. Third, speculative execution: the processor may execute a store speculatively and discard it, but the coherence traffic it generated is real and visible, which is why attacks such as Spectre could read data across security boundaries.

The deeper lesson is that coherence is a contract between hardware and software, and the hardware's side is deliberately minimal. The protocol guarantees a total order of line transfers; everything above that, the ordering of operations, the visibility of initialization, the atomicity of compound actions, is the memory model's job. Engineers who understand only the hardware picture write code correct on one architecture and broken on another; engineers who understand only the model picture are surprised by false sharing and the power cost of their fences.

At the distributed scale, the same ideas reappear under new names: a write invalidating replicas is an invalidate message; a directory protocol is a metadata service; the memory model is the consistency level a database offers, from read-your-writes to linearizability. The single-processor problem was solved by making the order of operations explicit and separating the guarantee the hardware makes from the guarantee the programmer needs. Distributed systems are still negotiating that same separation, and they fail in the same places: by assuming a stronger order than the protocol provides, or by paying for one they do not need.

Cache coherence, then, is not a hardware curiosity. It is the engineering of shared memory itself: a total order on copies, a minimal hardware guarantee, a memory model on top, and a list of failure modes that punishes anyone who confuses the layers.
